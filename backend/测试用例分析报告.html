三、逐类可行性分析

3.1 RouteChains（ccr-approval）

✅ 完全可行 — 纯静态工具类，零依赖，直接测试

类信息

属性值
类型final class，全静态方法
依赖仅 cn.hutool.core.util.StrUtil（工具类）和 java.util.List
构造函数private（不可实例化）
Mock 需求无 — 纯逻辑，零外部依赖

可行性分析

这是最容易测试的类。三个静态方法 fullChain()、of()、nextNode() 都是纯函数，输入输出确定，不涉及任何外部状态。

测试策略：直接调用静态方法，验证返回值。无需任何 Mock。

风险：无。唯一注意点是 of() 返回 subList（视图），测试中验证内容即可。

核心逻辑拆解

贷款链: BRANCH_MANAGER → DEPT_GENERAL_MANAGER → VICE_PRESIDENT → SIX_PEOPLE_GROUP 存款链: BRANCH_MANAGER → SIX_PEOPLE_GROUP fullChain("DEPOSIT") → [BRANCH_MANAGER, SIX_PEOPLE_GROUP] fullChain("LOAN"/其他) → [BRANCH_MANAGER, DEPT_GENERAL_MANAGER, VICE_PRESIDENT, SIX_PEOPLE_GROUP] of("LOAN", "VICE_PRESIDENT") → [BRANCH_MANAGER, DEPT_GENERAL_MANAGER, VICE_PRESIDENT] (截断到该节点) of("LOAN", null) → 全链 (routeCode 为空) of("LOAN", "UNKNOWN") → 全链 (不在链上，回退) of("DEPOSIT", "BRANCH_MANAGER") → [BRANCH_MANAGER] nextNode("BRANCH_MANAGER") → "DEPT_GENERAL_MANAGER" nextNode("SIX_PEOPLE_GROUP") → null (已在终点) nextNode("UNKNOWN") → null (不在链上)

3.2 RuleEngineImpl（ccr-rule）

✅ 完全可行 — 4 个 Mapper + 1 个 CacheUtil 全部可 Mock，逻辑复杂但路径清晰

类信息

属性值
类型@Service，3 个 public 方法
依赖（需 Mock）CcrRateRuleMapper、CcrRateRuleSetMapper、CcrProductRateLimitMapper、CcrCacheUtil
注入方式@Resource（字段注入）
Mock 方案@Mock + @InjectMocks 标准模式

可行性分析

三个 public 方法均可完整覆盖：

  • calcRoute(ruleSetId, input) — 规则匹配引擎，8+ 维度过滤 + 优先级排序 + 多匹配检测
  • validateContinuity(ruleSetId) — 区间连续性校验（空档/重叠/非法区间）
  • checkHardBoundary(businessType, productCode, rate) — 硬边界利率校验（缓存优先 + DB 回源）

技术要点：

  • Mapper 用 when(mapper.selectList(any())).thenReturn(...) mock，LambdaQueryWrapper 参数用 any() 匹配
  • selectById 用 when(ruleSetMapper.selectById(eq(id))).thenReturn(...)
  • cacheUtil.get(key) 可模拟缓存命中/未命中两种路径
  • match() 是 private 方法，通过 calcRoute 的输入组合间接测试各维度

难点 — 8+ 维度匹配逻辑：

match() 方法有 8 个字符串维度 + 金额区间 + 集团额度区间 + 期限区间，共 11 个条件分支。需要为每个维度设计"匹配/不匹配"的测试对。空条件=通配是关键规则。

难点 — 金额基准选择：

// amountBasis 默认 GROUP_TOTAL_CREDIT: 用 groupCreditTotal // amountBasis = APPLY_AMOUNT: 用 applyAmount // groupCreditTotal 为 null: 用 applyAmount BigDecimal amountBasis = in.getGroupCreditTotal() != null && !"APPLY_AMOUNT".equals(in.getAmountBasis()) ? in.getGroupCreditTotal() : in.getApplyAmount();

需要单独测试这三种基准选择路径。

3.3 NotificationServiceImpl（ccr-message）

⚠️ 可行，但需特殊处理 — List 类型注入 + JdbcTemplate 原生 SQL + 多层私有方法

类信息

属性值
类型@Service @Slf4j，4 个 public 方法
依赖（需 Mock）CcrNotificationRuleMapper、CcrNotificationRecipientMapper、CcrNotificationLogMapper、JdbcTemplate、List<RecipientResolver>、List<MessageSender>
注入方式@Resource（字段注入），@Value（maxRetry）
Mock 方案⚠️ 不能用 @InjectMocks 自动注入 List 字段，需 ReflectionTestUtils.setField 手动设置

可行性分析

挑战 1：List 类型注入

recipientResolvers 和 messageSenders 是 @Resource List<XXX> 类型。Spring 会自动收集所有实现类注入，但 @InjectMocks 无法处理 List 类型。

解决方案：用 @Mock 创建单个 resolver/sender 实例，放入 List 中，用 ReflectionTestUtils.setField 注入：

@Mock private RecipientResolver mockResolver; @Mock private MessageSender mockSender; @BeforeEach void setUp() { service = new NotificationServiceImpl(); ReflectionTestUtils.setField(service, "recipientResolvers", List.of(mockResolver)); ReflectionTestUtils.setField(service, "messageSenders", List.of(mockSender)); ReflectionTestUtils.setField(service, "maxRetry", 3); }

挑战 2：JdbcTemplate 原生 SQL

notifyEvaluation 内部通过 jdbcTemplate.queryForList(sql, args) 查询 ccr_commitment_plan 和 ccr_tracking_evaluation 表。需要 mock jdbcTemplate.queryForList 返回 List<Map<String, Object>>。

解决方案：用 when(jdbcTemplate.queryForList(anyString(), any(Object[].class))).thenReturn(...)，返回构造的 Map 列表。

挑战 3：DigestUtil.md5Hex 静态方法

buildMessageKey 和 sendNotification 内部调用 DigestUtil.md5Hex()（Hutool）。这是纯函数，输入相同输出确定，无需 mock，直接验证输出格式即可。

挑战 4：方法间调用链长

notifyEvaluation 内部调用了 buildContext、buildPlaceholders、upgradeTypes、resolveRecipients、inCoolDown、repeatExceeded、renderTemplate、sendNotification 等多个私有方法。测试需同时 mock 多个 Mapper 调用。

解决方案：sendNotification 单独测试（4 个 public 方法之一），notifyEvaluation 端到端 mock 测试。

3.4 WarmFlowServiceImpl（ccr-workflow）

⚠️ 可行，但需特殊处理 — 静态工厂方法 + warm-flow API 对象构建复杂

类信息

属性值
类型@Service @Slf4j，6 个 public 方法
依赖（需 Mock）JdbcTemplate、DefService、InsService、TaskService、HisTaskService（warm-flow 接口）
注入方式@Resource（字段注入）
静态方法依赖FlowEngine.newIns()、FlowEngine.newHisTask()、IdUtil.getSnowflakeNextId()
Mock 方案@Mock + @InjectMocks + mockStatic(FlowEngine.class)

可行性分析

挑战 1：FlowEngine 静态工厂方法

recordBusinessTrail 和 findOrCreateTrailInstance 内部调用了 FlowEngine.newIns() 和 FlowEngine.newHisTask()。这两个是 warm-flow 的静态工厂方法，返回可变实体对象。

解决方案：用 mockStatic(FlowEngine.class) mock 静态方法，返回 mock 的 Instance/HisTask 对象：

try (MockedStatic<FlowEngine> mocked = mockStatic(FlowEngine.class)) { Instance mockIns = mock(Instance.class); mocked.when(FlowEngine::newIns).thenReturn(mockIns); // test... }

挑战 2：warm-flow API 对象链式调用

findOrCreateTrailInstance 和 recordBusinessTrail 中对 Instance 和 HisTask 使用了链式 setter（setXxx().setYyy()...）。Mock 对象的 setter 返回 null 会 NPE。

解决方案：mock 的 Instance/HisTask 需要 RETURNS_DEEP_STUBS 答案，或手动配置每个 setter 返回 mock 自身。更简单的方案是让 FlowEngine.newIns() 返回真实对象（如果可实例化）而非 mock。

挑战 3：ensureStandardFlow 的 synchronized + 吞异常

ensureStandardFlow 是 synchronized 方法，且内部 try-catch 吞掉所有异常。测试需验证：已发布时跳过、未发布时创建、异常时不抛出。

挑战 4：todoTasks 纯 JdbcTemplate

todoTasks 是纯 SQL 查询，mock jdbcTemplate.queryForList 即可。最简单。

  • 框架支持：spring-boot-starter-test 已全局声明，JUnit 5 + Mockito 5.x（含 inline mock maker）开箱即用
  • 依赖可 Mock：所有外部依赖（Mapper、CacheUtil、JdbcTemplate、warm-flow Service）均为接口，Mockito 可完美 mock
