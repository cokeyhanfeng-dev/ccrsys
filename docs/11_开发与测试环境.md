# 开发与测试环境

## 1. 隔离原则

- 宿主机只复用满足版本要求的 Node、Maven、Docker Desktop。
- JDK 17 安装在项目 `.tools/`，不会修改系统 `JAVA_HOME`、`PATH` 或默认 Java。
- Maven 依赖写入项目 `.cache/m2/repository`，不会写入 `~/.m2/repository`。
- npm 缓存写入项目 `.cache/npm`，依赖写入 `frontend/node_modules`。
- MySQL、Redis 以及完整测试应用只运行在 Docker 的 `ccrsys-test` 项目中。
- 测试容器不会随 Docker Desktop 自动重启，统一通过 `./dev infra-up` 或 `./dev app-up` 显式启动。
- `.tools/`、`.cache/`、`node_modules/`、`dist/`、`target/` 均不提交 Git。

当前端口均仅绑定 `127.0.0.1`：

## 2. 首次初始化

Windows 轻量打包使用根目录 `release.cmd [1|2|12]`，工具预检使用 `release.cmd 12 -CheckOnly`。需要 Windows PowerShell 5.1+、Git、tar，以及所选构建对应的 JDK 17/Maven 3.9 或 Node 20+；后端默认执行测试。项目内工具路径、会话级 `CCR_JAVA_HOME` 和缓存隔离详见 `docs/31_离线增量部署手册.md` 的 Windows 小节。此入口仅构建 Jar/dist，不启动或重建测试容器。

先启动 Docker Desktop，然后执行：

```bash
./dev setup
./dev versions
```

当前 macOS arm64 环境会下载经过 SHA-256 校验的 Temurin JDK 17.0.20+8。系统 Maven 3.9.x 和 Node 20+ 可直接复用；缺少兼容 Maven 时，引导脚本会下载经过 SHA-512 校验的 Maven 3.9.16 到 `.tools/maven`。

## 3. 日常开发

只启动基础设施：

```bash
./dev infra-up
```

本地启动后端和前端：

```bash
./dev backend-run
./dev frontend-run
```

后端使用 `local` profile，连接 Docker 中的 MySQL/Redis。前端开发服务器仍位于 http://127.0.0.1:3000，代理到本地后端 `8080`。

## 4. 完整测试环境

```bash
./dev app-up
./dev smoke
./dev ps
```

登录冒烟默认使用隔离测试环境的统一初始口令并校验首登链路；需要覆盖时通过当前命令的
`CCR_SMOKE_PASSWORD` 环境变量传入，禁止将生产口令写入脚本或提交到仓库。

`app-up` 会构建并启动 MySQL、Redis、Spring Boot、Nginx/Vue 四个容器。首次启动 MySQL 时由
`scripts/dev/mysql-init.sh` 按以下顺序初始化：

1. 根目录中的基础结构、基础配置与基础种子（由脚本显式列出，包含 `01-09` 以及 `11`、`12`、`13`、`14`、`16`、`18`、`19`、`25`）；
2. `db/incr/*.sql`：按文件名升序执行全部增量；
3. 模拟数据、测试数据及清理脚本（`10`、`15`、`17`、`20`、`22`、`26`）。

`db/incr_prod_*.sql` 是存量生产环境的聚合升级脚本，不参与全新测试库初始化。

停止容器并保留测试数据：

```bash
./dev app-down
```

清空专用测试数据库并重新初始化：

```bash
./dev reset
./dev app-up
./dev smoke
```

`reset` 只删除 Compose 项目 `ccrsys-test` 的容器、网络和专用数据卷。

## 5. 提交前验证

```bash
./dev verify
```

它会使用项目 JDK/Maven 缓存执行后端全部单元测试，并使用兼容的本机 Node 执行 `npm ci` 与生产构建。涉及数据库、缓存、接口、权限、工作流或部署的改动还要执行：

```bash
./dev app-up
./dev smoke
```

查看日志：

```bash
./dev logs backend
./dev logs mysql
```
# Mini-App-Plus 授信决议 API 网关（2026-09-02）

该能力默认关闭，未配置时不影响原有申请。启用后需要在部署环境提供以下变量，接口契约和私有桶兑换要求见 `docs/30_API网关授信决议集成.md`。

```bash
CCR_INTEGRATION_CREDIT_RESOLUTION_ENABLED=true
CCR_INTEGRATION_CREDIT_RESOLUTION_GATEWAY_BASE_URL=https://api-gateway.internal.example
CCR_INTEGRATION_CREDIT_RESOLUTION_TOKEN_PATH=/miniapp/auth/token
CCR_INTEGRATION_CREDIT_RESOLUTION_APP_ID='<网关分配的应用标识>'
CCR_INTEGRATION_CREDIT_RESOLUTION_API_KEY='<至少16位，生产建议32字节以上随机API Key>'
CCR_INTEGRATION_CREDIT_RESOLUTION_ALLOWED_DOWNLOAD_HOSTS=minio.internal.example
```

Docker Compose 启动时可将这些变量写入服务器上的独立文件，例如
`/data/ccr/config/credit-resolution.env`（权限建议设为 `600`，不要放入代码仓库）：

```bash
# 文件内容示例（等号右侧替换为部署环境真实值）
CCR_INTEGRATION_CREDIT_RESOLUTION_ENABLED=true
CCR_INTEGRATION_CREDIT_RESOLUTION_GATEWAY_BASE_URL=https://api-gateway.internal.example
CCR_INTEGRATION_CREDIT_RESOLUTION_APP_ID=example-app-id
CCR_INTEGRATION_CREDIT_RESOLUTION_API_KEY=replace-with-secret
CCR_INTEGRATION_CREDIT_RESOLUTION_ALLOWED_DOWNLOAD_HOSTS=minio.internal.example
```

启动后端服务：

```bash
docker compose --env-file /data/ccr/config/credit-resolution.env up -d backend
```

需要同时构建并启动全部服务时：

```bash
docker compose --env-file /data/ccr/config/credit-resolution.env up -d --build
```

查看 Compose 最终生成的启动配置：

```bash
docker compose --env-file /data/ccr/config/credit-resolution.env config
docker compose ps
```

`docker compose config` 会展开环境变量，其中可能包含 API Key，仅在受控终端查看，不要复制到日志或工单。
已运行容器可通过 `docker inspect ccr-backend` 查看 Docker 保存的容器配置；其中同样包含环境变量明文。

本项目隔离测试栈由 `./dev app-up` 启动，底层命令可在根目录 `dev` 的 `app-up)` 分支查看。
测试栈需要注入网关参数时，直接在当前 shell 导出上述变量后运行 `./dev app-up`；
`compose.test.yml` 会把这些变量传入后端容器。

CCRSYS 使用 `X-App-Id/apikey` 并携带当前登录用户名（绩效码）换取该人员的 Mini-App-Plus Token，随后携带 Bearer Token 调用决议查询和文件兑换路由。令牌按绩效码分别缓存，到期前刷新，401 时只重新登录并重试一次。Mini-App-Plus 需启用 `MINIAPP_CCR_GATEWAY_AUTH_ENABLED`，配置与网关一致的 App ID/API Key，并给允许访问的人员绑定 `ccr_service` 角色。API 网关需要透传鉴权头并启用时间窗口、流水号防重放、限流和来源限制。禁止在仓库、Compose 文件和命令历史中填写真实 API Key、令牌、MinIO AccessKey 或 SecretKey；不得使用 `123456`、`root123` 等测试弱口令。

## 生产轻量打包与部署

开发机执行以下任一命令：

```bash
./dev release 1   # 仅后端 Jar
./dev release 2   # 仅前端 dist
./dev release 12  # 后端和前端
./dev release     # 交互选择 1/2/12
```

脚本在 `release/` 生成 `ccr-release-<时间>-<类型>.tar.gz` 和 `deploy-release.sh`。将两者上传至生产服务器 `/tmp`，执行：

```bash
bash /tmp/deploy-release.sh 1    # 仅后端
bash /tmp/deploy-release.sh 2    # 仅前端
bash /tmp/deploy-release.sh 12   # 全部
```

部署脚本自动选择 `/tmp` 中最新发布包、校验 SHA-256、备份旧 Jar/静态文件、替换并清理临时解压目录。默认后端容器自动识别 `ccr-prod-backend` 或 `ccr-backend`，也会尝试查找唯一包含 `/app/app.jar` 的运行容器；前端目录默认为 `/data/ccr/frontend`。环境不同可设置 `CCR_BACKEND_CONTAINER`、`CCR_BACKEND_JAR_PATH`、`CCR_FRONTEND_DIR`、`CCR_BACKUP_DIR`、`CCR_BACKEND_HEALTH_URL`。发布包留在 `/tmp` 便于核对和回滚，确认上线无误后可手工删除。
