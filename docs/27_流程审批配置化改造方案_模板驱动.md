# 流程审批配置化改造方案（流程模板驱动）

> 状态：设计稿，待评审。选型结论：方案一——流程模板表驱动，分两期实施（第一期最小改动落地，第二期路由引擎模板化）。
> 本方案替代 `docs/26_流程审批引擎化改造方案_WarmFlow驱动.md`（方案二，经评审未采纳：重写审批域风险过高、在途引擎单不可回退）。
> 边界（已与业务确认）：串行节点自由增删改 + 特殊节点（表决/行长/秘书岗）保留现有业务逻辑 + 在途单按冻结口径走完。
> 依据：当前仓库 HEAD 源码核实，引用格式 `文件:行号`。

---

## 1. 目标与非目标

**目标**：

1. 审批节点（含顺序）存库配置，增删节点、调整顺序**不改代码、不发版**，发布即对新提交生效。
2. 节点审批人、节点权限边界沿用现有配置体系（`ccr_node_assignee` / `ccr_node_permission`），不重建。
3. 流程模板治理沿用矩阵/LPR 同一套：草稿→送审→双人复核发布→停用，写 `ccr_config_change_log`，发布清缓存。
4. 在途单零影响：路由链本来就是提交时冻结在分项上的（`route_chain`），推进沿冻结链走，存量单无感。

**非目标**：

- 不做并行会签、任意分支拓扑；拓扑为"串行链 + 条件节点"（覆盖秘书岗场景）。
- 不重写表决、行长决策业务逻辑，只把触发判定从"节点编码字符串"改为"节点类型"。
- 不改审批人指派四层解析、不改 Warm-Flow 轨迹载体定位（流程定义仍由代码生成，只是改为按模板生成）。
- 不做在途单流程迁移。

## 2. 现状关键点（方案的依据）

| 位置 | 现状 | 改造方向 |

## 3. 数据模型

### 3.1 新增 `ccr_flow_template`（流程模板主表）

| 字段 | 说明 |
|---|---|
| `template_key` | 模板编码，如 `LOAN_STD` / `DEPOSIT_STD` / 产品自定义 |
| `template_name` | 显示名 |
| `business_big_type` | `LOAN_PUBLIC` / `LOAN_PERSONAL` / `DEPOSIT`（与矩阵口径一致） |
| `product_code` | 可空；空=该业务大类默认模板，非空=产品专属模板（优先级高于默认） |
| `status` | `DRAFT` / `REVIEW` / `EFFECTIVE` / `INVALID`（同矩阵生命周期，双人复核） |
| `effective_from` / `effective_to` | 生效窗口；同维度仅一条 EFFECTIVE |
| `publish_by` / `review_by` / `publish_time` / `remark` | 治理留痕 |

### 3.2 新增 `ccr_flow_template_node`（模板节点表）

| 字段 | 说明 |
|---|---|
| `template_id` | 所属模板 |
| `node_key` | 节点编码，如 `BRANCH_MANAGER` / `TEAM_LEADER`；同模板内唯一 |
| `node_name` | 显示名（前端节点名即取它，废弃 `NODE_LABELS`） |
| `node_type` | `NORMAL` 普通审批 / `VOTE` 六人表决 / `PRESIDENT` 行长决策 / `CONDITIONAL` 条件节点 |
| `seq` | 顺序号，增删节点后由配置页重排（10/20/30 留间隔） |
| `cond_expr` | CONDITIONAL 节点的触发条件 JSON，如 `{"amountMin":1000,"rateMax":2.6}`（仅贷款语义） |
| `remark` | 说明 |

特殊节点行为按 `node_type` 驱动（见 §5.3），`node_key` 本身不再承载语义——这就是"节点自由增加"的核心：新节点一律是 `NORMAL`，行为通用。

### 3.3 其他变更

- `ccr_config_change_log`：CONFIG_TYPE 增加 `FLOW_TEMPLATE`。
- 缓存新增 key `ccr:cfg:flow-tpl:effective`（全量 EFFECTIVE 模板 + 节点，整体缓存，发布/停用失效；登记进 `ccr_cache_config` 内置项）。
- `ccr_rate_matrix` 不改结构；二期起 `start_node_code` 在发布校验时必须在对应模板节点中存在。
- 种子：按现状生成两条模板——`LOAN_STD`（BM→GM→VP→SECRETARY[CONDITIONAL]→GROUP[VOTE]→PRESIDENT[PRESIDENT]）、`DEPOSIT_STD`（BM→GROUP[VOTE]→PRESIDENT[PRESIDENT]），直接 EFFECTIVE，与现有硬编码链等价，保证行为零变化。

## 4. 一期：链与节点字典配置化（最小改动）

目标：不改路由引擎逻辑，先让"加节点"变成纯配置操作（仍需配矩阵行，但不再需要改代码发版）。

1. `RouteChains` 改为从 `ccr:cfg:flow-tpl:effective` 缓存读链；缓存为空回退现有硬编码常量（灰度兜底，迁移零风险）。
2. 前端节点名字典改为接口下发（`GET /system/flow/templates/node-labels`，返回 node_key→node_name）。
3. 治理动作成套：模板 CRUD/送审/发布/停用 + 审计 + 缓存失效（复用 `FlowConfigController` 模式，发布校验：同模板 node_key 唯一、seq 不重、VOTE/PRESIDENT 类型节点全模板至多各一、首节点必须为 NORMAL）。
4. **一期加节点的操作路径**（也是本方案的验收场景）：配置页在 `LOAN_STD` 里插入 `TEAM_LEADER`（NORMAL，seq 介于 BM 与 GM 之间）→ 复核发布 → 按 `docs/25` §5 配矩阵行（终审岗=TEAM_LEADER、priority 顺移）和 `ccr_node_assignee` 指派 → 新提交即走新链。除矩阵 priority 顺移外全程无代码。
5. 在途兼容：分项 `route_chain` 冻结的是节点编码字符串，模板改名/删节点不影响已在链上的在途单（推进按字符串走）；**配置页对"删节点"要给醒目提示：仅影响新提交**。

一期出口标准：测试栈上零代码新增一个节点并走通"提交→新节点审批→上送→终审"全流程；存量用例全绿（`./dev verify` + `app-up` + `smoke`）。

## 5. 二期：路由引擎模板化

### 5.1 路由链构建改为模板驱动

- 路由输入（业务大类 + 产品码）→ 选模板（产品专属优先，缺省取业务大类默认）→ 取有序节点列表。
- `buildChain` 改为：从模板首节点起，沿 `seq` 到矩阵算出的终审节点截断；矩阵行 `start_node_code`（终审岗）必须是模板内节点，发布矩阵时校验，杜绝"矩阵指向模板里不存在的岗位"。
- 矩阵 `priority` 退出链路构建（保留字段，发布校验仅要求同维度组内唯一）；各岗位边界仍由矩阵行承载，计算逻辑（SPREAD/LPR±BP/交集）不变。历史 priority 顺移包袱就此消解。

### 5.2 秘书岗改为 CONDITIONAL 节点

- 模板里 `SECRETARY` 配为 `CONDITIONAL`，`cond_expr={"amountMin":1000,"rateMax":2.6}`；路由时按输入金额/利率求值，命中则节点入链（插在配置位置），不命中跳过。阈值改配置即生效，删除 `applySecretaryGate` 硬编码常量。

### 5.3 特殊节点判定改为类型驱动

- `checkOperatorAndNode` 排除普通通道的判定：从 `nodeCode == "SIX_PEOPLE_GROUP" / "PRESIDENT"` 改为查模板节点类型（VOTE/PRESIDENT）。
- 审批推进到 VOTE 类型节点 → 触发 `voteService.createGroupRound`；表决通过 → 推进到下一节点（模板里须为 PRESIDENT 类型）；PRESIDENT 类型节点 → 行长待办与 `presidentDecision`。表决/行长业务逻辑一行不改。
- 保留两条业务规则，语义显式化：**首节点=支行过手节点**（本支行限制、存款仅支行过手，绑定"模板首节点"而非 BRANCH_MANAGER 字面量）；**凡终审为 VOTE 节点必经 PRESIDENT 节点**（模板发布校验：VOTE 节点之后必须存在 PRESIDENT 节点）。

### 5.4 Warm-Flow 定义按模板生成

- 模板发布时按节点列表生成/更新 Warm-Flow 流程定义（新版本），替代 `loanNodeHandlers()` 手写与 `ensureStandardFlow` 的"已发布则跳过"。`ccr_product_route.flow_key` 继续作为产品级流程定义选择器。

### 5.5 配置页增强

- "流程模板"配置 tab：模板列表 + 节点表格编辑（增删、上下调序、类型选择、CONDITIONAL 阈值）+ 链路预览（与路由试算页打通：输入维度直接预览走哪条模板、经哪些节点、哪终审）。
- 节点指派入口跳现有指派配置；节点调价权限沿用 `ccr_node_permission`。

二期出口标准：矩阵新维度发布时不再人工维护 priority 顺序语义；秘书岗阈值改配置生效；全流程回归 + 双模板（贷款/存款）+ 产品自定义模板各一条端到端通过。

## 6. 迁移与切换

1. 增量 SQL（`db/incr/` 新编号，幂等）：建两张表 + 种子两条模板（等价现状链）+ 缓存项登记 + 字典枚举，登记 `docs/22` 台账。
2. 一期上线后行为应与现状**完全一致**（种子模板=硬编码链）；用路由试算 + 存量回归比对确认无差。
3. 在途单：冻结 `route_chain` 为字符串链，新旧模板切换对其无影响；新提交按发布时点的生效模板。
4. 回退：模板表清空或缓存删除后 `RouteChains` 回退硬编码常量，系统行为回到改造前。

## 7. 风险登记

| # | 风险 | 缓解 |
|---|---|---|
| R1 | 一期矩阵 priority 与模板 seq 可能配出不一致（链顺序与矩阵顺序矛盾） | 模板发布 + 矩阵发布双侧校验：矩阵命中行的岗位顺序必须与模板 seq 一致，冲突拒绝发布并提示 |
| R2 | 删节点/改 node_key 影响在途单展示（冻结链里有旧编码） | 节点名接口对未知编码回退显示原编码；配置页删除前校验并警告 |
| R3 | 特殊节点类型误配（如配两个 VOTE）导致流转错乱 | 发布校验强制约束（VOTE/PRESIDENT 至多各一、VOTE 后必有 PRESIDENT、首节点 NORMAL） |
| R4 | Warm-Flow 定义按模板再生成与既有 `flw_*` 数据冲突 | 二期 POC 先行验证"发布生成新版定义"；旧定义保留只读 |

## 8. 工作量与分期

| 期 | 内容 | 粗估 |
|---|---|---|
| 一期 | 两张表 + 种子 + 缓存/审计/治理 + `RouteChains` 读模板 + 节点名接口 + 前端字典改造 + 发布校验 + 回归 | 2–3 周 |
| 二期 | 路由模板化（buildChain 改造、priority 退出）+ CONDITIONAL 节点 + 类型驱动特判 + Warm-Flow 定义生成 + 配置页 + 全链路回归 | 4–6 周 |

一期即可交付"加节点零代码"（矩阵 priority 顺移仍需人工，属配置操作）；二期把矩阵侧的手工负担也消掉。两期独立可发布，一期不是半成品。

## 9. 验证方案

- 单测：模板选择（产品专属>默认）、链截断、CONDITIONAL 求值、发布校验全部约束、缓存失效、回退兜底。
- 集成：一期"零代码加节点"验收场景；二期贷款/存款/产品自定义三模板端到端；在途冻结链不受模板变更影响的回归用例。
- 发布演练：增量 SQL 幂等重跑、`DEL ccr:cfg:flow-tpl:effective` 后重建、回退路径演练。
- 门槛按 AGENTS.md：每期 `./dev verify` + `./dev app-up` + `./dev smoke` 全绿交付。
