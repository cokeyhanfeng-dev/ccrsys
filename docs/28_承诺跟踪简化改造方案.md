# 承诺跟踪简化改造方案

> 状态：设计稿，待评审。**本方案只出设计，不含任何代码改动。**
> 背景：现承诺跟踪实现（计划/指标/成员分摊/策略/策略版本/阈值/评估 7 张表 + 4 个定时任务）超出业务实际需要，且存在口径脱节问题（计划期限硬编码 +1 年、策略按首指标冻结等）。
> 业务口径（需求方拍板，2026-08-25）：
> 1. 数仓每天推当前贡献度值；
> 2. 承诺跟踪：到截止时点判断完成/未完成，并保留历史完成情况；
> 3. 在跟踪中的：数仓值 ÷ 承诺值 = 完成比例，多指标取算术平均；
> 4. 归档：截止后完成情况单独记录（单表终态或迁移归档表均可）；
> 5. 机构达成率：直接依据已截止的完成情况统计。

---

## 1. 总体思路

一句话：**一张跟踪表 + 一张历史表 + 一个每日定时任务**，替代现有"计划-指标-策略-版本-阈值-评估"整套体系。

- 承诺的唯一来源保持现状：客户经理在申请时录入 `ccr_application_commitment`（含指标、目标值、截止日期 `end_date`），终审通过后才开始跟踪，否决不跟踪。
- 完成比例统一口径：`完成比例 = 数仓最新批次实际值 ÷ 承诺目标值`。**承诺目标类型只保留三种：目标余额（金额）/ 笔数 / 比例**，其余类型选项（新增量、累计等）全部删除（需求方拍板 2026-08-25，原决策点 D1 闭环）。三种类型在跟踪侧都是同一个公式，仅单位与展示不同。
- 到期判定唯一口径：`today > end_date` 时判定，比例 ≥ 100% 为完成，否则未完成。彻底解决"计划 +1 年 vs 承诺截止日期"的双口径问题——**`end_date` 就是唯一的时间基准**。

## 2. 数据模型（新增 2 张表，旧表保留只读）

### 2.1 `ccr_commitment_track`（承诺跟踪主表，在途与终态同表）

| 字段 | 说明 |
|---|---|
| `id` / 公共审计列 / `version_no` | 沿用 BaseEntity 口径 |
| `track_no` | 跟踪编号（`TRK`+日期+序号，业务可读） |
| `application_id` / `application_no` | 来源申请（追溯用） |
| `customer_no` / `member_customer_no` | 客户号；集团成员承诺填成员号，单户/集团整体为空 |
| `org_id` | 归属机构（申请人机构，机构达成率统计维度） |
| `metric_code` / `metric_name` | 指标编码/名称 |
| `target_kind` | 目标类型：`BALANCE` 目标余额(金额) / `COUNT` 笔数 / `RATIO` 比例；**仅此三种**，决定单位与展示格式，计算同为 实际值÷目标值 |
| `target_value` / `unit` | 承诺目标值/单位（金额=万元、笔数=笔、比例=%，随 `target_kind` 带出） |
| `end_date` | 承诺截止日期（**直接取 `ccr_application_commitment.end_date`**） |
| `latest_actual` / `latest_data_dt` | 数仓最新实际值 / 对应数据日期 |
| `complete_ratio` | 最新完成比例（每次评估更新） |
| `status` | `TRACKING` 跟踪中 / `FINISHED_MET` 已完成 / `FINISHED_UNMET` 未完成（终态） |
| `finish_time` | 判定时间（终态时写入） |

唯一键：`uk_track(app_id, metric_code, member_customer_no)`（同一申请同指标同成员只跟踪一次，天然幂等）。

### 2.2 `ccr_commitment_track_history`（评估历史表）

| 字段 | 说明 |
|---|---|
| `track_id` | 所属跟踪记录 |
| `data_dt` | 数仓数据日期 |
| `actual_value` / `complete_ratio` | 当日实际值 / 完成比例 |
| `result` | 当日快照状态：`TRACKING` / 终态（到期判定行） |
| `eval_time` / `remark` | 评估时间 / 备注（如"到期判定"） |

唯一键：`uk_history(track_id, data_dt)`，同日重复跑幂等。用途：跟踪详情页展示历史曲线、事后审计追溯"当时是什么值"。

### 2.3 归档口径（采用"单表终态即归档"）

截止判定后 `status` 置终态、`finish_time` 写入，该行即为归档记录，**不做物理迁移**。机构达成率、历史查询都按终态过滤。
理由：少一次搬运动作、少一张表、无迁移失败补偿问题；数据量年增万级以内单表完全够。若未来确需物理分离，加一个夜间搬运 job 即可，模型不变。

## 3. 业务流转

### 3.1 开始跟踪（终审触发，复用现有链路）

- 触发点不变：`ItemFinalizationServiceImpl` 分项终态 → Outbox `COMMITMENT_CREATE` 链路**保留**，只替换消费者内部实现。
- 实现改为：整单终审通过（FINAL）后，把该申请 `ccr_application_commitment` 的每条承诺行转成一条 `ccr_commitment_track`（`TRACKING`）；同申请重复触发靠 `uk_track` 幂等；否决决议不生成。
- `metric_code = OTHER`（其它类手工承诺）：**不生成跟踪记录**，维持现状仅靠 `track_desc` 手工留痕——与需求口径"不做数值跟踪"一致，也消掉现实现里 OTHER 永远 DATA_PENDING 的死角。

### 3.2 每日评估（一个定时任务）

`dailyTrackJob`，默认每日 02:30（cron 可配 `ccr.commitment.track-cron`），对全部 `TRACKING` 行逐条：

1. 取数仓 `dw_contribution_metric` 该客户（成员承诺取成员号）+ 该指标**最近批次**值；
2. 更新 `latest_actual` / `latest_data_dt` / `complete_ratio`；写一条 history（同 `data_dt` 已有则跳过，幂等）；
3. `today > end_date` → 判定：`ratio ≥ 1` 置 `FINISHED_MET`，否则 `FINISHED_UNMET`，写 `finish_time` 和一条终态 history；终态行次日起不再扫描；
4. 到期未完成的，发一条通知（客户经理 + 支行行长，复用 ccr-message 现有通道与 `message_key` 幂等），文案如"客户 X 的存款日均提升承诺已到期未完成，达成 82%"。

单条失败记日志继续下一条；数仓当日无新批次就用上一批次值继续比对（`latest_data_dt` 原样展示，页面能看到数据新旧，不做 DATA_PENDING 状态）。

### 3.3 完成比例与平均值

- 单指标：`complete_ratio = latest_actual ÷ target_value`（target 为 0 或空 → 不建跟踪记录，建跟踪时校验）。
- 申请级/客户级/机构级的"完成比例" = 其下各指标 `complete_ratio` 的**算术平均**，展示时按比例原样显示；平均值计算时单项超过 100% 按 100% 计（避免单项超额掩盖其他项未达标——见 §6 决策点 D2）。

### 3.4 机构达成率

直接查主表终态行：

```sql
SELECT org_id,
       COUNT(*)                                          AS finished_total,
       SUM(status = 'FINISHED_MET')                      AS met_count,
       SUM(status = 'FINISHED_MET') / COUNT(*)           AS met_rate,        -- 完成率(按笔数)
       AVG(LEAST(complete_ratio, 1))                     AS avg_ratio        -- 平均完成比例
FROM ccr_commitment_track
WHERE status IN ('FINISHED_MET','FINISHED_UNMET')
  AND end_date BETWEEN ? AND ?                            -- 统计区间可选
GROUP BY org_id;
```

接口沿用现有 `GET /ccr/commitments/org-achievement`，内部实现换成这条统计，前端无感。

## 4. 停用与删除清单

| 对象 | 处置 |
|---|---|
| `ccr_commitment_plan` / `ccr_commitment_metric` / `ccr_commitment_member_alloc` / `ccr_tracking_evaluation` / `ccr_tracking_policy` / `ccr_tracking_policy_version` / `ccr_tracking_threshold` | **停用保留只读**（历史数据留档，不迁移；旧数据本身口径已乱，迁移价值低——见 §6 D3） |
| `CommitmentJobs` 四个定时任务（dailyEvaluate/expiryScan/backfillRecalc/monthlySummary） | 删除，由 `dailyTrackJob` 一个替代 |
| 跟踪策略配置（params 页策略 tab、TrackingPolicyController） | 下线 |
| 承诺录入的目标类型三分支（INCREMENT/TARGET_BALANCE/CUMULATIVE） | **收敛为三种**：目标余额(BALANCE)/笔数(COUNT)/比例(RATIO)。`ccr_application_commitment.target_type` 枚举同步替换（存量数据映射：TARGET_BALANCE→BALANCE；INCREMENT/CUMULATIVE 存量行保留原值只读展示，新增只允许三种）。前端承诺录入下拉同步收敛，单位随类型联动 |
| 预警灯色/风险等级（NORMAL/WATCH/AT_RISK、DATA_PENDING）、策略试算接口 | 删除 |
| 承诺录入（`ccr_application_commitment`、end_date 必填校验）、Outbox 触发链路、ccr-message 通知通道、前端跟踪页框架 | **保留不动** |

前端跟踪页简化为一页：列表（客户/指标/承诺值/最新值/完成比例/截止日期/状态）+ 详情抽屉（历史评估列表/简单曲线）。手工 `track_desc` 入口保留。

## 5. 发布与切换

1. 增量 SQL：建 2 张新表 + 字典项，不动旧表旧数据；登记 `docs/22` 台账。
2. 切换方式：新逻辑直接替换 COMMITMENT_CREATE 消费者实现与 org-achievement 接口实现，旧策略任务配置项移除。上线时点起新终审的申请走新表；存量在 TRACKING 的旧计划按 D3 决策处理。
3. 验证：`./dev verify` + `app-up` + `smoke`；新增回归：终审触发建跟踪、每日评估幂等（同 data_dt 重跑）、到期判定（完成/未完成/OTHER 不跟踪）、机构达成率 SQL、通知幂等。
