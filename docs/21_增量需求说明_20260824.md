## 一、客户信息数仓推送增加「管户客户经理」+ 查询权限控制

### 1.1 现状核对

- 数仓推送的客户主数据两张表**均无管户客户经理字段**：
  - `caps_corp_cust_basic_info`（对公，T01/A01/E01）：etl_md5 / data_dt / cust_no / cust_name / cert_tp / cert_no / ffthlv_class / entp_charic / openact_org_no / cust_class 等
  - `caps_indv_cust_basic_info`（对私，T02/A02/E02）：etl_md5 / data_dt / cust_no / cust_nm / cert_tp / cert_no / opnact_org_no / cust_class 等
  - 集团表 `dw_customer_group_snapshot` 仅 `manager_org_id`（主办**机构**编号），非客户经理工号
- 推送机制：数仓按契约表结构加工后**直接落库到 ccr_rate**，系统侧只读、无写入接口；批次标识 = `etl_md5` + `data_dt`，业务读最新成功批次。
- 查询接口（`CustomerController.java`，`/ccr/customers`）3 个入口：
  - `GET /ccr/customers?name=` 姓名/客户号模糊搜索（对公+对私 UNION）
  - `GET /ccr/customers/{customerNo}` 客户详情
  - `GET /ccr/customers/{customerNo}/business-view` 客户业务视图
  - 当前仅类级 `@SaCheckRole("customer_manager")`（L25）**角色校验，无任何客户级/数据级权限过滤** → 任意客户经理可拉任意客户。
- 用户表：`ccr_sys_user` **无独立工号列，`username` 即工号**（数仓 dws.ccr_sys_user 同源，9 位数字，如 `023010401`）；当前登录人工号取 `AppLoginUser.requireCurrentUser().getUsername()`。

### 1.2 需求内容

1. 数仓推送的客户信息表增加「管户客户经理」字段，**工号参照 `ccr_sys_user.username`**。
2. 权限规则：
   - **无管户客户经理工号**的客户 → **任何人**可从后台拉取客户信息；
   - **有管户客户经理**的客户 → **仅该管户客户经理**可拉取客户信息。

### 1.3 数仓需修改内容

| 表 | 修改 | 说明 |
|---|---|---|
| `caps_corp_cust_basic_info` | 新增列 `mgr_no VARCHAR(64) NULL COMMENT '管户客户经理工号(参照 ccr_sys_user.username)'` | 对公 |
| `caps_indv_cust_basic_info` | 新增列 `mgr_no VARCHAR(64) NULL COMMENT '管户客户经理工号(参照 ccr_sys_user.username)'` | 对私 |
| 契约文档 | `docs/04`(T01/T02)、`docs/15`(A01/A02)、`docs/02`(E01/E02)、`db/02_external_data.sql`、`db/10_mock_external.sql` 同步加列 | 文档与造数脚本 |
| 集团表 `dw_customer_group_snapshot` | **待确认**是否也补管户（现仅主办机构） | 见决策点① |

> 数仓侧需保证 `mgr_no` 与 `ccr_sys_user.username` 格式一致（工号）。推送时若客户无管户，则 `mgr_no` 为空。

### 1.4 后端/前端需修改

- **后端 `CustomerController.java`**：`search`(L35-51)、`detail`(L54-100)、`business-view`(L117-149) 统一加管户权限判断：
  - 客户 `mgr_no` 为空 → 放行；
  - `mgr_no` 非空 → 仅当 `当前登录人 username == mgr_no` 放行；search 结果过滤掉无权客户，detail/business-view 返回无权（403/业务错误）。
  - SQL 层：search 的 WHERE 加 `(mgr_no IS NULL OR mgr_no = :loginEmpNo)`。
- **前端**：search 联想由后端过滤，前端基本不改；detail/business-view 需补"无权限查看该客户"错误提示（当前会空白）。
- 关联页面：`loan.vue`(L1257-1330)、`deposit.vue`(L400-440)、`RelatedPersonsEditor.vue`(L269-274)。

### 1.5 待确认决策点

- ① 集团客户（`dw_customer_group_snapshot`）是否也需要管户字段并纳入权限？
- ② 需求说"无管户的**任何人**可从后台拉取"——当前接口仅 `customer_manager` 角色可调。是**维持客户经理角色 + 客户级过滤**，还是**放开角色**（如行长/审计也能拉）？

## 二、贷款利率申请：新增/存量统一按「授信担保拆分明细」拆分（不再按合同/授信协议）

### 2.1 现状核对（最终方案，2026-08-25 用户拍板）

- **方向演变**：初版「存量按合同拆分」→ 用户纠偏「存量按担保方式拆分、不再关注合同」→ 最终「**新增/存量统一：只关注每笔授信按担保方式拆分的细项，不建合同关系、不回填/补全合同号**」。
- 数仓现无「授信×担保方式」拆分结构：`dw_loan_contract_snapshot`（合同级，无 guarantee_type 拆分）、`dw_mortgage_snapshot`/`dw_guarantor_snapshot`（按 `contract_no` 关联措施）、`dw_credit_agreement_snapshot`（协议）。
- 本系统存量申请旧逻辑：强制选授信协议 → 按协议项下贷款合同映射分项 → 依赖合同关系校验。

### 2.2 需求内容

**新增/存量统一「纯拆分项」模式**：只关注每笔授信按担保方式拆分的细项（担保方式 + 拆分金额 + 担保措施明细 + 原利率 + 申请利率），**不建合同关系（`ccr_pricing_item_contract_rel`）、不回填/补全合同号**。拆分项数据由**数仓新增「授信担保拆分明细表」推送**，本系统存量申请直接读取展示勾选 + 填申请利率。

### 2.3 数仓需修改内容（新增 2 张表，契约编号 T21/T22，见 docs/09/15）

**T21 `dw_credit_split_snapshot`（拆分项主表）**：每行 =「授信 × 担保方式」一个拆分细项。
| 字段 | 类型 | 说明 |
|---|---|---|
| split_no | VARCHAR(64) | 拆分项编号（唯一业务键，勾选/防重） |
| cust_no | VARCHAR(64) | 客户号 |
| credit_no | VARCHAR(64) | 所属授信编号（顶层授信维度） |
| contract_no | VARCHAR(64) | 关联贷款合同号（仅参考，不作为拆分键） |
| guarantee_type | VARCHAR(32) | MORTGAGE/GUARANTEE/PLEDGE/BILL_MARGIN/CREDIT_MARGIN/CERTIFICATE_DEPOSIT |
| split_amount | DECIMAL(18,4) | 拆分金额（万元） |
| currency | VARCHAR(8) | 币种 |
| original_rate | DECIMAL(7,4) | 原利率%（预填参考） |
| maturity_date | DATE | 到期日 |
| split_status | VARCHAR(16) | EFFECTIVE 有效 / SETTLED 结清 |

**T22 `dw_credit_split_measure_snapshot`（拆分项担保措施表）**：每行 = 一个措施，抵押物/保证人字段**逐列照抄现有 `dw_mortgage_snapshot` / `dw_guarantor_snapshot`**（用户要求对齐现有表结构，不塞 ext_json）。
- 抵押物：`mortgage_type/mortgage_name/owner_name/owner_cert_no/register_no/assess_value/assess_date/mortgage_ratio/mortgage_addr`
- 保证人：`guarantor_name/guarantor_cert_type/guarantor_cert_no/guarantee_type/guarantee_amount/guarantee_balance`
- 通用（质押/保证金/存单）：`measure_type/measure_name/collateral_no/currency/ext_json`

**系统表改动**：`ccr_pricing_item` 加 `source_split_no`（存量调息来源拆分项编号，溯源/防重；新增为空）。

### 2.4 后端/前端需修改（已实施）

- **后端**：
  1. `DataWarehouseService`：加 `creditSplits`（读 T21，仅 EFFECTIVE 最新批次）+ `splitMeasures`（按 split_no 批量读 T22）；
  2. `CustomerController.businessView`：返回 `creditSplits`（每项内嵌 T22 measures）；
  3. `CcrApplicationServiceImpl.createLoanItems`：**不建合同关系、不回填合同号**，`source_split_no` 随分项落库；
  4. `ApplicationSubmitServiceImpl.checkDuplicateContractApplication`：存量带 source_split_no 按**拆分项精确防重**；拆分项为空（新增/手工补录）回退「客户+担保方式」。
- **前端 `loan.vue`**：
  1. 授信信息区**移除授信协议下拉与协议要素**（授信协议编号等冗余字段去除），存量仅显示拆分细项合计；
  2. 存量展示「授信担保拆分明细」**勾选列表**（全选/清空，勾选即生成分项，措施/原利率/金额/到期日从数仓带出）；
  3. 分项卡片**去掉参考合同下拉、贷款合同 badge**，改「拆分项」badge；
  4. 校验去掉存量强制合同号；`buildPayload` 不再传合同号/plannedContractFlag，改传 `sourceSplitNo`。
- **审批 `detail.vue`**：存款审批仅显示存款录入信息（贷款区块 `isLoan` 分流已实现）；清理 `appliedCredit` 死代码区块。

### 2.5 决策点（已确认）

- ④ 防重口径：存量按 `source_split_no` 精确防重（同一拆分项已有在途调息申请即阻断）；新增回退「客户+担保方式」。
- ⑤ `plannedContractFlag`：**新增/存量统一不建合同关系**，该语义已从 `buildPayload` 移除，不再使用。

## 三、机构贡献度达成率：只统计「已结束」的承诺

### 3.1 现状核对

- 机构达成率 D19 由数仓生成 `dw_org_performance_snapshot`（org_code / stat_month / achieved_amount / expected_amount / completion_rate），**系统只读、不自行计算**。
- 分子 `achieved_amount` = 数仓当前贡献度已达成（`dw_contribution_metric` 最近批次，全量客户，**不过滤到期**）；
- 分母 `expected_amount` = 该机构**已通过审批**申请所录入的拟达成贡献度合计（`ccr_application_commitment`，已排除 `metric_code='OTHER'` 与草稿/被否，**不过滤 end_date**）；
- `completion_rate` = achieved / expected；批次=**月度**。
- 系统内补充统计 `orgPlanStats`/`customerPlanStats`(CommitmentQueryServiceImpl.java:237-260) 对机构/客户下**全部**计划 `AVG(achievement_ratio)` 求平均——**同样含未到期计划**。
- 展示入口：`/ccr/commitments/org-achievement`（CommitmentQueryServiceImpl.java:226-273）、审批详情「机构达成」卡（ApprovalController.java:1052-1067 / ApprovalServiceImpl.java:1322-1338），均读该数仓快照。

### 3.2 需求内容

**机构达成率 = 截至当前日期，已结束的贡献度完成率；截至时间未到（未到期）的不计入分子分母。**

### 3.3 数仓需修改内容

`dw_org_performance_snapshot` 加工口径（docs/09 A10、docs/04 T10）调整：

| 项 | 现状 | 修改后 |
|---|---|---|
| 分母 expected_amount | 该机构全部已通过审批申请拟达成承诺合计（不过滤到期） | **仅统计区间已结束**（end_date <= 统计截止日）的已通过申请拟达成承诺合计，仍排除 OTHER 与草稿/被否 |
| 分子 achieved_amount | 数仓当前贡献度全量（不过滤） | 与分母**同一客户/指标集合**的实际达成贡献度（口径保持 CONTRIBUTION_AMOUNT 优先） |
| 时点 | 月度快照，最新批次最新月份 | 明确与"截至当前日期"的映射（见决策点⑥） |

> 若数仓读不到业务库承诺 `end_date`，需业务系统在推送/中间表中补带"承诺完成截止日期"。

### 3.4 后端/前端需修改

- 若数仓改造后快照口径即正确，`orgAchievement`/`orgPerformance` **无需改代码**（只读数仓）；
- 系统内 `orgPlanStats`/`customerPlanStats`(L237-260) 的 `AVG(achievement_ratio)` 需加"仅已结束计划"过滤，避免计划平均达成率仍含未到期；
- 前端展示字段（approval/detail.vue:439-453、history/archive.vue:342-353）`achievedAmount/expectedAmount/completionRate` 不变。

### 3.5 待确认决策点

- ⑥ **"已结束"的判定字段**（关键）：系统存在两个"结束日期"——
  - `ccr_application_commitment.end_date`：申请时录入的**承诺完成截止日**（拟达成贡献度承诺在什么时间点内完成）；
  - `ccr_commitment_plan.end_date`：承诺跟踪周期到期（默认=审批通过日+1年，`ItemFinalizationServiceImpl.java:283-285`，**未回填 commitment.end_date**）。
  - **建议以 `ccr_application_commitment.end_date`（承诺完成截止日）为准**：若按 plan.end_date（1 年）过滤，上线早期几乎无"已结束"计划，达成率恒空。
- ⑦ 分子统计口径：按承诺结束日所在月对齐 `dw_contribution_metric` 的 `stat_end`，还是取最新批次值？建议与分母同一统计区间对齐。

## 四、审批流程节点核对与修正

### 4.1 现状核对（测试库实测，生产疑同源）

流程定义由 `StandardFlowInitializer` 启动时代码生成（`WarmFlowServiceImpl.ensureStandardFlow`，仅不存在已发布定义时创建）。当前 `flow_definition`（rate_approval，is_publish=1）节点链：

`start → BRANCH_MANAGER → DEPT_GENERAL_MANAGER → VICE_PRESIDENT → SIX_PEOPLE_GROUP → PRESIDENT → end`

**链本身基本符合需求**（09 对公三档需求 B13 支行行长必经、完整链路、PRESIDENT 上会必经行长决议），但存在以下问题：

| # | 问题 | 严重度 | 详情 |
|---|---|---|---|
| P1 | **矩阵旧两档 vs 需求三档** | **高（业务阻断）** | 代码按三档算 `LT_1000/GE_1000_LT_5000/GE_5000`（`RateMatrixRouterImpl.toAmountTier`），测试库矩阵仅旧两档 `LT_5000/GE_5000` → **<5000 万对公贷款提交路由报 `RULE_NO_MATCH`** |
| P2 | **矩阵 dept_code 字母码** | **高（越权）** | 矩阵 `dept_code` 用 `COMPANY_FINANCE/CREDIT_REVIEW/RETAIL`，需求/指派用数字 org_code（3202233912/3202233943/3202233991）→ 冻结进分项后**精确处理人匹配失效，静默回退"全行该角色可处理"**（越权不报错） |
| P3 | **flow_node.permission_flag 与真实角色码不符** | 中 | `DEPT_GENERAL_MANAGER`=dept_general_manager（真实角色=dept_gm）、`SIX_PEOPLE_GROUP`=six_people_group（真实=committee_member）。当前鉴权走 `CurrentLoginUser.NODE_ROLE` 硬编码未受影响，但按该字段推断的界面/逻辑会错 |
| P4 | **SECRETARY（贷审会秘书）不在流程定义** | 中 | ≥1000 万且申请利率 <2.6% 时必经秘书岗（`applySecretaryGate` 动态插入，`ccr_node_assignee` seed 已配处理人），但流程定义/图不可见 |
| P5 | **处理人/分管行长映射缺失** | 高（越权） | `ccr_node_assignee`=0 行（六人组/秘书岗精确处理人失效）、`ccr_dept_vp`=0 行（部门→具体分管行长映射丢失） |
| P6 | **存贷共用一个标准流程定义** | 低 | 存款/保证金实际链路 `BM→GROUP`（RouteChains.DEPOSIT_CHAIN），流程图上却含 DGM/VP/PRESIDENT |

### 4.2 需求（目标态）

- 贷款流程节点链：`start → BRANCH_MANAGER → DEPT_GENERAL_MANAGER → VICE_PRESIDENT → SIX_PEOPLE_GROUP → PRESIDENT → end`，并纳入 **SECRETARY**（≥1000 万且 <2.6% 时条件必经，否决即整单拦截）；
- 存款/保证金单独定义：`start → BRANCH_MANAGER → SIX_PEOPLE_GROUP → end`；
- 矩阵：三档 `LT_1000/GE_1000_LT_5000/GE_5000`，`dept_code` 用数字 org_code，<1000 万存量=零售金融 3202233991、新增=授信评审 3202233943（与 `db/07_rate_matrix.sql` 一致）；
- `flow_node.permission_flag` 用真实角色码（DGM→dept_gm、GROUP→committee_member）；
- 补 `ccr_node_assignee`（六人小组 6 人 + SECRETARY=计划财务部总经理）与 `ccr_dept_vp`（3 行）。

### 4.3 数仓需修改内容

**无结构改动。** 本项为系统内配置修正（矩阵/指派/流程定义），不涉及数仓推送表加工。

### 4.4 后端/前端需修改

1. **矩阵**：按 `db/07_rate_matrix.sql`（三档、数字 dept_code）重灌测试/生产库；清矩阵缓存（`ccr:cfg:matrix:effective` 版本号自动失效）；用 09 §5 的 10 个场景 `/ccr/rule/matrix-route` 回归；
