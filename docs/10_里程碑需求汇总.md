## 三、对公贷款按金额三档路由 —— 已实施(2026-08-14,已部署验证)

### 目标(含用户 2026-08-14 澄清)

对公贷款按**申请金额**分三档:

| 档位 | 金额区间 | 链路 |
|---|---|---|
| 1 | **≥5000 万(含)** | **保持不变**(现状对公链路) |
| 2 | **1000 万–5000 万(含 1000 万)** | **按原 <5000万 链路走**(现状) |
| 3 | **<1000 万** | 存量:零售金融部 → 零售金融部分管领导;新增:授信评审部 → 授信评审部分管领导;**利率区间与个人贷款一致** |

> 用户原话:"1000 万到 5000 万的贷款,还是按原来 5000 万以下的链路走;5000 万以上的也保持不变。""1000 万以下的对公贷款:存量贷款走零售金融部,然后报零售金融部的分管领导审批;新增贷款还是走授信评审部,然后再报授信评审部的分管领导审批。其利率区间跟个人贷款是一样的。"

### 最终方案(用户 2026-08-14 拍板,已落地)

- **三档链路**:三档统一走**完整链路**(与个人贷款一致)——`BRANCH_MANAGER`(必经)→`DEPT_GENERAL_MANAGER`→`VICE_PRESIDENT`→`SIX_PEOPLE_GROUP`(兜底),按利率边界链式(权限内提前终审);`<1000万` 档存量命中部门=**零售金融部(org_code 100103)**、新增命中部门=**授信评审部(org_code 100102)**,部门仅分流**节点内处理人**(部门总经理/分管行长按 dept_code 解析),链路形态不变。
- **金额定档基准**:一律按**申请/分项金额**定档(`amountBasis=APPLY_AMOUNT` 全局改为按申请金额,不再集团授信总额优先)。
- **金额档三档化**:`RateMatrixRouterImpl` 定档从"5000 单阈值"扩为 **1000/5000 双阈值三档**——`LT_1000`(<1000万)/`GE_1000_LT_5000`(1000万含-5000万)/`GE_5000`(≥5000万);`match()`/`voteConditionHit()` 同步。
- **矩阵种子**(`db/07_rate_matrix.sql`):原 `LT_5000` 37 行统一改档 `GE_1000_LT_5000`(1000万-5000万维持原 <5000万 链路不变);个人贷款段前插入 **15 行 `LT_1000` 档对公行(9801-9815)**:存量 dept=100103(GM SPREAD 3.8/20BP、VP RATE 3.8、GROUP RATE 3.8,customer_type 通配)、新增 dept=100102(BM/GM LPR+100BP、VP LPR+80BP、GROUP `<LPR+80BP`,按 1Y/3Y/5Y 分 12 行),利率边界与个人贷款一致。
- **配置界面**(`params.vue`):金额档下拉、voteCondition 构造器、voteConditionText 全部三档化;`dict.ts AMOUNT_TIER` 三档文案。

### 验证(10 场景端到端试算,`/ccr/rule/matrix-route`)

| 场景 | 结果 |
|---|---|
| 500万 4.2% | BM 终审 ✓ |
| 500万 3.6% | GROUP 上会 ✓ |
| 500万 3.9% | VP 终审 dept=100102(新增) ✓ |
| 存量 500万 3.9% | VP 终审 dept=100103(存量走零售金融部!) ✓ |
| 2000万 3.9% | BM 终审(现状不变) ✓ |
| 8000万 3.9% | GM 终审 dept=100102(现状不变) ✓ |

## 四、贷审会秘书岗 —— 已实施(2026-08-14,已部署验证)

### 描述(用户原话,2026-08-14)

> "对 1000 万以上的所有贷款,如果申请的利率在 2.6% 以下,在分管行长审批后,需要增加一个贷审会秘书岗。由贷审会秘书岗审核完毕后,再往分管行长、六人小组那边去走。"

### 最终方案(用户 2026-08-14 拍板,已落地)

- **适用范围**:1000 万以上所有贷款(含 1000万-5000万、≥5000万 两档;**不含 <1000万**);存量/新增均触发。
- **触发条件**:申请利率 **< 2.6%**(`requestedRate < 2.6`,含存量/新增)。
- **节点语义**:**否决即拦截,流程终止**——秘书岗为**审核岗**(非调价岗),仅"同意/否决";否决=整单 REJECTED,流程终止;同意则继续上送。
- **链路**:`... → VICE_PRESIDENT → SECRETARY(新插入) → SIX_PEOPLE_GROUP → ...`——秘书岗**插在分管行长之后、小组之前**;若链路无 VP(权限内提前终审),则插在链尾终审节点之前。

### 实现要点(已落地)

- **引擎条件插节点**(`RateMatrixRouterImpl.applySecretaryGate`):isLoan(业务大类 `LOAN*`)且金额 ≥1000万 且 利率 <2.6% → 在 `VICE_PRESIDENT` 后插入 `SECRETARY`(链中无 VP 则链尾节点前插入);已含 SECRETARY 不重复插。三个贷款返回点(权限内终审/岗位下限终审/小组兜底)统一包裹。
- **节点注册**:`CurrentLoginUser.NODE_ROLE` 加 `SECRETARY→secretary` 角色;`NodeAssigneeResolver` 按既有四层解析(PERSON→GROUP→DEPT→ROLE),种子 `ccr_node_assignee` `SECRETARY→ROLE secretary`(id 2091000000000000001)。
- **审批推进零改动**:提交时冻结 `routeChain`(含 SECRETARY);`RouteChains.nextNode` 沿冻结链推进;SECRETARY 非终审(`routeCode≠SECRETARY`)→ 权限内也自动 escalate;reject 整单否决天然拦截。
- **用户/角色**(`db/08_system.sql`):用户 `secretary/123456`(1017,贷审会秘书,org 1000);角色 `secretary`(2011,贷审会秘书岗,菜单 1,4,5,10,11)。
- **前端**(`dict.ts` NODE_LABELS 加 SECRETARY、`detail.vue` ROLE_NODE 加 secretary→SECRETARY + 秘书岗节点利率区只读 + 操作提示):路由预览/审批详情链路展示、审批详情节点操作按秘书岗文案渲染。

### 验证

- 10 场景试算:`[G]` 2000万 2.4% → chain=`[BRANCH_MANAGER,DEPT_GENERAL_MANAGER,VICE_PRESIDENT,SECRETARY,SIX_PEOPLE_GROUP,PRESIDENT]`(SECRETARY 正确插 VP 与 GROUP 之间)✓;`[H]` 2000万 2.8% 不插 ✓;`[I]` 500万 2.4% 不插(金额不够)✓;`[J]` 存量 2000万 2.4% 也插 ✓。
- secretary 用户登录(`/auth/login`)、待办 `/ccr/approval/tasks`、已办 `/ccr/approval/done` 均 200。

## 五、配置化能力(节点/产品新增能否"自动化/配置化")—— 调研结论 + 改造需求

### 背景(用户 2026-08-14)

> "类似于这种突然增加节点和贷款产品(或者某些产品)的场景,你帮我看一下你现在能不能做到自动化增加或者配置化。如果目前实现不了配置化,你帮我也写到需求里面,我们看看这个需求怎么去配置化。"

### 现状结论(代码实测,2026-08-14)

**1) 新增"贷款产品"——已完全配置化(界面操作,无需改代码)**

- 系统管理 → 参数管理 → **产品配置**页:产品目录(ccr_product)新增/编辑/启停/删除 + 产品审批链路(ccr_product_route)草稿→送审→**复核发布(双人复核)**→停用;支持 route_mode(CHAINED/DIRECT_VOTE)、start_node_code、mandatory_vote、president_decision、vote_condition(金额档/企业类型)。
- 配套配置均界面维护:权限矩阵(ccr_rate_matrix)、产品边界(ccr_product_rate_limit)、LPR 版本;申请页产品下拉以产品目录为权威来源(非前端硬编码)。
- 提供"模拟路由"试算,可即时验证新产品的审批链路。

**2) 新增"审批节点"(如贷审会秘书岗)——半配置化,核心编排仍硬编码,必须改代码**

- **已配置化**:节点→处理人指派(流程与审批人员配置 → 节点指派,ccr_node_assignee,按人/角色/部门/组 + 代理人/有效期)、节点利率边界(ccr_node_permission)、矩阵行(start_node_code 可引用新节点编码)。
- **数据可配但无维护界面**:部门→分管行长映射(`ccr_dept_vp`,§D16a 一人可分管多部门,运行库 100101/100103→1022、100102→1023)当前**无任何界面与后端 CRUD,只能手工 SQL 维护**;新增/调整部门分管行长无审计、无生效期管理。**新增部门分管行长必须改库,是配置化缺口之一。**
- **必须改代码的硬编码点(实测定位)**:
  - 后端 `CurrentLoginUser.NODE_ROLE`:节点→系统角色 **硬编码 Map**(新增节点不注册会抛"未知审批节点");
  - 后端 `RouteChains`:贷款链/存款链**固定数组**;`RateMatrixRouterImpl` 链首 BRANCH_MANAGER / 兜底 SIX_PEOPLE_GROUP 常量、金额定档 5000 单阈值;
  - 后端 `VoteServiceImpl`:表决节点 SIX_PEOPLE_GROUP、行长决策节点 PRESIDENT 的触发/状态机**按编码硬编码**;`ApprovalServiceImpl` 存款双轨、支行范围过滤等节点分支;
  - 前端 `dict.ts NODE_LABELS` 节点名称、detail.vue 角色→节点映射与节点特殊逻辑(委员投票/行长决策区)。
- **关键能力缺口**:现有路由模型只能表达"**终审岗位**",**无法表达"在链路中按条件插入一个必经节点"**——需求四(贷审会秘书岗)正是此类(利率<2.6% 且 1000万以上时在分管行长后插入)。**必须新增引擎逻辑,纯配置化做不了。**

**3) Warm-Flow 流程定义(flow_definition)仅记录审批轨迹,不驱动流转**(flow.vue 页签内已注明),流程可视化编排目前未接入引擎。

**4) 机构表(ccr_sys_dept)——已完全界面化,非缺口**

- 前端 `system/dept.vue`(系统管理→机构管理)、后端 `SysDeptController`(list/tree/create/update/updateStatus/delete)提供完整维护能力:机构**新增/编辑/启停/删除均前台操作**,无需手工 SQL。
- 机构编码 `org_code` **新增后禁改**(唯一、被数据权限前缀匹配/路由矩阵/节点指派引用),是刻意安全设计,非配置化缺口。(2026-08-14 已删除 `dept_code` 字母列,编码统一 org_code)
- 种子 `09_system_dept.sql` 仅初始化兜底;日常维护走界面。

**5) 数仓外部数据表——开发期 mock 模拟推送,非配置项**

- `db/02_external_data.sql` 是**建表契约**(约定数仓推送字段,如基本户账户 `basic_account_no`);`db/10_mock_external.sql` 等是开发期**模拟数仓推送的数据**——ALTER/INSERT 仅发生在开发环境,用于无真实数仓时的联调。
- 生产环境这些落地表(caps_*/dw_*)由数仓每日直接推送落地,**不存在人工维护,也不存在"配置界面"需求**。
- 客户数据字段(基本户账户等)属**数据而非系统配置**:前台展示/填报即界面化(需求一已实施),无需另行提供配置界面。

### 需求 E:节点/产品新增"全配置化"改造(建议,待确认)

把上述硬编码点数据化,使"新增审批节点"也能界面配置、不改代码:

1. **节点字典表化**:新增节点表(如 ccr_node:节点编码/名称/关联角色/节点类型),替代 `CurrentLoginUser.NODE_ROLE` 与前端 `NODE_LABELS` 硬编码,节点名称从数据库读取。
2. **节点类型化**:节点按类型通用处理(APPROVE 普通审批 / VOTE 表决 / DECISION 行长决策),审批/表决引擎按**节点类型**分支,替代按节点编码分支。
3. **链路编排配置化**:新增"链路与插节点"配置(支持"在节点 X 后、满足条件 Y 时插入节点 Z"的条件分支),替代 `RouteChains` 固定数组与矩阵仅定终审岗位的能力边界。
4. **金额定档阈值配置化**:金额档区间(1000/5000 等)读配置而非硬编码(需求三的三档化亦可顺带收益)。
5. **同步改造**:审批详情/路由预览/待办过滤按节点类型与数据库名称渲染。
6. **部门分管行长映射界面化**:为 `ccr_dept_vp`(部门→分管行长,一人可分管多部门)提供维护界面与生效期管理,与节点指派同入口统一维护,替代手工 SQL;新增部门、换分管行长、调整分管范围全部界面化、留痕。

> 注:该项为引擎级改造,范围较大,建议作为独立迭代;需求三(三档路由)、需求四(贷审会秘书岗)落地时,新增节点仍按"改代码 + 矩阵/指派配置"方式实施。

## 六、个人经营贷新增部门归属修正 —— 已实施(运行库+种子,已生效)

### 业务口径(用户 2026-08-14)

个人经营性贷款(`LOAN_PERSONAL`)**存量**走零售金融部;**新增**走授信评审部(部门总经理 + 分管行长均按授信评审部),与对公"存量=公司金融部 / 新增=授信评审部"规律一致。**利率边界不变**(新增 LPR+100BP/80BP)。

### 改动

- **运行库** `ccr_rate_matrix`:个人经营贷新增 1Y/3Y/5Y 的 GM/VP 行 `dept_code`(机构org_code)100103→100102、remark 同步(共 6 行:9755/9756/9759/9760/9763/9764);存量 EXISTING 行保持 100103(零售金融部)不动。
- **种子文件** `db/07_rate_matrix.sql`:同步上述 6 行 + **全文件部门编码统一 org_code 数字码**(100101 公司金融部/100102 授信评审部/100103 零售金融部,2026-08-14 起删除字母码),与运行库及节点指派 `100101:dept_gm` 等一致。
- 指派(`ccr_node_assignee` 已有 `100102:dept_gm`)、分管行长映射(`ccr_dept_vp` 已有 `100102→1023`)无需改动。

### 修正后链路

| 个人经营贷 | 部门总经理 | 分管行长 |
|---|---|---|
| 存量 | 零售金融部总经理(1021 周,org_code 100103) | 吴分管行长(1022,兼管公司金融部100101+零售金融部100103) |
| 新增 | 授信评审部总经理(1020 孙,org_code 100102) | 郑分管行长(1023) |

> 生效说明:矩阵读取走 Redis 缓存(`ccr:cfg:matrix:effective`),本次缓存未命中时自动回源,修正立即生效;可在「参数管理 → 模拟路由」以个人经营贷新增单试算验证链路与部门归属。
