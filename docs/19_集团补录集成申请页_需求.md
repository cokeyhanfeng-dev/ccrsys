# 需求：集团补录集成至利率申请页

> 提出日期：2026-08-19
> 状态：**已定稿**（决策点 A–J 全部拍板，按 §二/§四 实施）
> 范围：利率贷款申请（`loan.vue` 第一步集团区块）+ 提交链路 + 后台数据表

## 一、背景与问题

集团客户申请利率时，第一步需要输入集团号查询数仓集团快照（集团主数据、批复授信、有效成员列表），勾选成员录入申请金额与申请利率。

现状痛点：

1. **数仓未统计的集团录不进去**。数仓没有的集团，`suggest` 联想查不到、提交校验 `GROUP_MEMBER_VALID` / `checkGroupConstraints` 会以「集团主数据快照缺失 / 集团授信快照缺失 / 成员不在集团有效成员快照中」**BLOCK**。
2. **上一版方案入口不合适**。已实现「系统管理 → 集团管理」独立页（`/system/group`），但实际使用人是**客户经理在提交贷款申请时补录**，不是管理员单独维护——独立系统/页面与真实使用场景不符。

## 二、需求目标

把集团补录能力**内嵌到利率申请页**，客户经理在提交申请时直接完成补录，规则对齐现有「客户手工确权」补录逻辑；补录数据落后台表，**跨申请带出**。

核心规则（用户提出，与客户补录一致）：

1. **没有编码（新增）的，不需要补录**。
2. **只有存量的，才需要补录**。
3. **集团下属的企业也能补录**，补录后从后台表关联带出。
4. **新过来的集团授信等为空**，按新集团方式对待（不做存量校验）。
5. **不做单独系统**，功能在贷款申请流程内。

## 三、现有实现盘点（复用 vs 需调整）

| 模块 | 现状 | 处置 |
| --- | --- | --- |
| `ccr_group` / `ccr_group_member` 表 | 手工集团主数据/成员，已建（增量 SQL 002） | **保留**，作为补录数据载体 |
| `ManualGroupService`（CRUD+查重） | 已实现 | 保留，**能力下沉申请页提交链路**（独立维护 Controller 删除） |
| `GroupQueryController`（suggest/group/members） | 已合并「数仓+手工」双来源（数仓优先、手工兜底） | 保留 |
| 提交链路（`qualityPrecheck`/`checkGroupConstraints`/`collectGroupChain`） | 已兼容手工集团（手工集团回退补录批复总额度） | **按定稿调整**：申请额度勾稽 + 新增豁免 + 提交时落表 |
| 「系统管理 → 集团管理」独立页 `/system/group` | 已实现（admin/customer_manager） | **独立页面删除**（详见 §4.8） |
| 客户补录先例（`customer_info_json` 人工确权） | 数仓拉不出 → 申请页手工填写 → BLOCK 降 WARN | 集团补录交互对齐此模式 |

## 四、核心规则细化

### 4.0 集团业务本质与审批链路（已拍板）

**集团 = 对公整体 + 成员维度**：

- 申请按**整个集团**，视同一个对公企业；流程与对公客户一致：**先查询集团的授信与融资情况，再进行利率申请**。
- 与普通对公的**唯一区别**：名下有多个成员，需**带出成员的信息与额度**参与申请。
- **利率申请按成员**：每个成员行内 = **申请金额 + 申请利率/期限**，成员是利率申请的最小单元；集团整体定档仍用成员申请金额合计，审批链路不变。

**审批链路按对公**（用户拍板）：

- 路由定档口径与对公客户完全一致：业务大类 `LOAN_PUBLIC`（对公）+ 申请金额定档（矩阵路由 `amountBasis=APPLY_AMOUNT`，以成员申请金额合计为金额档基准，现状已统一，确认保留）。
- 存量集团申请时**必须查询展示数仓授信/融资**（批复授信、可用额度），与对公一致；数仓无授信快照或新增集团时，就地补录**申请额度**（本次新增授信，见 §4.5）。
- 集团专属校验向对公客户看齐，唯一多出的部分是**成员维度**（成员在团、成员申请金额合计勾稽）。

### 4.1 「新增」vs「存量」判定与数据优先级（已拍板：数据以数仓为准）

以**数仓是否收录该集团编号（`group_no`）**为判定基准，且**数据以数仓为准**：

- **数仓收录 `group_no`（存量）**：一律**以数仓数据为准**（主数据、授信、成员均以数仓快照为准）。若授信或成员缺失，就地补录（缺什么补什么）。
- **数仓未收录 `group_no`（新增）**：以**补录数据为准**。集团基本信息（对公客户全套）就地补录，成员正常录入，申请额度必填；提交时**豁免集团主数据/授信/成员快照校验**，按对公新增客户对待。

三种状态：

| 状态 | 判定 | 表现 |
| --- | --- | --- |
| 存量 | 数仓有 group_no | 数仓数据为准；授信/成员缺失就地补录（缺什么补什么） |
| 全新新增 | 数仓无 + 手工无 | 集团基本信息（对公全套）+ 成员 + 申请额度就地录入，提交豁免存量校验 |
| 已登记 | 数仓无 + 手工有 | 带出手工主数据**免补录**，只录申请额度 + 成员申请金额/利率 |

**撞数仓处理**：新增集团 `group_no` 若在提交时已被数仓收录，**自动按存量处理**（数仓数据优先展示、做存量校验），不拒绝、不覆盖数仓；手工补录数据仅作冗余保留（`suggest` 合并已按「数仓先 put、手工 putIfAbsent」实现，数仓优先）。

### 4.2 申请页补录入口（内嵌，不跳独立页）

在 `loan.vue` 第一步集团区块，`queryGroup` 后根据判定结果出现不同状态：

| 场景 | 申请页表现 |
| --- | --- |
| 数仓命中（完整） | 现有逻辑：集团基本信息+授信融资+成员带出，勾选成员录申请金额+申请利率 |
| 数仓命中但授信缺失 | 授信区显示「数仓无授信快照」，就地补录**申请额度**（必填） |
| 数仓命中但成员缺失 | 成员列表就地补录（成员对公全套+成员要素），补录项标记「手工」 |
| 数仓未收录（新增集团） | 集团基本信息就地补录（对公客户全套），成员正常录入，申请额度必填；**不出现存量授信校验**，按新集团对待 |

交互对齐客户补录：手工补录的数据随申请提交，`submit-check` 中对应项降为 **WARN（提示已按人工补录提交，请确认）**，不再 BLOCK。

### 4.3 集团补录字段（已拍板：对公客户基本信息全套）

集团补录信息与**对公客户申请信息要求一致**，集团基本情况信息全部拉出/补录：

| 类别 | 字段 | 说明 |
| --- | --- | --- |
| 对公客户基本信息（全套） | `group_no` | 集团编号（对应对公客户号，新增/存量均需） |
| | `group_name` | 集团名称（对应对公客户名称，补录必填） |
| | `ucr_code` | 统一社会信用代码 |
| | `five_level_class` | 五级分类 |
| | `credit_level` | 信用等级 |
| | `industry` | 行业 |
| | `registered_capital` | 注册资本 |
| | `open_org` | 开户机构 |
| | `open_date` | 开户日期 |
| | `basic_account` | 基本账户 |
| 集团特有 | `group_type` | 集团类型（默认 INDUSTRY_GROUP） |
| | `manager_org_id` | 管理机构 |
| | `group_status` | 集团状态（默认 NORMAL） |
| | `currency` | 币种（默认 CNY） |

### 4.4 成员补录字段（已拍板：对公全套 + 成员要素，利率按成员）

成员补录信息与**对公客户申请信息要求一致**，分为企业要素、成员要素与利率内容三部分：

| 类别 | 字段 | 说明 |
| --- | --- | --- |
| 企业要素（对公客户全套） | `member_customer_no` | 成员客户号（必填） |
| | `member_name` | 成员名称（必填，数仓无反查时补录） |
| | `ucr_code` | 统一社会信用代码 |
| | `five_level_class` | 五级分类 |
| | `credit_level` | 信用等级 |
| | `industry` | 行业 |
| | `registered_capital` | 注册资本 |
| | `open_org` | 开户机构 |
| | `open_date` | 开户日期 |
| | `basic_account` | 基本账户 |
| 成员要素 | `member_role` | 成员角色 CORE / GENERAL |
| | `control_relation` | 控制关系（可选） |
| | `relation_start` / `relation_end` | 关系起止（空=在团） |
| | `apply_amount` / `currency` | 申请金额、币种 |
| 利率内容（按成员） | `apply_rate` / `apply_term` | 申请利率 / 期限（每成员一份） |

> **不含授信要素**：成员授信不做补录——授信是集团级的，在集团申请（申请额度）时补录。

### 4.5 申请额度（已拍板）

- **术语**：补录额度字段 = **「申请额度」**（本次申请的新增授信额度），区别于数仓「批复总额度」。
- **必填**：所有集团申请必录（新增/存量一致），存量集团数仓有授信时数仓批复仅作**展示参考**，不参与勾稽。
- **存储**：随申请存申请上下文 `group_info_json`，**每次申请一条、多条并存**（历史各笔不合并、不覆盖、不参与本次勾稽）。
- **勾稽基准**：成员申请金额合计 ≤ **本次申请额度**。
- **不落 `ccr_group` 主表**。

### 4.6 数据落表与带出（已拍板）

- 落表边界：
  - **新增集团** → 落 `ccr_group` + `ccr_group_member`（集团登记册 + 手工成员）。
  - **存量集团** → **不落 `ccr_group` 主表**，补录的成员落 `ccr_group_member`。
  - **申请额度** → 不落主表，随申请上下文 `group_info_json` 保存。
- **落表时机 = 提交时**：草稿阶段补录数据暂存申请上下文（`ccr_application` 新增 JSON 字段 `group_info_json`，参照 `customer_info_json`），提交时解析落 `ccr_group`/`ccr_group_member`，随快照采集一并完成；不产生草稿孤儿数据。
- **重复录入最新覆盖**：按 `group_no`（集团）/ `group_no + member_customer_no`（成员）幂等，最新录入覆盖旧数据。
- **带出**：`suggest`/`group`/`members` 已合并「数仓+手工」，落表后其他申请可联想带出；**数仓优先、手工兜底**。

### 4.7 提交链路调整

| 校验 | 现状 | 调整 |
| --- | --- | --- |
| `SUBJECT_EXISTS`（集团主数据） | 数仓/手工都无 → BLOCK | **数仓无 = 新增集团豁免**（数仓无即放行）；数仓有 = 存量需在团（数仓优先） |
| `GROUP_CREDIT_EXISTS`（授信/批复总额度） | 手工集团缺补录值 → BLOCK | **申请额度必填**（所有集团申请），存 `group_info_json` 多条并存；数仓批复仅展示参考，不参与勾稽 |
| `GROUP_MEMBER_VALID`（成员在团） | 双来源任一侧在团放行 | 新增集团成员手工录入即放行；存量成员缺则补录后放行 |
| 额度勾稽（成员申请合计 ≤ 批复总额度） | 数仓或手工批复总额度 | 勾稽 = **成员申请金额合计 ≤ 本次申请额度**（所有集团申请统一） |

### 4.8 独立管理页与权限（已拍板）

- **「系统管理 → 集团管理」独立页面删除**（前端 `group.vue`/路由/菜单、后端独立维护 `ManualGroupController` 一并移除），不做单独系统。
- **`ManualGroupService` 保留**，能力下沉为申请页提交链路内部使用（新增/存量判定、提交时落表、查重）。
- 客户经理补录全部在申请页内完成；后台表数据仅通过申请提交链路写入，无独立维护界面。

## 七、验证（定稿后）

1. **新增集团**：数仓无 `GROUP9001` → 申请页就地补录集团对公全套 + 成员 + 申请额度 → 提交预检**无 BLOCK**（授信空按新集团）→ 提交成功，落 `ccr_group`+`ccr_group_member`。
2. **存量集团补申请额度**：数仓有集团但授信缺失 → 申请页就地补录申请额度 → 提交通过、勾稽生效。
3. **存量集团补成员**：数仓有集团但成员缺失 → 申请页就地补录成员 → 提交通过，快照质量 `GROUP_MEMBER_VALID` PASS。
4. **利率按成员**：每成员带申请金额+申请利率提交 → 定档用成员金额合计。
5. **跨申请带出**：补录后另一申请输入集团号可联想带出补录的集团/成员。
6. **数据以数仓为准**：手工 `GROUP9001` 被数仓收录后 → 以数仓数据展示，手工数据不覆盖数仓。
7. **回归**：数仓完整集团 GROUP001 原流程不变；单测全绿。
