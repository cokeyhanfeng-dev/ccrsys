# 需求：集团补录集成至利率申请页

> 提出日期：2026-08-19
> 状态：**已定稿**（决策点 A/B/C/D 全部拍板，按 §二/§四 实施）
> 范围：利率贷款申请（`loan.vue` 第一步集团区块）+ 提交链路 + 后台数据表

## 一、背景与问题

集团客户申请利率时，第一步需要输入集团号查询数仓集团快照（集团主数据、批复授信、有效成员列表），勾选成员录入申请金额。

现状痛点：

1. **数仓未统计的集团录不进去**。数仓没有的集团，`suggest` 联想查不到、提交校验 `GROUP_MEMBER_VALID` / `checkGroupConstraints` 会以「集团主数据快照缺失 / 集团授信快照缺失 / 成员不在集团有效成员快照中」**BLOCK**。
2. **上一版方案入口不合适**。已实现「系统管理 → 集团管理」独立页（`/system/group`），但实际使用人是**客户经理在提交贷款申请时补录**，不是管理员单独维护——独立系统/页面与真实使用场景不符。

## 二、需求目标

把集团补录能力**内嵌到利率申请页**，客户经理在提交申请时直接完成补录，规则对齐现有「客户手工确权」补录逻辑；补录数据落后台表，**跨申请带出**。

核心规则（用户提出，与客户补录一致）：

1. **没有编码（新增）的，不需要补录**。
2. **只有存量的，才需要补录**。
3. **集团下属的企业也能补录**，补录后从后台表关联带出。
4. **新过来的集团授信等为空**，按新集团方式对待（不做存量校验）。
5. **不做单独系统**，功能在贷款申请流程内。

## 三、现有实现盘点（复用 vs 需调整）

| 模块 | 现状 | 处置 |
| --- | --- | --- |
| `ccr_group` / `ccr_group_member` 表 | 手工集团主数据/成员，已建（增量 SQL 002） | **保留**，作为补录数据载体 |
| `ManualGroupService`（CRUD+查重） | 已实现 | 保留，接口权限已开放客户经理 |
| `GroupQueryController`（suggest/group/members） | 已合并「数仓+手工」双来源 | 保留 |
| 提交链路（`qualityPrecheck`/`checkGroupConstraints`/`collectGroupChain`） | 已兼容手工集团（手工集团回退补录批复总额度） | **需按「新增/存量」规则调整** |
| 「系统管理 → 集团管理」独立页 `/system/group` | 已实现（admin） | **移除客户经理入口**（详见 §5.7，待拍板） |
| 客户补录先例（`customer_info_json` 人工确权） | 数仓拉不出 → 申请页手工填写 → BLOCK 降 WARN | 集团补录交互对齐此模式 |

## 四、核心规则细化

### 4.0 审批链路规则（已拍板：按对公客户）

**集团的审批链路按照对公客户的来**（用户拍板）：

- 路由定档口径与对公客户完全一致：业务大类 `LOAN_PUBLIC`（对公）+ 客户类型按成员企业性质（SOE/NON_SOE）+ **按申请/分项金额定档**（矩阵路由 `amountBasis=APPLY_AMOUNT`，现状已统一，确认保留，不再以集团授信总额作金额档基准）。
- 集团专属校验（`checkGroupConstraints` 的批复总额度必填 / 成员在团 / 额度勾稽）**向对公客户看齐**：
  - **新增集团（数仓无）**：豁免批复总额度强制与额度勾稽（对公新增无授信直接放行），路由按申请金额定档。
  - **存量集团**：数仓有授信时仍可按原数仓口径勾稽；授信缺失需补录时补录值为可选勾稽基准（自愿，不强制 BLOCK）。

### 4.1 「新增」vs「存量」判定

以**数仓是否收录该集团编号（`group_no`）**为判定基准：

- **新增（无编码/数仓无此集团）**：数仓 `findGroup` 查不到 → 集团属新增 → **不需要补录**。成员企业、申请金额、授信在申请页正常录入即可，提交时**豁免集团主数据/授信/成员快照校验**。
- **存量（有编码/数仓有此集团）**：数仓有此集团 → 属存量 → 若**授信或成员缺失**则需补录（缺什么补什么）。

> 注：此处「编码」指数仓集团主数据是否已收录。若业务上「新集团」也有内部编号（客户经理自编），判定基准不变——数仓无记录即按新增。

### 4.2 申请页补录入口（内嵌，不跳独立页）

在 `loan.vue` 第一步集团区块，`queryGroup` 后根据判定结果出现不同状态：

| 场景 | 申请页表现 |
| --- | --- |
| 数仓命中（完整） | 现有逻辑：集团信息+授信+成员带出，勾选录金额 |
| 数仓命中但授信缺失 | 授信区显示「数仓无授信快照」，就地补录批复总额度（必填） |
| 数仓命中但成员缺失 | 成员列表就地补录（成员客户号+名称+角色+关系起止），补录项标记「手工」 |
| 数仓未收录（新增集团） | 集团信息就地录入（集团号+名称+状态），成员正常录入；**不出现授信补录**，按新集团对待 |

交互对齐客户补录：手工补录的数据随申请提交，`submit-check` 中对应项降为 **WARN（提示已按人工补录提交，请确认）**，不再 BLOCK。

### 4.3 集团补录字段

| 字段 | 说明 |
| --- | --- |
| `group_no` | 集团编号（新增/存量均需） |
| `group_name` | 集团名称（补录必填） |
| `group_type` | 集团类型（默认 INDUSTRY_GROUP） |
| `approved_total_amount` | 批复总额度（万元）——**仅存量集团授信缺失时补录必填**；新增集团不需要（授信空为正常） |
| `manager_org_id` / `currency` / 备注 | 可选 |

### 4.4 成员补录字段

| 字段 | 说明 |
| --- | --- |
| `member_customer_no` | 成员客户号（必填） |
| `member_name` | 补录公司名（必填，因数仓无反查） |
| `member_role` | CORE / GENERAL |
| `control_relation` | 控制关系（可选） |
| `relation_start` / `relation_end` | 关系起止（空=在团） |

### 4.5 数据落表与带出（已拍板）

- 补录的集团/成员统一落 **`ccr_group` / `ccr_group_member`**（含新增集团/成员，跨申请复用）。
- **落表时机 = 提交时**：草稿阶段补录数据暂存申请上下文（`ccr_application` 新增 JSON 字段，参照 `customer_info_json`），提交时解析落 `ccr_group`/`ccr_group_member`，随快照采集一并完成；不产生草稿孤儿数据。
- 带出：`suggest`/`group`/`members` 已合并「数仓+手工」，落表后其他申请可联想带出。
- 落表幂等：同 `group_no` 已存在（数仓或手工）则复用/更新，不重复建。

### 4.6 提交链路调整

| 校验 | 现状 | 调整 |
| --- | --- | --- |
| `SUBJECT_EXISTS`（集团主数据） | 数仓/手工都无 → BLOCK | **新增集团豁免**（数仓无即放行）；存量需在团 |
| `GROUP_CREDIT_EXISTS`（授信/批复总额度） | 手工集团缺补录值 → BLOCK | **新增集团豁免**（按对公客户，无授信放行）；存量缺失可补录（自愿，不强制 BLOCK） |
| `GROUP_MEMBER_VALID`（成员在团） | 双来源任一侧在团放行 | 新增集团成员为手工录入即放行；存量成员缺则补录后放行 |
| 额度勾稽（成员申请合计 ≤ 批复总额度） | 数仓或手工批复总额度 | **存量集团**按数仓授信勾稽；**新增集团豁免**（等同对公新增，按申请金额定档） |

### 4.7 独立管理页与权限（已拍板）

- **「系统管理 → 集团管理」独立页面删除**（前端 `group.vue`/路由/菜单、后端独立维护 Controller 一并移除），不做单独系统。
- 客户经理补录全部在申请页内完成；后台表数据仅通过申请提交链路写入，无独立维护界面。

## 五、影响范围

- **前端**：
  - 删除独立页 `group.vue`、路由 `/system/group`、`layout/index.vue` 菜单项「集团管理」。
  - `loan.vue` 集团区块新增补录交互（新增集团就地录入 / 存量授信缺失就地补录批复总额度 / 存量成员缺失就地补录成员），补录数据写入申请上下文随提交提交。
  - `ccr_application` 新增集团补录 JSON 字段（草稿暂存，参照 `customer_info_json`）。
- **后端**：
  - 删除 `ManualGroupController` 独立维护接口；`SaTokenConfig` 移除 `/system/manual-group/**` 豁免。
  - 提交链路：新增/存量判定（数仓无集团=新增，豁免批复总额度/额度勾稽，按对公定档）；存量补录可选勾稽。
  - 提交时解析申请上下文补录数据落 `ccr_group`/`ccr_group_member`（幂等，group_no 存在则复用），随快照采集完成。
  - `GroupQueryController` 合并「数仓+手工」查询保留（补录后带出）。
- **数据库**：`ccr_group`/`ccr_group_member` 表不变（已有增量 SQL 002）；`ccr_application` 新增补录 JSON 字段（增量 SQL）。
- **测试**：单测补充新增集团豁免/存量补录/提交落表用例；端到端按 §七 验证。

## 七、验证（定稿后）

1. **新增集团**：数仓无 `GROUP9001` → 申请页直接录入集团+成员+金额 → 提交预检**无 BLOCK**（授信空按新集团）→ 提交成功。
2. **存量集团补授信**：数仓有集团但授信缺失 → 申请页就地补录批复总额度 → 提交通过、额度勾稽生效。
3. **存量集团补成员**：数仓有集团但成员缺失 → 申请页就地补录成员 → 提交通过，快照质量 `GROUP_MEMBER_VALID` PASS。
4. **跨申请带出**：补录后另一申请输入集团号可联想带出补录的成员。
5. **回归**：数仓完整集团 GROUP001 原流程不变；单测全绿。
