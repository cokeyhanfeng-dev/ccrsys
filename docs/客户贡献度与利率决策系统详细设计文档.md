## 1. 总体说明

### 1.1 文档目标

本设计将已确认的业务需求收敛为可实施的开发设计，解决以下问题：

1. 客户主体统一支持 **个人、企业单户、集团客户** 三类；集团客户拥有统一综合授信总额度，并将额度拆分给多个成员客户；个人/企业单户直接以本客户作为申请与审批主体。
2. 每个成员/客户可拥有多个**用信或担保分项**，贷款审批原子单位为**担保类型分项**（同一申请下多担保类型各自独立路由、独立校验、独立计票），关联现有合同/拟签合同；存款审批原子单位为**账户级定价分项**。
3. 贷款利率审批按 LPR±BP 参数化权限矩阵自动路由；决议作为合同/补充协议的定价依据，借据只用于执行结果核验。
4. 客户申请由客户经理在 PC 端发起，**支行行长为强制必经节点**（所有产品/所有审批链路，B13）；普通审批节点可在权限范围内调整利率；六人小组和总行行长只作决策、不修改利率。
5. 六人匿名表决后台计票，委员之间不可见身份、票型和实时结果；**≥4 票赞成通过**，逐担保类型独立计票。
6. 审批结束后生成**承诺跟踪计划**，通过定时任务读取数仓最新数据持续校验；校验周期、阈值、提醒对象、提醒渠道、升级路径全部配置化、版本化。
7. 外部数据采用"稳定核心字段 + 扩展属性 + 纵表指标 + 数据集版本"相结合模型，业务数据**统一由内部数据仓库加工提供**，本系统消费做不可变快照绑定。

### 1.2 术语与业务口径（已锁定）

| 编号 | 已锁定口径 |
|---|---|
| B01 | 客户经理只在 PC 端新建、编辑、提交和关联重提申请；移动端只承载审批。 |
| B02 | 客户主体包括个人、企业单户和集团客户；个人、企业单户直接以本客户作为申请与审批主体，集团客户按集团总额度拆分到成员。 |
| B03 | 成员额度下可以有多个用信或担保分项，每个分项可对应多份贷款合同，每份合同可对应多笔借据。 |
| B04 | 担保组合可以作用于合同或合同下借据；一笔借据可关联多个担保措施，担保措施也可覆盖多笔借据。 |
| B05 | **贷款审批原子单位为担保类型定价分项**（现有合同或拟签合同）；**存款审批原子单位为账户级定价分项**（现有账户或拟开户方案）；不得按单笔借据拆分审批。 |
| B06 | 普通审批节点只有"通过、否决"；不存在审批后的原单退回修改（退回走重提，见 B14）。 |
| B07 | 普通审批节点可调整利率，但不得突破本人权限边界和全行业务硬边界。 |
| B08 | 六人小组只对申请利率投"通过、否决"，不修改利率。 |
| B09 | 六人全部完成后计票；赞成票不少于 4 票为通过。 |
| B10 | 委员看不到其他成员身份、票型、处理状态和汇总结果；汇总仅向总行行长及授权审计人员展示。 |
| B11 | 凡进入六人小组且表决通过的定价分项，必须经总行行长最终决策（上会必经行长）。 |
| B12 | 总行行长按定价分项选择"同意利率"或"一票否决"，不能修改利率。 |
| B13 | 客户经理提交申请后**必须经过支行行长**（所有产品/所有审批链路，含 DIRECT_VOTE 直接上会），不能直接进入六人小组。 |
| B14 | 否决后的原申请或原分项保持终态；重新发起创建新申请并关联原申请，已批准分项沿用原决议（D18b）。 |
| B15 | 审批依据使用提交时冻结的数据快照；承诺跟踪使用审批后数仓最新成功批次。 |
| B16 | 集团贡献度与成员贡献度分层展示，并防止成员、关联人重复归集。 |
| B17 | 承诺跟踪周期、阈值、提醒人、渠道、升级规则全部配置化。 |
| B18 | 集团金额档次默认按集团综合授信批复总额度判断，避免通过成员拆分规避权限层级。 |
| B19 | 移动审批 App 发布在行内内部工作平台，不依赖企业微信；身份、机构和岗位由内部工作平台统一认证与映射。 |
| B20 | 审批决议不是贷款合同。决议是内部定价审批结论和合同/补充协议执行依据；一份贷款合同可对应多笔借据，借据利率应继承并校验合同最终执行利率。 |

**关键术语：**

- **当前贡献度**：数据仓库取数，反映客户现有综合贡献，供审批人参考，同时作为"拟达成贡献度"达成跟踪的**实际达成值**（分子）。含综合总额与明细，本系统对明细加总并与总额勾稽。
- **拟达成贡献度（=承诺贡献）**：客户经理申请时录入的预期贡献，作为**承诺基线**（分母），随申请存档、审批期间不变；不做勾稽校验、不设时效限制。
- **定价分项**：审批原子单位，按担保类型/产品/期限等维度生成；绑定实际利率执行载体（贷款合同或存款账户）。
- **决议**：内部定价审批结论，不是合同；作为合同/补充协议执行依据。
- **快照**：申请提交时冻结的数仓数据，审批/历史审批只读已绑定快照。

## 2. 业务范围与系统边界

### 2.1 本系统负责

1. 个人、企业单户、集团及其成员、授信、用信分项、合同、借据和担保资料的申请视图。
2. 客户经理利率申请及拟达成贡献度（承诺）录入。
3. 数据质量校验、快照冻结和流程路由预览。
4. 普通节点审批调价、六人匿名表决、行长最终决策。
5. 决议形成、历史审批、审计轨迹和数据导出。
6. 承诺计划生成、定时校验、预警、月报和历史履约查询。
7. LPR、权限矩阵、产品边界、跟踪策略和提醒规则配置。

### 2.2 本系统不负责

1. 集团综合授信批复、成员额度调剂和授信额度占用核算。
2. CIF、信贷核心、征信和贡献度折算模型的源系统处理。
3. 直接修改数仓权威数据。
4. 在移动端录入客户、融资合同、担保、借据、附件和贡献承诺。
5. 使用利率审批流程替代授信审批流程。

### 2.3 端侧边界（决议 D10）

| 业务能力 | PC 端 | 移动端 |
|---|---|---|
| 客户经理新建/重新发起申请 | 保留 | 移除 |
| 客户/关联人/融资/证明材料录入 | 保留 | 移除 |
| 拟达成贡献度（承诺）录入与跟踪 | PC 客户经理端保留 | 移除 |
| 待办审批、节点调价 | 保留 | 保留 |
| 六人匿名表决 | 保留 | 保留 |
| 行长同意/一票否决 | 保留 | 保留 |
| 历史审批 | 保留 | 保留 |

> 移动端最终只保留：**审批工作台、待办列表、审批详情、历史审批、消息、我的**。移动端不暴露新建申请、融资录入、附件上传、数据中心数据刷新等接口。

### 2.4 数据方向

```
CIF、信贷核心、征信及贡献度平台  →  内部数据仓库
内部数据仓库  →  数仓落地数据区（caps_*/dw_*_snapshot）
数仓落地数据区  →  利率审批系统业务库落地表（直接落表，按 §10.2⑥ 表结构）
利率审批系统业务库落地表  →  申请不可变快照（ccr_snapshot_*）
申请不可变快照  →  PC 与移动审批
PC 与移动审批  →  审批决议与承诺计划（ccr_resolution/ccr_commitment_*）
承诺结果回传或机构达成加工区  →  内部数据仓库
```

> **数据接入方式（业务方确认）**：**基本数据（客户基本信息、本行/他行融资、担保、贡献度指标、征信、机构达成、集团授信等）由内部数据仓库按本系统要求的数据表结构（§10.2⑥ 落地表）加工完成后直接推送到业务库对应落地表**；本系统**直接读表访问**，**不通过接口访问数据仓库/外部系统**。数仓侧负责按约定表结构与批次字段（`data_dt`/`etl_md5`/`batch_no`）落库，系统侧只读落地表做展示、勾稽与快照冻结（§9.1/§9.4/§9.5）。

### 3.4 工作流选型（Warm-Flow）

1. 新建 `ccr-workflow` 模块，引入兼容 Spring Boot 3 / JDK 17 的 Warm-Flow 版本（经 POC 验证后锁定）。
2. 工作流业务接口通过公共 API 层解耦，业务模块不直接操作引擎内部表（`flow_*`）。
3. 流程定义只表达节点、候选人和流转，**不承载**利率计算、计票和贡献度算法。
4. 业务记录使用**定价分项编号**作为 `businessId`；流程状态通过事件监听回写业务分项状态。
5. 流程发起、消息通知、对外回传通过 **Outbox 事件**可靠异步执行。

### 3.5 事务边界与 Outbox

1. 申请主单、分项、承诺、快照包和流程发起指令先在**本地事务**中提交。
2. 流程发起、消息通知和对外回传通过 `ccr_outbox_event` 可靠异步执行。
3. 消费端以 `event_no` 幂等处理，避免"申请成功但任务未生成"或重复通知。
4. 审批、投票、行长决策使用业务版本号与唯一约束防止重复提交。

**Outbox 事件表（`ccr_outbox_event`）关键字段**：`event_no`（唯一，消费端幂等）/ `event_type`（FLOW_START / NOTIFY / RESOLUTION_CREATE / COMMITMENT_CREATE）/ `biz_type` / `biz_id` / `payload`(JSON) / `retry_count` / `max_retry`(默认5) / `next_retry_time` / `last_error`。消费按 `event_no` 幂等；失败指数退避重试，超过 `max_retry` 置 FAILED 并告警。

### 3.6 缓存设计（Redis）

**缓存目标**：热点读接口命中率 ≥90%，降低 DB 压力，支撑 §16 性能基线（单接口 P95 < 1s）。

| 缓存对象 | Key 设计（示例） | 过期 | 失效时机 |
|---|---|---|---|
| 字典项 | `ccr:dict:{type}:{value}` | 24h | 字典增删改/停用 |
| 参数版本（LPR/矩阵/产品边界/规则集/阈值） | `ccr:cfg:{domain}:{version_id}`、`ccr:cfg:{domain}:eff:{effective_date}` | 24h | 配置发布/作废（主动删） |
| 产品目录/产品审批链路 | `ccr:cfg:product:list`、`ccr:cfg:product-route:{product_code}:{date}` | 24h | 产品配置发布/停用（主动删） |
| 指标定义/展示模板 | `ccr:metric:{code}` / `ccr:schema:{code}` | 24h | 配置发布 |
| 矩阵命中结果 | `ccr:route:{matrix_no}:{条件hash}` | 1h | 矩阵发布 |
| 外部数据时效 | `ccr:source:{source_code}` | 5min | 数据批次入库 |
| 审批详情组装 | `ccr:approval:detail:{application_id}` | 随快照冻结只读 | 提交/审批操作后清 |
| 待办/消息角标 | `ccr:todo:badge:{user_id}` / `ccr:msg:badge:{user_id}` | 5min | 待办生成/完成时刷新 |
| 审批人员解析 | `ccr:assignee:resolve:{node_code}:{asOfDate}` | 1h | 人员配置变更 |

**一致性策略**：
1. **配置发布 → 主动失效**：`ccr:cfg:*` / `ccr:route:*` / 指标与模板 key 在配置复核发布成功后由发布服务删除（§8A.2），下次请求重建；
2. **版本号参与 Key**：配置类缓存 key 携带 `version_id`，天然隔离新旧版本，避免"改配置后读到旧值"；
3. **提交事务不读缓存**：`submit-check`、快照冻结、路由回写一律走 DB（当前事务），保证冻结口径精确（D11）；
4. **角标/时效类短 TTL 兜底**：待办角标、外部数据时效容忍短暂不一致，过期即失效。

**高可用与防护**：
- **穿透**：DB 未命中时缓存空值（短 TTL，如 60s）或布隆过滤器；
- **击穿**：热点 key（当前生效 LPR/矩阵）用 Redisson 分布式锁重建 + 逻辑过期兜底；
- **雪崩**：过期时间加随机抖动（±20%）；Redis 哨兵/集群部署；
- **降级**：Redis 不可用时熔断回 DB（缓存异常不阻断业务）；**写路径永不依赖缓存**。

### 3.7 数据源配置化（外部配置文件）

**目标**：数据库连接参数（驱动 / URL / 用户名 / 密码 / 连接池）从代码内配置抽离为**部署侧可修改的外部配置文件**，切换数据库环境**无需改代码、无需重新打包**，编辑配置文件即生效。

**现状（已核实 `ccr-admin/src/main/resources/`）**：`application.yml` 为公共配置（`spring.profiles.active: dev`、Sa-Token、Warm-Flow、MyBatis-Plus）；数据源 url/username/password 在 `application-dev.yml` **明文硬编码**；部署用 docker-compose 以环境变量 `SPRING_DATASOURCE_*` 注入覆盖。

**改造方案（基于现有 Spring Boot 外部化配置机制增量改造）**：

1. **连接参数抽离（含连接池）**：数据源连接参数**与连接池参数（Hikari）均移入各环境 profile 文件**——池大小按环境差异化（dev 小池 / test 中池 / prod 大池）；`application.yml` **不再含任何数据源连接参数**，仅保留公共配置（server/sa-token/warm-flow/mybatis-plus）。
2. **多环境 profile 文件**（jar 内置 dev 默认值）：
   - `application-dev.yml`（本地 / Docker 开发默认，现有文件改造）
   - `application-test.yml`（测试环境）
   - `application-prod.yml`（生产环境）
   - 环境切换：`spring.profiles.active=dev|test|prod`（默认 dev）。
3. **外部配置目录覆盖（核心）**：启动加载 `spring.config.additional-location=optional:file:./config/`（`optional:` 目录缺失不阻断启动）；部署侧在运行目录 `config/` 放置同名文件（如 `config/application-prod.yml`），**优先级高于 jar 内配置**；运维**直接编辑 `config/` 下文件**调整/切换数据库连接，无需重新打包。
   - **Spring 配置加载优先级（高→低）**：命令行参数 → `SPRING_*` 环境变量 → **外部 `config/` 目录文件** → jar 内 `application-{profile}.yml` → jar 内 `application.yml`。外部 `config/` 文件覆盖 jar 内默认；生产真实连接只需写入部署侧 `config/application-prod.yml` 即可，jar 内保留开发默认。
   - **外部 `config/` 目录模板**（部署侧提供；**建议加 `.gitignore`、不进代码库**）：
     ```
     config/
     ├── application-dev.yml      # 本地/Docker（jar 内已有默认，外部可选覆盖）
     ├── application-test.yml     # 测试环境真实连接（外部提供）
     └── application-prod.yml     # 生产环境真实连接（外部提供，含密码）
     ```
     示例 `config/application-prod.yml`：
     ```yaml
     spring:
       datasource:
         driver-class-name: com.mysql.cj.jdbc.Driver
         url: jdbc:mysql://prod-db-host:3306/ccr_rate?useUnicode=true&characterEncoding=utf8&serverTimezone=Asia/Shanghai&useSSL=false&allowPublicKeyRetrieval=true
         username: ccr_prod
         password: <真实密码，仅存此处>
         hikari:
           maximum-pool-size: 50
           minimum-idle: 10
     ```
4. **凭据管理**：本期**不引入密码加密**（业务方确认）；但真实密码**只存在于部署侧外部配置文件**（`config/` 下），jar 内/镜像内置为开发默认值，避免真实凭据进代码库与镜像。
5. **部署改造（docker-compose）**：后端容器挂载宿主机 `./config:/app/config`，设 `SPRING_CONFIG_ADDITIONAL_LOCATION=optional:file:/app/config/`，**移除** `SPRING_DATASOURCE_*` 环境变量注入——数据源参数统一由外部配置文件承载（`SPRING_CONFIG_ADDITIONAL_LOCATION` 仅用于告知 Spring"外部配置目录位置"，为 Spring Boot 机制，非数据源参数环境变量化）。
6. **共用数据源**：Warm-Flow / MyBatis-Plus 与业务共用同一数据源（`ccr_rate` 库），无需单独配置；若后续数仓分库，预留多数据源扩展点，本期不实现。

**验收**：
1. 修改部署侧 `config/application-dev.yml` 的 `url` 指向另一库并重启即连新库（jar 内文件未动）；
2. `spring.profiles.active=prod` 生效生产数据源；
3. 生产连接参数（含密码）仅存在于部署侧 `config/application-prod.yml`，jar 包/镜像内无真实密码；
4. 连接池参数按环境生效（dev 小池 / prod 大池）；
5. `docker compose up` 一键起环境仍正常连通。

## 4. 核心领域模型

### 4.1 业务层级

```
申请主体  →  个人、企业单户或集团客户
个人、企业单户  →  本客户业务；集团  →  集团授信与成员额度
本客户业务或成员额度  →  用信或担保分项（担保类型分项）
用信或担保分项  →  贷款合同/拟签合同 或 存款账户/拟开户方案
贷款合同或存款账户  →  合同级/账户级定价分项
定价分项  →  独立流程实例
独立流程实例  →  审批决议
审批决议  →  合同/补充协议或账户利率执行
贷款合同  →  多笔借据继承核验；审批决议  →  承诺计划
```

> 本节至 4.5 的集团总额度、成员拆分和成员关系设计**仅适用于 GROUP**；INDIVIDUAL 和 CORPORATE_SINGLE 不虚构集团或成员层级，直接以客户号关联其授信、合同、账户、借据和担保资料。

### 4.2 集团综合授信（仅集团场景）

- 集团综合授信是集团层面权威额度容器，字段至少含：集团授信编号、批复总额度、币种、已分配额度、已使用额度、可用额度、有效期、循环标识、状态、授信版本。
- 系统校验成员分配额度合计不得超过集团总额度，但**不自行计算**复杂额度占用；循环额度、表内外占用、币种折算等结果以授信系统或数仓提供为准。
- **金额档次判定（B18/D6）**：集团金额档次默认按集团综合授信批复总额度判断（`dw_group_credit_snapshot.approved_total_amount`），避免通过成员拆分规避权限层级；个人/企业单户按分项申请金额 `pricing_amount`。

### 4.3 成员授信额度（仅集团场景）

- 集团额度按成员拆分，支持 **EXCLUSIVE（独占）** 与 **SHARED（共享）** 两种模式；SHARED 通过 `shared_limit_group_no` 关联，不简单加总。
- 利率审批只读取成员额度，**不允许**在利率审批中调剂成员额度。

### 4.4 用信或担保分项

成员额度/客户下可有多个用信分项，如抵押、保证、信用、质押、银票保证金等。分项记录：产品、担保主类型、额度、已用额度、可用额度、期限、币种、状态。

### 4.5 合同、借据、存款账户和担保组合

- 贷款合同是利率执行载体；一个用信分项可对应多份贷款合同，一份贷款合同可对应多笔借据。
- 存量调息绑定现有合同并通过合同变更或补充协议执行；新增业务尚未签约时绑定拟签合同业务标识，审批通过后回填正式合同号。
- 同一合同下借据**不因笔数不同拆分审批**，借据仅用于核验余额、期限、担保及实际执行利率是否符合合同与决议。
- 存款定价分项可关联一个或多个同客户存款账户；新增存款未开户时可关联拟开立账户标识，审批后回填实际账号。
- 担保组合可在合同层关联，并保留合同下借据与具体担保措施的多对多明细（`ccr_note_guarantee_rel`）。
- 担保主体可能是当前成员、集团其他成员、集团外企业或自然人；抵押物/质押物所有人可与借款主体不同。

> 因此合同、借据与担保措施**分别建模**：审批关系绑定合同，执行核验沿合同读取多笔借据，借据与担保措施采用多对多关系，不在借据表中只保存一个担保类型。

### 4.6 利率定价分项（审批原子单位）

- 定价分项必须绑定实际利率执行载体：贷款绑定一份现有合同或拟签合同，存款绑定账户或拟开户方案。
- 一个贷款合同只生成一个有效定价分项和一份最终决议；同合同下多笔借据不重复生成审批任务。
- 多份合同即使申请条件相同，也在后台生成**独立定价分项和决议**，可在前台批量展示与办理。
- 拟签合同拆分至少遵循（任一条件不同必须拆分）：
  1. 同一实际定价客户、同一产品；集团场景还必须同一集团、同一成员；
  2. 同一担保主类型或同一担保组合；
  3. 同一期限档、币种、原利率、申请利率和调整原因；
  4. 规则引擎计算得到同一路由。
- 新增授信尚未签订合同时，定价分项关联拟用信分项和拟签合同业务标识；审批后回填正式合同并校验合同金额、期限、担保、最终利率和决议日期。

## 5. 角色与权限

> 权限模型采用"**组织—岗位—用户 + 功能权限码 + 数据权限 + 审批节点权限**"四层结构，认证由内部工作平台统一 SSO 完成（B19），Sa-Token 负责会话与鉴权。

### 5.1 组织—岗位—用户模型

**组织（机构）树**：
- 层级：总行 → 部门（公司金融部 / 授信评审部 / 零售金融部 / 风险管理部 / 计划财务部 / 内控合规部 等）→ 分支机构（支行）→ 网点。
- 机构编码唯一；支持集团管理机构（成员机构归属）。
- 机构树用于数据权限范围与审批岗位归属（`dept_code`）计算。

**岗位（pos）**：客户经理、支行行长、部门总经理、分管行领导、六人小组成员、总行行长、配置复核人、流程管理员、审计人员、合同经办岗。岗位挂机构；同一岗位在不同机构可存在多个实例。另内置 **admin（超级管理员）**：系统管理 + 参数配置全功能，不参与业务审批，无机构归属。

**用户（user）**：来自内部工作平台统一认证，一个用户可绑定多个岗位/机构组合（如"城东支行 客户经理"与"宜城支行 客户经理"）；登录后当前机构/岗位可切换（限本人已授权组合，禁止越权伪造）。

**会话与映射**：SSO 登录 → 后端按统一用户标识映射出机构、岗位、角色、权限码集合 → 生成 Sa-Token 会话；**前端不传角色/权限，只显示后端下发的权限集合**。**会话超时（业务方确认）**：会话采用**活跃超时（idle timeout）2 小时**——Sa-Token `activeTimeout=7200` 秒，任意合法请求自动续期；**连续 2 小时无任何操作会话自动失效、强制退出，须重新登录后才能进入**；到期后受保护接口统一返回 401，前端清除本地登录态并跳转登录页（移动端同规则，复用 PC 会话）。

### 5.1.1 机构管理功能（admin，系统管理域）

机构由 **admin** 在"系统管理-机构管理"统一维护（权限码 `ccr:system:dept:*`），是数据权限（§5.4）与审批岗位归属（§5.5）的根。设计要点：

- **机构类型**：`HEAD`（总行）/ `DEPT`（部门）/ `BRANCH`（支行）/ `NETWORK`（网点）/ `GROUP`（集团管理机构）。机构树层级：总行 → 部门 / 支行 → 网点；集团管理机构独立挂载，成员机构经 `parent_id` 归属。
- **编码规则**：**层级前缀编码**（如 `1000` 总行 → `1002` 支行 → `100201` 网点）。**机构范围按编码前缀匹配**，避免递归查询——`当前机构编码` 为前缀即"本机构及全部下级"，如 `apply_branch_code LIKE '1002%'` 覆盖支行 1002 及其网点 100201（支行行长 DEPT 范围，§5.4）。
- **机构字段**：编码（唯一、禁改）、名称、上级机构、机构类型、状态（启用/停用）、负责人、备注；`del_flag` 软删。见 §10.3.20 `sys_dept`。
- **状态控制**：新增机构默认停用，启用后方可被用户绑定与业务选择；**停用/删除校验**——机构下存在未完结申请、在途审批任务、未关闭承诺时禁止停用/删除（提示存量业务数）；停用不影响历史数据只读。
- **用户—机构—岗位绑定**（admin 在"系统管理-用户管理"维护）：一个用户可绑定多个机构/岗位组合（如客户经理可挂多个支行），设置**默认机构/岗位**（登录首启）；登录后切换机构/岗位限本人已授权组合（§5.1）。
- **数据权限范围计算**：登录时按用户当前机构计算 `dept_scope`（数据权限级别 + 机构编码前缀集合）写入 Sa-Token 上下文，拦截器据此注入 SQL（§5.4）；**机构树变更后广播事件，强制在途会话重新计算**。

| 角色 | 端侧 | 可见范围 | 主要操作 | 不可操作 |

**岗位部门归属（D16a）**：权限矩阵中"部门总经理/分管行领导"按业务类型归属部门——**对公存量 → 公司金融部**；**对公新增授信 → 授信评审部**；**个人经营性贷款 → 零售金融部**。审批沿归属自动路由对应部门岗位。

**六人审批小组组成**（§7.5）：授信评审部分管行领导、风险管理部分管行领导、计划财务部分管行领导、授信评审部总经理、风险管理部总经理、计划财务部总经理。

### 5.3 功能权限码体系（菜单 / 按钮 / 接口三级）

权限码格式：`ccr:{域}:{动作}`。前端 `v-permission` 控制菜单与按钮显隐；后端 Sa-Token 接口校验权限码；两者必须一致（前后端权限清单由后端接口 `/api/v1/auth/permissions` 统一下发）。

| 域 | 权限码（示例） | 授权角色 |
|---|---|---|
| 申请 | `ccr:application:create / edit / submit / resubmit / delete / draft` | 客户经理 |
| 审批 | `ccr:approval:todo / approve / reject / adjustRate` | 支行行长、部门总经理、分管行长 |
| 表决 | `ccr:vote:ballot / count / result`（`result` 仅行长+审计） | 六人小组成员 |
| 行长决策 | `ccr:president:decide` | 总行行长 |
| 决议 | `ccr:resolution:settle / verify / list` | 合同经办岗、行长 |
| 快照/数据 | `ccr:snapshot:view / confirm` | 客户经理（提交前）、数据中心管理员 |
| 承诺 | `ccr:commitment:view / evaluate / monthlyReport / feedback` | 客户经理、支行行长、部门 |
| 配置 | `ccr:config:lpr:edit / matrix:edit / limit:edit / policy:edit / dataset:edit / dict:edit`、`ccr:config:*:publish`（复核人；admin 默认持有全部） | 配置复核人（admin 全部） |
| 审计 | `ccr:audit:ballotDetail / export / configVersion` | 审计人员 |
| 消息 | `ccr:message:list / read` | 全部登录用户 |
| 导出 | `ccr:export:contribution / history / monthlyReport / archive` | 按数据权限 |
| 系统管理 | `ccr:system:dept:view / edit / status`、`ccr:system:user:view / edit / assign` | admin |

### 5.4 数据权限（四级）

| 级别 | 范围 | 应用场景 |
|---|---|---|
| `ALL` | 全行 | 总行行长、审计（授权范围内）、admin（配置域） |
| `DEPT` | 本机构及全部下级机构 | 支行行长（本支行及网点申请与跟踪）、部门总经理（本部门对应业务类型）、分管行长 |
| `GROUP_MEMBER` | 集团管理机构 + 成员机构 | 集团客户经理、集团审批 |
| `SELF` | 本人 | **客户经理（本人提交的申请/承诺/贡献度）**、委员会（本人表决任务）、普通审批（流转到本人的任务） |

- 数据权限由 Sa-Token 登录角色、领域服务对象授权和服务端列表过滤共同执行，**禁止在前端传入机构或申请人条件决定访问范围**。
- **新增（create）服务端打标**：客户经理新建申请时由登录上下文写入 `applicant_user_id`、`applicant_org_id`、`apply_branch_code`；请求体同名字段不参与归属判定。
- **查询与存量操作**：客户经理按申请人本人过滤；支行行长按 `apply_branch_code` 精确匹配所属支行并覆盖下辖网点；普通审批、分管、委员和合同经办按当前指派、历史参与、表决分配或决议关系校验。详情、保存、提交、附件、历史和导出统一调用 `ApplicationAccessService`，越权返回 403。
- 审批任务权限采用"节点 + 机构 + 本人"三重匹配：任务候选人为"该节点归属部门 + 当前处理机构（普通审批）/ 固定 6 名成员（委员会）"。

### 5.5 审批节点权限（`ccr_node_permission`）

节点权限决定"谁能审批、能否调价、调价边界、是否必经、是否上送"。由路由引擎在提交事务内解析并写入分项。

| 字段 | 说明 |
|---|---|
| `node_code` | 节点编码（branch_manager / dept_manager / supervising_president / committee / president_decision） |
| `role_codes` | 可审批角色集合 |
| `dept_code` | 审批归属部门（D16a） |
| `can_adjust_rate` | 是否可调价（普通节点 Y；委员会/行长 N） |
| `boundary_source` | 调价边界来源：`MATRIX`（权限矩阵）/ `PRODUCT`（产品硬边界） |
| `boundary_rate` | 本节点权限下限（由矩阵计算，见 §8.2） |
| `mandatory_flag` | 是否必经节点（所有申请支行行长 Y，B13） |
| `auto_escalate_flag` | 低于下限是否自动上送（Y） |
| `sort` | 节点顺序 |

**节点调价规则（B7/D3）**：
1. 审批利率必须 ≥ 本节点权限下限（`boundary_rate`）且 ≥ 产品硬边界下限。
2. 审批人调价后利率仍 ≥ 下限 → 本节点通过并采用调整后利率。
3. 审批人调价后利率 < 下限（或申请利率本就 < 下限）→ 禁止本节点终审，工作流自动上送上一节点/进入六人小组。
4. 委员会与行长节点**不可调价**，只能对现有申请利率投票/决策（B8/B12）。

### 5.5.1 审批人员可配置（`ccr_node_assignee`）

> **需求**：审批流程各节点的实际处理人必须**可配置**，而非硬编码为固定角色/固定人。支持按人、按角色、按部门、按人员组四种指派方式，并支持**代理人（暂代）**与**有效期**。配置由流程管理员维护（权限码 `ccr:flow:assignee:*`），随流程定义生效。

**三层指派模型**（解析优先级从高到低）：

| 层级 | 配置载体 | 说明 |
|---|---|---|
| 人员级 | `ccr_node_assignee`（`assignee_type=PERSON`） | 直接指定具体审批人，最高优先 |
| 组级 | `ccr_node_assignee`（`assignee_type=GROUP`） | 指定人员组（复用系统人员组） |
| 部门+角色级 | `ccr_node_permission`（`role_codes` + `dept_code`） | 按角色 + 归属部门动态匹配 |
| 角色级（兜底） | `ccr_node_permission`（`role_codes`） | 未命中上层时按全局角色匹配 |

**解析顺序**：同一节点先命中人员级 → 组级 → 部门+角色级 → 角色级，命中即止；同层多指派人按 `relation`（AND=需全员 / OR=任一，默认 OR）与 `sort` 处理。

**`ccr_node_assignee` 字段要点**（完整字段见 §10.3.19）：
- `assignee_type`：`PERSON`（工号）/ `GROUP`（组编码）/ `ROLE`（角色码）/ `DEPT`（部门码）；
- `relation`：`AND`（多人时生成多份待办，需逐人处理）/ `OR`（任一人处理即通过）；
- `delegate_to` + `delegate_start`/`delegate_end`：**代理人暂代**，有效期内新待办投递给代理人，主指派人保留可见，到期自动回退；
- `valid_from`/`valid_to`：配置有效期，过期配置不参与解析；
- `flow_key`：可限定到具体流程定义，空则适用该节点所有流程。

**待办生成与冻结（与快照不可变一致，D11）**：
1. 提交事务内由路由引擎解析节点序列后，按上述顺序**解析每个节点的实际处理人**（含代理展开），写入 `ccr_approval_task` 的 `assignee_id/assignee_name/assignee_type`；
2. 解析结果随提交**冻结**：审批中途修改 `ccr_node_assignee` **只影响新提交的流程**，不影响已流转实例，避免审批中换人导致流程跳变；
3. Warm-Flow 节点 handler 不硬编码处理人，统一读取任务上的 `assignee_*` 字段生成待办；
4. **运行期例外**：被指派人可自行设置/更换代理人（`POST /api/v1/flow/assignee/{id}/delegate`），不影响已生成待办的主指派人记录，操作写审计日志。

**变更审计**：人员配置增删改、代理设置均写操作日志（§15.3）；批量变更前强制 `resolve` 预览解析结果（§12.17）。

### 5.5.2 部门分流方案 A（§D16a 落地，2026-08-11）

> §D16a 岗位部门归属（§5.2 已述）：对公存量 → 公司金融部；对公新增授信 → 授信评审部；个人经营性贷款 → 零售金融部。本小节为实现机制（**分的是节点内处理人，不是节点链**——链路 `BRANCH_MANAGER→DEPT_GENERAL_MANAGER→VICE_PRESIDENT→SIX_PEOPLE_GROUP` 不变）。

- **部门归属编码统一**：矩阵 `ccr_rate_matrix.dept_code` 统一为机构部门编码（GSB=公司金融部 / SXSB=授信评审部 / LSB=零售金融部），经 `ccr_sys_dept.dept_code` 关联机构（消除独立第三套编码）。部门改名只改 `dept_name`，审批流不受影响。
- **dept_code 透出落库**：路由计算后透出到 `RouteResult.deptCode`，提交时冻结到分项 `ccr_pricing_item.dept_code`（新增列）。
- **部门总经理按部门解析**：`ccr_node_assignee` 用 `assignee_type=DEPT`、`assignee_code` 语法「机构dept_code:角色码」（如 `GSB:dept_gm`）——按分项 `dept_code` 精确匹配机构，取该机构下指定角色启用用户（换总经理只改机构角色配置，不依赖具体工号）；无「:」维持原 org_code 前缀匹配（兼容存量）。
- **分管行领导一人分管多部门**：新增 `ccr_dept_vp(dept_code, vp_user_id, ...)` 映射表（一个部门多分管行长、一个分管行长多部门，纯配置）。VICE_PRESIDENT 节点且分项 dept_code 非空时按映射解析；未命中/无 dept_code 回落原四层/角色兜底。
- **待办与权限**：待办过滤 `filterByNodeAssignee`、权限校验 `guardNodeAssignee` 均按分项 `dept_code` 解析部门类节点处理人；越权审批被拦截。

### 5.8 移动端权限映射

- 移动端**不自行鉴权**：内部工作平台 WebView 容器注入 `access_token` → 后端校验并复用 PC 会话权限码。
- 移动端仅渲染审批类权限（`ccr:approval:* / ccr:vote:ballot / ccr:president:decide`）对应的入口；其余入口（申请/配置/数据）在后端返回菜单时直接过滤。
- 移动端审批详情数据接口与 PC 同源（读同一快照），仅返回审批所需字段。

### 5.9 权限校验时序

```
SSO 登录（内部工作平台）
  → 后端映射：用户 → 机构/岗位/角色/权限码集合
  → 生成 Sa-Token 会话（存登录人、角色与当前机构）
  → 每次请求：① 登录态校验 → ② 接口角色/权限校验 → ③ 领域服务对象授权与服务端列表过滤
      → ④ 业务状态机校验（如仅 DRAFT 可提交、仅 COMMITTEE_PASS 可决策）
      → ⑤ 写操作幂等 + 乐观锁
```

### 5.10 权限原则与审计

1. 前端菜单、按钮、接口、数据四层同时控制，权限集合由后端统一下发。
2. 数据权限按总行、部门、集团管理机构、成员机构、本人任务五类控制。
3. 真实系统不提供普通用户随意切换角色的能力（演示环境除外）。
4. 移动端复用内部工作平台 SSO，不允许前端自行伪造机构/岗位/角色。
5. 全部权限变更、越权尝试、敏感查询（投票明细/导出/审计）记录操作日志。

### 6.2 F2 客户基本信息管理（仅 PC 客户经理端）

- 支持**企业/个人**客户基本信息录入与展示；支持**关联人**录入（姓名/关系/证件号；若在客户信息库中匹配则标记为该客户关联人）。
- **关联人唯一绑定（新决策）**：关联人可**对公**（统一社会信用代码）可**对私**（身份证），以**证件号区分并必填**；**录入即判定占用**——证件号已在**全行**范围内绑定其他客户则无法再次绑定；**绑定对象 = 申请主客户**（单户场景 `customer_no`；集团场景绑**集团编号 `group_no`**，同一集团可复用）；**暂不支持解绑**。存储于独立表 `ccr_relation`（§10.3.21），接口见 §11.2 `relations/check`、`relations/bind`。
- 对公字段：客户名称、统一社会信用代码、基本账户开户行（本行基本户/他行基本户/暂无）、五级分类、内部信用等级、所属行业、注册资本、客户性质（存量/新增）、申请机构等。
- 对私字段：姓名、证件类型、证件号码、是否本行开户、开户机构、开户日期、职业、年收入、婚姻状况、居住地址、联系电话、客户性质等。
- **客户性质判定（D6）**：当前有账户且有历史贷款余额 = 存客；有账户无历史余额 = 新客。数据源为客户主数据每日同步（快照批次），申请创建时绑定快照存档，审批期间口径稳定。
- 关联人贡献度由数仓按关联人证件号反查（`metric_scope='RELATED'`），并入当前贡献度展示；**不产关联人关系快照表**（PRD §8.2）。

### 6.3 F3 贡献度展示（双概念并列）

- **当前贡献度（数仓取数）**：对公/对私本人/关联人三范围，区分"业务余额 / 收入中收 / 折算贡献"三类口径分别展示；**综合贡献总额（数仓权威值）+ 明细** 并列展示，明细加总与总额勾稽（D13b）。
- **拟达成贡献度（申请录入）**：与当前贡献度**并列展示**给审批人，作为定价参考。
- 数据来源标注：每类数据展示数据来源（仓库/人工录入）、数据日期、统计区间和本次落地情况。
- **勾稽校验（D13b）**：数据仓库同时传入**综合贡献总额（权威值）与指标明细**，本系统将**参与勾稽的明细**（排除 `RATIO` 存贷比等无贡献金额的派生指标）加总，并与总额做差额校验：差额为 0 → 通过；在可配置容差内 → 预警；超容差或**必填指标缺失** → **校验失败（默认阻止提交）**。
- **综合贡献总额定义**：由数仓按贡献度口径（万元）直接提供的**权威汇总值**（纵表指标中编码如 `TOTAL_CONTRIBUTION`，或接口独立字段 `totalContribution`），**不是**本系统对明细的简单相加结果；明细加总仅用于与总额比对、验证明细推送完整一致。两类口径"业务余额 / 收入中收"各自金额由数仓折算为贡献度金额后归入总额，本系统**不自行折算**、不做 FTP/费率等参数计算（暂不启用）。

**当前贡献度指标一览（依据《XX企业贡献度测算明细》核对，PRD §9.0）：**

| 指标编码 | 指标 | 范围 | 指标值口径 |
|---|---|---|---|
| `TOTAL_CONTRIBUTION` | **综合贡献总额** | 综合 | **数仓权威值（万元），勾稽比对基准（§6.3/D13b）** |
| `PUBLIC_DEPOSIT_AVG` | 存款日均 | PUBLIC | 数仓直接提供的贡献度金额 |
| `PUBLIC_PROJECT_LOAN_AVG` | 项目贷日均 | PUBLIC | 数仓直接提供的贡献度金额 |
| `PUBLIC_DISCOUNT_SPREAD` | 贴现规模 | PUBLIC | 数仓直接提供的贡献度金额 |
| `PUBLIC_OFF_BALANCE_INCOME` | 中间业务收入 | PUBLIC | 数仓直接提供的贡献度金额 |
| `PUBLIC_EXCHANGE_SPREAD` | 结售汇业务总量 | PUBLIC | 数仓直接提供的贡献度金额 |
| `PUBLIC_PAYROLL_CONTRIBUTION` | 代发客户数 | PUBLIC | 数仓直接提供的贡献度金额 |
| `PUBLIC_PAYROLL_AMOUNT` | 代发金额 | PUBLIC | 数仓直接提供的贡献度金额 |
| `PUBLIC_WEALTH_INCOME` | 对公财富中收 | PUBLIC | 数仓直接提供的贡献度金额 |
| `PRIVATE_DEPOSIT_AVG` | 对私存款日均 | PRIVATE_SELF | 数仓直接提供的贡献度金额 |
| `PRIVATE_LOAN_AVG` | 对私贷款日均 | PRIVATE_SELF | 数仓直接提供的贡献度金额 |
| `PRIVATE_WEALTH_INCOME` | 对私财富中收 | PRIVATE_SELF | 数仓直接提供的贡献度金额 |
| `PUBLIC_DEPOSIT_LOAN_RATIO` | 存贷比 | RATIO（派生参考） | 对公存款月均/(流贷月均+项目贷月均)，数仓直接提供比率值，**不参与勾稽** |

> 指标值为数仓直接提供的贡献度金额（万元），业务系统直接加总勾稽、不做任何参数计算（FTP/费率等参数折算暂不启用）。

### 6.4 F4 拟达成贡献度（承诺）管理（仅 PC）

- **录入**：客户经理申请时按申请/担保类型逐笔录入拟达成贡献度（对公/对私/关联人指标维度），作为本笔申请承诺基线，随申请存档、审批期间不变。
- **承诺类型下拉**：存款日均提升、贷款新增、中收增长、代发业务增长、项目贷款新增、贴现业务增长、汇兑业务增长、外汇中收增长、财富中收增长、关联人存款提升、结算归行率提升、**其它（手工录入，无法跟踪达成）**。
- **规则**：不做勾稽校验、不设时效限制（D15）。
- **"其它"项（承诺类型"其它"）**：由客户经理**手工录入**，**目标值可为金额（万元）或自由文本描述**（如业务推进事项，存 `commitment_desc`）；数仓 `dw_contribution_metric` **无"其它"指标（数仓不产）**，故该承诺项**不做数值达成跟踪**——**不计入机构达成率分母（D19）**（分子无数仓"其它"实际达成值，计入将致分母虚高失真）；**跟踪方式改为客户经理手工描述**：在承诺跟踪页（§12.11）手工填写跟踪内容（进展/说明，textarea，存 `ccr_commitment_metric.track_desc`）留痕，**不计算数值达成率、不参与阈值预警与月报提醒**；审批/跟踪展示以手工描述为准，标注"手工描述跟踪，无数值达成率"。
- **达成跟踪（D21，以数仓当前贡献度为实际达成值）**：
  1. 将同一客户跨申请/担保类型的拟达成承诺**按指标 code 加总**，聚合为客户级承诺基线（分母）；
  2. 以数仓最近批次当前贡献度同指标实际值（分子）逐项对比，计算达成率与落差；
  3. 按月推送落差提醒（F6）。
- **展示**：与数仓当前贡献度并列展示给审批人，作为定价参考。
- **机构达成率（D19）**：分母 = 该机构**已通过审批**申请所录入的拟达成贡献度（承诺）合计（按贡献金额计算，**不含"其它"手工项**）；分子 = 数仓当前贡献度（最近批次，客户级）已达成贡献金额。草稿/被否不计入考核基线。

### 6.5 F5 分级利率审批

- 按金额/利率/客户类型自动判断层级，6 人投票，≥4 票通过执行申请利率。
- 分级路由规则见第 8 章（LPR±BP 权限矩阵）。

- **客户经理提交申请后必经支行行长节点**（B13，§8.3），支行行长通过后按链路继续流转。
- 上会必经行长决议（D20a）。

### 6.6 F6 消息通知

- 审批进度推送：节点流转、待办生成、表决结果、行长决策结果实时推送。
- 拟达成贡献度未达成**月报提醒**（以数仓当前贡献度为实际达成值）；提醒对象支持动态解析（客户经理、支行行长、审批小组成员等）。
- 消息类型：`approval`（待处理提醒）、`result`（审批完成）、`warning`（承诺未完成提醒）、`system`（系统通知）。
- 通知走 `ccr_message` + 内部工作平台 App 推送；带重试、回执、去重（`message_key` 唯一）。

### 6.7 F7 数据导出

- **批次落地监控动态化（#42，2026-08-12）**：落地表清单不再写死，实时查询 `information_schema.TABLES`（`table_schema=DATABASE()`、`table_type='BASE TABLE'`、`table_name LIKE 'dw\_%' OR 'caps\_%'`），排除弃用表 `dw_org_dim`，表名正则白名单 `^[a-zA-Z][a-zA-Z0-9_]*$` 防注入；新增/下线表无需改代码自动纳入/消失；表中文说明走"已知表→说明"映射（缺失回退表名）。详见 §9.6。

## 7. 业务流程设计

### 7.1 申请步骤（PRD §7.1）

```
选择客户主体类型（个人/企业单户/集团）→ 输入客户基本信息
→（集团）录入集团与成员额度
→ 录入本行融资、他行融资（补录+Excel/OCR）、担保资料、佐证材料
→ 录入申请利率、申请期限、担保类型分项（逐担保类型拆分）
→ 选择承诺类型并录入拟达成贡献度
→ 数据校验（质量/时效/勾稽）→ 通过或阻断
→ 保存草稿（可多次）→ 提交（冻结快照+计算路由）
→ 进入审批工作流
```

### 7.2 申请提交事务（PRD §8.7，全链路自动串联）

**提交接口**：`POST /api/v1/application/{id}/submit`

**原子事务（`@Transactional`）**：
1. 锁定申请版本（`version_no` 乐观锁），校验状态必须为 `DRAFT`。
2. 重新执行**最新数据校验**：质量校验、数据时效校验、贡献度勾稽校验；任一失败整体回滚并返回阻断项明细。
3. **产品校验**：逐分项校验产品已启用（`ccr_product`）且当前存在生效产品审批链路（`ccr_product_route`）；产品停用/未配置链路 → 阻断。
4. 按权限矩阵**冻结 LPR 版本与规则版本**（`lpr_version_id`/`rate_rule_set_id`），以提交日为准。
5. 创建**不可变快照包**（`ccr_snapshot_bundle`）并绑定申请。
6. 逐担保类型分项调用 `RateMatrixRouter.calcRoute` 计算**唯一路由**（按产品命中 `ccr_product_route` 链路 + `ccr_rate_matrix` 边界，§8A.5②），回写 `route_code`、`start_node_code` 与链路模式。
7. 状态置 `SUBMITTED→ROUTING`。
8. 同事务写入 Outbox 事件：`FLOW_START`（逐分项发起流程）、`NOTIFY`。

**提交后异步（Outbox 消费，幂等）**：
- 流程实例发起（Warm-Flow），按路由起始节点生成第一个待办。
- 向申请人、下一节点审批人推送消息。
- 任一异步环节失败自动重试（指数退避，上限 5 次），超过置 FAILED 并告警，不阻塞主流程。

> 提交失败 = 整单回滚，不会出现"申请已建但快照未绑"的半成品（D11 不可变快照 + §8.7 提交事务）。

### 7.3 审批接口与动作

| `POST /api/v1/approval/task/submit-check` | 提交前校验：完整性 + 最新数据校验（质量/时效/勾稽），返回阻断项 |

### 7.4 审批人详情页数据组装

审批详情页按 `applicationId + pricingItemId` 组装，数据源全部来自**提交时冻结快照**（只读，无"刷新外部数据"按钮——按 PRD B11/D11 已移除）：

1. **客户基本信息**（对公/对私 13 字段）：名称、证件号、基本户行别、五级分类、内部信用等级、行业、注册资本、客户性质、申请机构、开户机构等。
2. **存款申请**：账户号、产品、期限、当前利率、申请利率。
3. **贷款申请（融资情况）**：融资余额、期限、当前利率、申请利率、贷款投向。
4. **担保**：担保类型、担保主体、抵押物/质押物、担保金额。
5. **历史履约**：还款记录、逾期情况、五级分类变化。
6. **机构达成**：该机构已通过审批申请的承诺合计与数仓当前贡献达成（D19）。
7. **关联人**：关联人姓名、证件号、关系、关联人当前贡献度。
8. **客户贡献度方案**：当前值（数仓） vs 申请值（拟达成承诺），分指标并列。
9. **节点利率调整记录**：原利率 → 节点调整后利率 → 申请利率，含调整人、调整时间、原因。
10. **决策区**：普通节点决策（通过/否决）、委员会表决区（匿名，只显示自己的票与状态）、行长决策区（同意/否决）。
11. **授信信息（#74 手工补录，2026-08-12）**：数仓授信协议与 `credit_info_json` 手工补录快照**合并展示**——补录行 `source="APPLICATION"` **置顶**（新增授信协议号可空显示「—」）、按协议号与数仓去重；徽标动态「申请补录 + 数仓 / 数仓」，补录行协议编号带「补录」标记。

### 7.5 六人表决流程（D5/D9/D10/D17/D20）

**成员组成**：授信评审部分管行领导、风险管理部分管行领导、计划财务部分管行领导、授信评审部总经理、风险管理部总经理、计划财务部总经理（6 人固定）。

**规则**：
1. **逐担保类型独立计票**（D18a）：每个定价分项生成独立的表决批次与任务，不跨分项合并计票。
2. 委员会只能投"通过 / 否决"，**不能修改利率**（B8）。
3. **一人一票**：同一委员对同一分项只能投一票；重复投票被幂等拦截（`(round_id, round_item_id, voter_user_id)` 唯一约束）。
4. **匿名性（B10/D9）**：委员间互相看不到：身份、票型、处理状态、汇总结果。系统内部通过"匿名码映射表"实现，委员端只显示本人投票状态；汇总结果仅向总行行长及授权审计人员展示。
5. **计票**：六票齐（或超时到期后按已投票人数）触发计票；赞成票 **≥4** 通过（B9），少于 4 票否决。整个会话不显示"2/3"等易混淆措辞（B5 修正）。
6. 表决通过的分项 → 自动进入行长决策（B11/D20a）；表决否决 → 该分项置 `VOTED_DOWN`，整单进入相应终态。
7. 行长决策在**同一页面分项决策区**逐分项完成，不能修改利率（B12）。

### 7.6 行长最终决策（B12/B11）

- 前置：该定价分项经委员会表决通过。
- 总行行长按定价分项选择"**同意利率**"或"**一票否决**"，不修改利率。
- 同意 → 分项 `FINAL`，决议自动签发（`ISSUED→CONTRACT_PENDING`），承诺计划自动生成。
- 一票否决 → 分项 `VETOED`，整单按分项状态汇总进入终态。
- 行长决策自动触发：决议签发 → 决议执行核验 → 承诺计划生成（Outbox 串联，全程幂等）。

### 7.7 决议签发与执行核验

**决议签发（D11）**：行长决策同意后自动生成 `ccr_resolution`，主键雪花，决议号格式 `RES-YYYYMMDD-<seq>`，金额 `DECIMAL(20,4)` 万元、利率 `DECIMAL(9,6)` 百分数、**`issue_time`（决议日期=签发时间，自动生成，无有效期周期）**、状态 `ISSUED→CONTRACT_PENDING`。

**决议回填七项校验（合同经办岗回填合同号/补充协议号后自动触发）**：
1. 决议必须存在且未作废。
2. 合同号/补充协议号非空且唯一。
3. 合同客户必须与决议客户一致（客户号一致）。
4. 合同金额 ≥ 决议金额（合同金额不得小于决议金额）。
5. 合同期限 ≥ 决议期限（合同期限不得短于决议期限）。
6. 合同最终执行利率 = 决议利率（按合同号/补充协议号取 `dw_loan_note_snapshot` 最新执行利率）。
7. 担保措施与决议担保类型匹配（担保主类型一致，抵押物/质押物对应）。

**两级执行核验**：
- **合同级**：合同最终执行利率 = 决议利率。
- **借据级**：借据执行利率 = 合同最终执行利率（沿 `ccr_pricing_item_contract_rel` → 合同 → `dw_loan_note_snapshot` 多笔借据逐一核验）。
- 任一不一致 → 核验失败，自动通知合同经办岗（幂等去重，`message_key` 唯一），阻塞决议归档，直至人工修正或重跑核验通过。

### 7.8 退回 / 重提（D18b，修正已实现系统问题①）

> ⚠️ **修正说明**：已实现系统文档 07 的 D-7 曾写"重提全部重新审批（不沿用原决议）"，与 PRD D18b 冲突。**本设计以 PRD D18b 为准**：重提时**已批准类型必须沿用原决议**，只重审未通过或新增的类型。

**退回触发条件**：某定价分项被否决（委员会否决 / 行长一票否决）。

**退回语义（§7.5 / PRD §7.6）**：
1. 原申请或原分项保持**终态**（`VOTED_DOWN` / `VETOED` / `REJECTED`），**不可回退到 DRAFT** 修改后重走（B6）。
2. 客户经理**重新发起新申请**，新申请在后台**关联原申请**（`ccr_application_relation`，`relation_type='RE_SUBMIT'`）。
3. **重提分项规则（D18b）**：
   - 原申请**已批准**的定价分项 → **沿用原决议**，不重新发起审批；
   - 原申请**未通过/新增**的定价分项 → 重新发起审批；
   - 若需修改已批准分项的利率 → 走**新增变更申请**（关联原决议），不覆盖原决议。
4. 重提继承引用原申请的他行融资补录数据（D14）。
5. 重提申请产生**新申请号**，原申请终态归档可查（历史审批）。

**重提数据流**：`ccr_application_relation(relation_type='RE_SUBMIT', src_application_id, target_application_id)` + `ccr_pricing_item.source_pricing_item_id / inherit_flag` 标记分项继承关系。

### 7.9 状态机（§7.6 / PRD §7.6，修正说明）

```
DRAFT
  │ 提交（submit）
  ▼
SUBMITTED
  │ 提交事务成功（冻结快照+路由）
  ▼
ROUTING
  │ 普通节点逐级通过/上送
  ├──► APPROVED_LEVEL（本级权限内终审，无更高节点）
  │       │ 决议签发
  │       ▼
  │     FINAL
  │
  ├──► VOTING（六人小组）
  │       │ 逐担保分项独立计票，≥4 票
  │       ▼
  │     COMMITTEE_PASS
  │       │ 上会必经行长
  │       ▼
  │     PRESIDENT_DECISION
  │       ├── 同意 → FINAL（决议签发+承诺计划）
  │       └── 一票否决 → VETOED
  │
  └──► REJECTED（某节点否决）
          ├── 重提（新申请，已批准沿用原决议）
          └── CLOSED
  │
  └──► RETURNED（重提后原申请终态，不可回 DRAFT）
```

> ⚠️ **状态机修正说明**：已实现系统将"重提"建模为 `RETURNED→DRAFT`，与 PRD §7.5/B14 冲突。**本设计采用终态模型**：任何被否/退回的申请保持终态，重提创建新申请（新申请号）并关联原申请，原申请不可回 DRAFT。

**分项级状态**（每个定价分项独立）：`PENDING → ROUTING → APPROVED / VOTING → COMMITTEE_PASS / PRESIDENT_DECISION → FINAL / VETOED / REJECTED`。

### 7.10 数据校验流程

- **质量校验**：必填缺失、格式错误、范围错误、关联完整性、金额/利率字段类型与范围。
- **时效校验**：外部数据批次 `data_dt` 距今 ≤ 配置时效（如 3 个自然日），超时阻止提交。
- **勾稽校验**：贡献度明细加总 vs 总额差额；0 通过、容差内预警、超容差阻断。
- **利率边界校验**：申请利率 ∈ [全行业务硬边界, LPR±BP 权限矩阵边界]；任一校验失败返回阻断项，整体回滚。

## 8. 利率规则与路由引擎

### 8.1 路由模型

```
输入：pricingItem（金额、期限档、担保类型、产品、业务大类型、新旧客户、所属机构）
  + 冻结 LPR 版本 + 冻结权限矩阵（boundary_rate/boundary_bp/bp_sign）
  → 匹配 RateMatrix（最高优先级优先，priority 升序，第一命中生效）
  → 输出 route_code + 节点序列（node1 → node2 → ... → 决议）
```

### 8.2 权限矩阵表（`ccr_rate_matrix`）

| 字段 | 含义 | 示例 |
|---|---|---|
| `matrix_no` | 矩阵编号 | MATRIX-001 |
| `business_big_type` | 业务大类 | LOAN / DEPOSIT |
| `new_or_existing` | 新客/存客 | EXISTING / NEW |
| `customer_type` | 客户类型 | INDIVIDUAL / CORPORATE / GROUP |
| `enterprise_type` | 企业性质（对公） | SOE（国企）/ NON_SOE（非国企）/ N/A（个人） |
| `amount_tier` | 金额档次（万元） | 对公默认分档 `(0, 5000]` / `(5000, ∞)`，可配置（§8.4） |
| `term_tier` | 期限档 | `(0, 12]` 月 |
| `guarantee_type` | 担保类型 | GUARANTEE / MORTGAGE / CREDIT / PLEDGE |
| `start_node_code` | 起始审批节点 | branch_manager |
| `dept_code` | 审批归属部门（岗位路由） | corp_finance / credit_review / retail |
| `boundary_type` | 边界类型 | `RATE` / `BP` |
| `boundary_min_rate` | 最低利率 | 3.000000（%） |
| `boundary_bp` | BP 边界值 | 35（BP） |
| `bp_sign` | BP 符号 | ABOVE（加）/ BELOW（减） |
| `lpr_term` | 关联 LPR 期限 | 1Y / 5Y |
| `priority` | 匹配优先级（越小越优先） | 1 |

**边界利率计算**：
- `boundary_type='BP'`：`boundary_rate = lpr(lpr_term) + (bp_sign='ABOVE' ? +boundary_bp : -boundary_bp) × 0.01`
- `boundary_type='RATE'`：`boundary_rate = boundary_min_rate`

**权限节点利率边界（D3）**：每个节点在路由中携带 `[min_rate, max_rate]` 边界（由矩阵 `boundary_rate` 与全行业务硬边界 `ccr_product_rate_limit` 取交集）。审批人仅可在边界内调价，超出边界需上送上一级。

### 8.3 路由算法伪代码

```
function calcRoute(pricingItem, lprVersionId, asOfDate):
  product = select from ccr_product where product_code = item.productCode and status = ENABLED
  if product.isEmpty():
      return ERROR_ROUTE("产品未启用，请先在产品配置中心登记/启用")
  candidates = select from ccr_rate_matrix
    where business_big_type = item.businessBigType
      and new_or_existing = item.newOrExisting
      and customer_type = item.customerType          # GROUP 场景按集团金额档
      and amount_tier contains item.effectiveAmount  # 集团用批复总额度，见 4.2
      and term_tier contains item.termMonths
      and guarantee_type = item.guaranteeType
  candidates.sortBy(priority asc)                     # priority 升序，第一命中生效
  if candidates.isEmpty():
      return ERROR_ROUTE("未命中权限矩阵")
  matched = candidates.first()
  # 计算边界利率（BP 换算 / RATE 直取）
  boundaryRate = resolveBoundaryRate(matched, lprVersionId)
  # 校验申请利率是否在边界内
  if item.requestedRate < boundaryRate:
      return ERROR_ROUTE("申请利率低于权限下限，无权审批，需上会/上级审批")
  routeNodes = buildRouteNodes(item.productCode, matched, amount, enterpriseType)
  return { routeCode: matched.matrixNo, nodes: routeNodes, boundaryRate: boundaryRate }

function buildRouteNodes(productCode, matched, amount, enterpriseType):
  # 节点序列由"产品审批链路配置"（ccr_product_route，§8A.5②）决定，不再硬编码：
  route = select from ccr_product_route
    where product_code = productCode and status = PUBLISHED and effective_date <= asOfDate
  # 支行行长必经（全局强制 B13）：客户经理提交申请后，任何产品/任何链路
  # （含 DIRECT_VOTE 直接上会）审批首节点恒为支行行长，不受产品链路配置影响（§8A.5②）
  branchManager = "BRANCH_MANAGER"   # 支行行长节点（本机构 DEPT 范围，§5.4）
  if route.route_mode == DIRECT_VOTE:
      # 存款/保证金（D16b 一律直接上会）：先必经支行行长，再进入六人小组 + 行长决策
      return [branchManager, VOTING, PRESIDENT_DECISION]
  # CHAINED（贷款）：支行行长 + 起始节点 + 流程定义推导节点序列
  startNode = route.start_node_code or matched.startNodeCode
  if route.mandatory_vote or matches(route.vote_condition, amount, enterpriseType, item.requestedRate < boundaryRate):
      # 强制上会或命中上会条件：必经支行行长后链式上送，再必经六人小组 + 行长决策
      return buildChain(branchManager, startNode, matched.deptCode, [VOTING, PRESIDENT_DECISION])
  else:
      # 权限内终审：必经支行行长后可达 APPROVED_LEVEL（FINAL），无需上会
      return buildChain(branchManager, startNode, matched.deptCode, [APPROVED_LEVEL])
```

### 8.4 上会条件（D20）

- 申请利率低于节点边界利率 → 上会（进入六人小组）。
- **上会与否统一由产品审批链路配置驱动**（`ccr_product_route`，§8A.5②）：产品级配置 `mandatory_vote` / `vote_condition` 决定是否上会与上会条件，替代硬编码判定。
- **对公贷款金额分层强制上会**：按 5,000 万金额边界（**可配置**，产品链路 `vote_condition.amount_tier` 或矩阵 `amount_tier`）——金额 > 边界 → **必经六人小组表决 + 总行行长决策**，不论利率是否越界；金额 ≤ 边界且利率在权限内 → 权限内终审。规则来源《关于调整经营性贷款利率审批流程的议案》，正式实施配置为可维护参数。
- **国企/非国企分层**：对公贷款矩阵行按 `enterprise_type`（SOE/NON_SOE）区分，命中不同起始节点/归属部门/是否上会（配置化）。
- 委员会表决通过 → **必经总行行长决策**（B11/D20a）。
- 集团金额档次按集团综合授信批复总额度判定（B18）。

### 8.5 版本管理

| 配置 | 版本表 | 说明 |
|---|---|---|
| 产品目录 | `ccr_product` | 产品主数据（权威来源），新增/停用即生效，停用后新申请不可选 |
| 产品审批链路 | `ccr_product_route` | 产品 ↔ 审批链路（route_mode/强制上会/上会条件/行长决策），提交事务按产品命中 |
| LPR | `ccr_lpr_version` + `ccr_lpr_config`（按指标×产品） | 计划财务部维护（D12）；发布后新申请采用新版本，审批中申请沿用提交时冻结版本 |
| 权限矩阵 | `ccr_rate_matrix`（版本化字段 `version`） | 计划财务部维护草稿 → 配置复核人复核发布 |
| 产品边界 | `ccr_product_rate_limit` | 全行业务硬边界，不可被节点权限突破 |
| 规则集 | `ccr_rate_rule_set` + `ccr_rate_rule` | 版本化，冻结于提交事务 |

**LPR 维护（D12）**：LPR 日常发布、版本管理由**计划财务部**负责；权限矩阵由计划财务部与相关业务部门协同维护、配置复核人发布。

### 8.6 路由预览与一致性

- 提交前 `route-preview` 返回逐分项路由与边界，供客户经理确认。
- 提交时重算路由，以**提交事务内计算为准**（防配置漂移），并写入 `ccr_pricing_item.route_code/start_node_code/boundary_rate`。
- 审批中若矩阵/LPR 版本变更，**已冻结申请不受影响**（版本快照化，D11）。

## 8A. 参数配置功能详细设计

> 配置中心统一管理全部业务参数。原则：**维护与发布分离**（配置维护由 admin 维护草稿、配置复核人复核发布，§5.6 无独立"参数管理员"角色）、**版本化**、**提交时冻结**（新参数只影响新申请）、**变更全程审计**。对应表结构见 §10.3.15-17，UI 见 §12.13。

### 8A.1 配置域总览

| 配置域 | 维护角色 | 复核/发布角色 | 版本表 | 生效方式 | 对应 §12.13 页签 |
|---|---|---|---|---|---|
| LPR | admin（口径由计划财务部提供，统一状态机与发布流程 **admin 配置即可**） | 配置复核人 | `ccr_lpr_version` + `ccr_lpr_config`（按指标×产品） | 提交事务冻结 `lpr_version_id` | LPR 管理 |

| 产品配置（产品目录+审批链路） | admin | 配置复核人 | `ccr_product` + `ccr_product_route` | 提交事务按产品审批链路路由 | 产品配置 |
| 产品边界 | admin | 配置复核人 | `ccr_product_rate_limit` | 提交时硬边界校验 | 产品边界 |

### 8A.2 配置统一状态机与发布流程

```
DRAFT（草稿，admin）
  │ 提交复核 submitReview
  ▼
PENDING_REVIEW（待复核，配置复核人）
  ├─ 复核通过 publish → PUBLISHED（已发布，可再作废/停用）
  ├─ 复核驳回 reject → DRAFT（退回修改，附驳回意见）
  └─ 作废 obsolete → OBSOLETE（不可再用于新申请）
PUBLISHED ──停用 disable──▶ DISABLED
```

**发布规则**：
1. 发布前必做**完整性校验**（见各域校验规则），失败禁止发布。
2. 发布为**双人制**：维护人 ≠ 复核发布人（权限分离，`ccr:config:*:publish` 仅复核人）。
3. 发布操作需二次确认，写配置变更记录（before/after JSON + 操作人 + 时间 + 版本）。
4. 已发布版本只读（可查看/可作废，不可编辑）；修改必须基于新版本草稿。
5. **生效不追溯**：已冻结申请/快照不受新版本影响（D11）；生效时点写入 `effective_date`。
6. **发布后主动失效缓存**：清理该配置域在 Redis 中的版本/命中/模板 key（§3.6 缓存表），下次请求按新版本重建。

**配置变更记录（审计）**：`config_change_log`（配置域、版本号、变更字段、旧值/新值、操作人、操作类型、时间、状态）。审计人员可按域/时间查询全量变更历史。

### 8A.3 LPR 配置（按指标、按产品添加，不单行展示）

> **配置模型（用户拍板）**：LPR 参数**按指标（LPR 期限 1Y/5Y+）× 产品类型逐行添加**，不采用"一版一行只含 1Y/5Y 两值"的单行展示；**产品类型划分参照需求**（对公贷款 / 个人经营性贷款 / 存款各产品：对公定期 3/6/12/24/36 月、协定存款、通知存款 1/7 天、银票保证金、信用证保证金等）。配置统一状态机与发布流程按 §8A.2 由 **admin 配置即可**。

**字段**：
- `ccr_lpr_version`（版本头）：`version_no`（版本号，唯一）、`effective_date`（生效日）、`publish_date`、`publish_by`（计划财务部）、`audit_by`（复核人）、`status`（DRAFT/PENDING_REVIEW/PUBLISHED/OBSOLETE）、`remark`。
- `ccr_lpr_config`（LPR 明细，按指标×产品多行）：`version_id`、`lpr_term`（指标/期限：1Y / 5Y+）、`product_type`（产品类型，参照需求）、`lpr_value`（DECIMAL(9,6) 百分数）、`lpr_bp`（相对 LPR 的加点 BP，可空，按产品差异化阈值）、`remark`。

**校验规则**：
- 同一版本内 `(lpr_term, product_type)` 唯一；
- `lpr_value` 必须在合理区间（如 0.5%–8%，可配置上限）且精确到 0.05 的整数倍（LPR 报价规则）；
- `effective_date` ≥ 发布日，且不与已发布版本生效日冲突（同日仅一版）；
- 版本号唯一；发布时不得存在同指标同产品的更高生效日版本。

**生效机制**：提交事务按 `effective_date <= 提交日` 的**最新一版**取 `lpr_version_id` 冻结；BP 换算与产品边界校验按明细行 `(lpr_term, product_type)` 精确取值；展示当前生效版本（最新 PUBLISHED）。

**UI（§12.13 LPR 管理页签）**：版本列表（版本号、生效日、状态、操作）；进入版本后按"指标 × 产品"矩阵式明细维护（行=产品类型，列=1Y/5Y+，逐格添加/修改），**不单行展示 1Y/5Y 两值**；"＋新增 LPR 版本" → 保存草稿 → 提交复核 → 复核人列表"复核通过/驳回"→ 发布二次确认；历史版本只读。

### 8A.4 权限矩阵配置

**字段**（`ccr_rate_matrix`，含 `version` 版本化）：`matrix_no`、`business_big_type`（LOAN/DEPOSIT）、`new_or_existing`、`customer_type`（INDIVIDUAL/CORPORATE_SINGLE/GROUP）、`amount_tier`、`term_tier`、`guarantee_type`、`start_node_code`、`dept_code`、`boundary_type`（RATE/BP）、`boundary_min_rate`、`boundary_bp`、`bp_sign`（ABOVE/BELOW）、`lpr_term`（1Y/5Y）、`priority`、`status`、`effective_date`。

**校验规则**：
1. **命中唯一性（按链路分轨）**：`priority` 唯一性按**存款 / 贷款不同链路分别判定**——
   - **贷款链路**（LOAN）：同一组条件（业务大类+新存+客户类型+金额档+期限档+担保类型）内 `priority` 唯一（第一命中生效，防歧义）；按 §8.3 链式路由。
   - **存款链路**（DEPOSIT/MARGIN，D16b 一律直接上会）：不参与链式优先级命中，仅按**产品类型 + 期限档**唯一（同产品同期限不得重复配置），命中后直接判定"申请利率是否高于该产品期限上限 → 上会"。
2. **条件区间不重叠**：同条件下 `amount_tier`、`term_tier` 区间不得交叠。
3. **边界合法性**：`boundary_type=RATE` 时必须填 `boundary_min_rate`（且 ≥ 产品硬边界下限）；`boundary_type=BP` 时必须填 `boundary_bp`、`bp_sign`、`lpr_term`（无 RATE 值）；两者互斥。
4. **节点/部门有效**：`start_node_code` 存在且对应节点开启；`dept_code` 对应业务类型归属部门存在（D16a）。
5. **矩阵与产品边界一致性**：矩阵下限不得低于同产品 `ccr_product_rate_limit` 下限（硬边界不可被矩阵突破）。

**生效机制**：提交事务内逐分项调用路由引擎命中最新 PUBLISHED 矩阵；命中失败 → 阻断提交并提示"未命中权限矩阵，请联系计划财务部配置"。

**模拟验证（发布前必做）**：admin 可输入一组申请条件（金额/期限/担保/新存/客户类型/业务类型）→ 系统输出：命中矩阵、路由节点序列、边界利率 → 人工核对后再提交复核。模拟结果记录留痕。

**UI**：矩阵列表（条件列 + 边界 + 优先级 + 状态）；新增/编辑表单（条件选择器 + 边界配置联动：选 BP 显示 bp_sign/bp/lpr_term，选 RATE 显示 min_rate）；"模拟路由"按钮；优先级排序；复核发布流程同 8A.2。

### 8A.5 产品配置（产品目录 + 产品审批链路配置化）

> **产品配置化（业务方确认）**：**所有产品统一在配置中心登记**（产品目录 `ccr_product`），并**为每个产品配置其审批链路**（`ccr_product_route`）。产品新增/停用、是否上会、审批链路节点序列**不写死在代码**，均由配置驱动；申请页产品下拉、LPR 明细的产品类型、权限矩阵、产品边界统一以产品目录为**权威来源**。配置统一状态机与发布流程按 §8A.2 由 **admin 配置即可**。

**① 产品目录 `ccr_product`（产品主数据）**

**字段**：`product_code`（产品编码，唯一）、`product_name`、`business_big_type`（LOAN/DEPOSIT）、`product_category`（产品线：对公贷款/个人经营性贷款/对公定期 3/6/12/24/36 月/协定存款/通知存款 1/7 天/银票保证金/信用证保证金…）、`customer_type`（适用客户类型）、`currency`、`default_min_rate`/`default_max_rate`（产品默认利率区间，供申请页默认值）、`default_min_term_months`/`default_max_term_months`（默认期限范围）、`status`（ENABLED/DISABLED）、`effective_date`、`remark`。

**校验规则**：
- `product_code` 全局唯一；产品编码一经启用不可修改（仅可停用）；
- 产品停用后：**新申请不可选**该产品，在途审批/已冻结申请不受影响（D11）；
- 产品目录为"存款产品/贷款产品"等字典项的**权威来源**，字典项与产品目录保持一致（§8A.9）；
- 产品被申请/矩阵/LPR 引用时不可删除（仅可停用）。

**② 产品审批链路配置 `ccr_product_route`（产品 ↔ 审批链路）**

**字段**：`product_code`、`business_big_type`、`flow_key`（Warm-Flow 流程定义 key，空=默认流程）、`start_node_code`（起始节点，空=按矩阵推导）、`route_mode`（`CHAINED` 链式逐级 / `DIRECT_VOTE` 直接上会）、`mandatory_vote`（BOOLEAN 是否强制六人小组）、`president_decision`（BOOLEAN 是否必经行长决策）、`vote_condition`（JSON 上会条件：金额档 `amount_tier`、`enterprise_type`（SOE/NON_SOE）、利率越界等，命中即上会）、`priority`、`status`、`effective_date`、`remark`。

**校验规则**：
- **支行行长节点恒必经（B13，全局强制，非可配置）**：客户经理提交申请后，无论 `route_mode`（CHAINED/DIRECT_VOTE）与任何链路配置，**审批首节点恒为支行行长**（系统固定注入，产品链路配置不含支行行长开关）；`DIRECT_VOTE` 表示支行行长之后直接进入六人小组 + 行长决策，不再走链式层级；
- 同产品 `(product_code, effective_date)` 唯一；同一时点仅一版 PUBLISHED 生效；
- `route_mode=DIRECT_VOTE`（存款/保证金，D16b 一律上会）：`start_node_code` 置空，命中后**先必经支行行长，再进入六人小组 + 行长决策**，不参与链式优先级；
- `route_mode=CHAINED`（贷款）：`start_node_code` 必填，节点序列由矩阵 + 流程定义推导（§8.3）；
- `mandatory_vote=true` 时（如对公贷款金额 >5,000 万）**必经六人小组 + 行长决策**，与利率是否越界无关；
- `flow_key` 存在且为已发布流程；`start_node_code` 存在于该流程节点（§11.11）。

**生效机制**：提交事务逐分项调用路由引擎：按 `product_code` 命中最新 PUBLISHED 产品链路 → 判定 `route_mode` / `vote_condition` / `mandatory_vote` → 生成完整执行链与“是否上会”；与权限矩阵命中（§8A.4 `ccr_rate_matrix`）取交集后，一次性冻结 `product_route_id/product_route_version/route_mode/route_chain_json/node_permission_json/president_required/flow_key/hard_boundary_rate`。`route_code` 继续记录提交利率下计算得到的预计终审节点。普通审批逐级上送、节点调价、表决通过后的行长步骤只消费冻结计划，配置变更仅影响新提交（D11）。

**UI（§12.13 产品配置页签）**：产品目录 Tab（产品编码/名称/业务大类/产品线/状态/操作）＋ 产品审批链路 Tab（产品 → 链路：route_mode、起始节点、强制上会开关、行长决策开关、上会条件 JSON 可视化构建器、模拟路由预览）＋ 产品边界 Tab（利率硬边界）。复核发布流程同 8A.2。

**③ 产品利率边界 `ccr_product_rate_limit`（全行业务硬边界，保留）**

**字段**：`product_code`（关联产品目录）、`product_name`、`business_big_type`、`currency`、`min_rate`、`max_rate`、`min_term_months`、`max_term_months`、`status`。

**校验规则**：
- `min_rate < max_rate`；范围不得随版本被矩阵突破（**全行业务硬边界**，任何节点调价不得越界）；
- 同产品同币种同期限范围唯一；`product_code` 必须存在于产品目录且为启用产品。

**生效机制**：提交校验、审批调价校验、路由边界校验均读取；变更即时生效（但已冻结申请不受影响）。

### 8A.6 利率规则集配置

**字段**（`ccr_rate_rule_set`：`set_no`、`set_name`、`version`、`status`；`ccr_rate_rule`：`rule_set_id`、`rule_code`、`condition`（JSON 条件）、`action`（JSON 动作，如路由覆盖/边界覆盖）、`priority`、`enabled`）。

**校验规则**：规则条件 JSON 合法；同集内 `rule_code` 唯一；优先级不重复；动作引用的节点/边界存在。

**生效机制**：提交事务冻结 `rate_rule_set_id`；规则在路由计算前按优先级应用（条件命中则调整路由/边界）。

### 8A.7 跟踪策略 / 阈值 / 提醒配置

**字段**：
- `ccr_tracking_policy` + `_version`：`policy_code`、`policy_name`、`version`、`evaluate_frequency`（MONTHLY/WEEKLY）、`evaluate_cron`、`status`。
- `ccr_tracking_threshold`：`policy_version_id`、`metric_code`、`warning_level`（GREEN/YELLOW/RED）、`threshold_min`（如 80%）、`threshold_max`、`action`（NOTIFY/ESCALATE）。
- `ccr_notification_rule`：`rule_code`、`trigger_event`（WEEKLY/MONTHLY/ON_THRESHOLD）、`channel`（APP/PC）、`template`（含占位符）。
- `ccr_notification_recipient`：`rule_id`、`recipient_role`（CUSTOMER_MANAGER/BRANCH_MANAGER/DEPT_MANAGER/VOTE_MEMBER）、`resolve_mode`（STATIC/DYNAMIC）。

**校验规则**：阈值区间不交叠（GREEN < YELLOW < RED 有序）；RED 级必须配置 `ESCALATE` 动作；提醒模板占位符与字段匹配；`evaluate_cron` 合法。

**生效机制**：**下一评估周期生效**（当月生效不影响本月已生成计划）；已生效策略版本随计划快照。

### 8A.8 数据集 / 字段 / 指标配置

- `ccr_dataset_definition` + `ccr_dataset_version`：数据集编码、名称、来源表、批次策略、时效天数（`freshness_days`）、数据日期字段。
- `ccr_field_definition`：字段名、字段类型、来源字段、是否脱敏、展示名称、排序、是否必填、是否参与勾稽。
- `ccr_metric_definition`：指标码、名称、`metric_scope`（PUBLIC/PRIVATE_SELF/RELATED/GROUP/GROUP_MEMBER）、`value_type`（AVG_BALANCE/INCOME/CONTRIBUTION_AMOUNT）、单位、来源表字段、展示名、排序。
- `ccr_source_mapping`：数据源编码 → 落地表、批次号、时效配置、是否参与提交校验（**数据源即数据仓库直接推送的业务库落地表，本系统直接读表，不经接口，§2.4/§9.1**）。

**校验规则**：字段/指标码唯一；`metric_code` 与承诺类型映射一致（PC_INDICATOR_DEF 对应）；勾稽必填指标不得缺失定义。

**生效机制**：展示/校验即时生效；已冻结快照不受影响（D11）。

### 8A.9 字典管理

字典项（`dict_type` + `dict_value/label`）：承诺类型（12 项，含"其它"手工项）、担保类型（8 项）、客户性质、企业性质、客户类型、业务类型、贷款期限档、存款产品、五级分类、内部信用等级、预警级别、消息类型、审批状态、决议状态、投票类型等。

- 新增/停用字典项即时生效；**已提交申请沿用字典值快照**（展示历史值不随字典变化）。
- 字典项变更记录审计。

## 9. 数据与数据支撑

### 9.1 数据来源与边界

> **全部基本数据由数据仓库按 §10.2⑥ 落地表结构加工后直接推送到业务库对应表**，本系统**直接读表访问，不通过接口**；本系统对这些数据一律只读，做展示、勾稽、快照冻结（§2.4）。

| 数据 | 来源 | 本系统处理 |
|---|---|---|
| 客户基本信息 | 数仓落地 `caps_corp_cust_basic_info` / `caps_indv_cust_basic_info` | 只读 + 申请快照 |
| 本行融资 | `dw_loan_contract_snapshot`（原 `dw_own_financing_snapshot` 已并入，2026-08-11） | 只读，原利率来源 |
| 他行融资 | 征信 + 人工/Excel/OCR 补录 | 补录分离存储 |
| 抵押/质押 | `dw_mortgage_snapshot` | 只读 |
| 担保人 | `dw_guarantor_snapshot` | 只读 |
| 当前贡献度 | `dw_contribution_metric` | 只读 + 勾稽校验 |
| 征信 | `dw_credit_report_snapshot` / `dw_credit_financing_detail` | 只读 |
| 机构达成 | `dw_org_performance_snapshot` | 只读（分子） |
| 机构维度 | `dw_org_dim` | 只读；机构名称/层级展示（F8 申报支行）、`sys_dept` 编码对齐 |
| 借据核验 | `dw_loan_note_snapshot` / `dw_credit_financing_summary` | 只读，两级核验 |
| 集团授信/成员额度 | `dw_group_credit_snapshot` / `dw_group_member_credit_snapshot` | 只读，金额档判定 |

### 9.2 当前贡献度口径（D13/D15/D21）

- 当前贡献度由数仓提供（`dw_contribution_metric`，纵表指标），本系统只读展示并做勾稽。
- 指标口径：`metric_scope`（PUBLIC / PRIVATE_SELF / RELATED / GROUP / GROUP_MEMBER）、`value_type`（AVG_BALANCE / INCOME / CONTRIBUTION_AMOUNT）、`metric_code`。
- **综合贡献总额**：由数仓作为独立指标行（`metric_code='TOTAL_CONTRIBUTION'`，`value_type=CONTRIBUTION_AMOUNT`，单位万元）随 `dw_contribution_metric` 纵表**一并落表推送**，本系统直接读表取值；**勾稽比对基准**（§6.3）。（数据接入统一走落地表直接读表，不经接口返回。）
- **勾稽校验**：**参与勾稽的明细**（排除 `RATIO` 存贷比等派生无金额指标）加总 vs 综合贡献总额差额校验（0 通过 / 容差内预警 / 超容差或必填指标缺失阻断，默认阻断提交）。
- 拟达成贡献度不做勾稽、不设时效（D15）；承诺类型含"其它"（客户经理手工录入，数仓无该指标）——**不参与达成跟踪、不计入机构达成率分母（D19）**，详见 §6.4。

### 9.3 提交前校验清单（提交事务内）

1. 必填字段完整性校验。
2. 数据时效校验（快照 `data_dt` ≤ 配置时效）。
3. 贡献度勾稽校验。
4. 利率边界校验（申请利率 ∈ [产品硬边界, LPR±BP 矩阵边界]）。
5. 担保/合同/账户关联完整性校验。
6. 集团场景：成员额度与集团总额度校验（只读，不调剂）。

### 9.4 外部数据时效管理

- 外部数据快照携带 `data_dt`（数据日期）、`etl_md5`（ETL 批次指纹）、批次号。
- 时效配置在 `ccr_source_mapping`/`ccr_dataset_definition` 中按数据源配置（默认 3 个自然日）。
- 提交前校验所有绑定数据源时效；超时阻断并提示"数据源数据日期过期，请联系数据中心刷新"。

### 9.5 不可变快照（D11）

**快照绑定时机**：申请提交事务内冻结 `ccr_snapshot_bundle`（`bundle_no` 唯一），绑定 `snapshot_bundle_id` 到申请与各分项；`uk_snapshot_application(application_id)` 保证一申请最多一个快照包。

**快照内容**：客户基本信息、本行/他行融资、担保、贡献度指标、集团/成员额度、借据核验底稿（`dw_loan_note_snapshot` 提交时刻数据）。

**快照读取规则（D11/B15）**：
- 审批中、历史审批、导出、决议核验**一律读快照**，不实时查数仓。
- **不提供"刷新外部数据"按钮**（已按 PRD B11 从 demo 移除）。
- 承诺跟踪例外：使用审批后数仓**最新成功批次**（B15）。

### 9.6 数据中心功能（F8）

- 批次落地监控（**动态清单，#42**）：落地表清单实时查 `information_schema.TABLES`（`dw_`/`caps_` 前缀、`table_type='BASE TABLE'`），排除弃用表 `dw_org_dim`，表名正则白名单 `^[a-zA-Z][a-zA-Z0-9_]*$` 防注入；已知表按登记顺序展示（含中文说明，顺序即看板顺序），动态新增表按字母序追加、说明回退表名；列：**数据表 / 数据源 / 最新数据日期 / 批次行数 / 落地时间**（`dw_org_performance_snapshot` 特判 `snapshot_ts` 落地时间列，其余表该列无则置空）。
- 质量校验结果：每批校验规则命中情况（`ccr_snapshot_quality_result`）。
- 差异确认：质量校验预警项的确认与责任人。
- 时效看板：各表最新数据日期 → 计算 `delayDays`（超 `dataStaleDays` 默认 3 天为 `STALE`，否则 `OK`，无数表亦 `STALE`）；接口返回 `table/sourceName/latestDataDt/delayDays/thresholdDays/status`。

> 已实现工程 DDL 位置：`G:\project\ccr\db\`（01-08 顺序执行）。本设计沿用其命名与字段约定，并按下文修正项调整。已实现系统数据库共 **69 张业务/落地表 + 77 个字典项**（`README.md` 验证结果）。

### 10.1 命名与公共字段约定

| 约定 | 规则 |
|---|---|
| 前缀 | `ccr_*` 业务表；`caps_*`/`dw_*` 数仓落地；`flow_*` Warm-Flow 引擎表 |
| 主键 | 雪花 ID（`BIGINT`） |

| 利率 | `DECIMAL(9,6)`，单位**百分数**（`3.200000` = 3.20%） |

#### 10.3.4 `ccr_pricing_item_contract_rel` / `ccr_pricing_item_deposit_rel`

- 分项-合同：`pricing_item_id`、`contract_no`（拟签合同用业务标识 `PENDING_<uuid>`）、`contract_type`（EXISTING/PENDING）、`settle_flag`（审批后回填）。
- 分项-账户：`pricing_item_id`、`account_no`（拟开户 `PENDING_<uuid>`）、`account_type`（EXISTING/PENDING）、`settle_flag`。
- 草稿保存沿用逻辑删除后重建语义。两表均由 MySQL 生成 `active_application_id=CASE WHEN del_flag='0' THEN application_id ELSE NULL END`；活动合同以 `(active_application_id, contract_business_key)` 唯一，活动账户以 `(active_application_id, deposit_account_hash)` 唯一。历史行的生成列为 NULL，可保留多次保存版本；拟开户账户哈希为空时延续多分项语义。

#### 10.3.5 担保三表

- `ccr_guarantee_package`：`application_id`/`pricing_item_id`、`package_no`、`guarantee_type`、`guarantee_amount`、`guarantee_status`。
- `ccr_guarantee_measure`：`package_id`、`measure_type`（MORTGAGE/PLEDGE/GUARANTEE/CREDIT）、`guarantor_id`、`guarantor_name`、`collateral_id`、`collateral_no`、`collateral_value`、`evaluation_value`、`evaluation_org`、`cert_no`、`registered_date`。
- `ccr_note_guarantee_rel`：`note_no`（借据号）、`measure_id`，多对多明细（D11 借据核验沿此读取担保一致性）。

> **担保方式收敛（#76，2026-08-12）**：前端担保方式下拉收敛为 **4 种**（抵押 MORTGAGE / 质押 PLEDGE / 保证 GUARANTEE / 信用 CREDIT，`dict.ts` `GUARANTEE_TYPES`）；存量措施编码（如 `BILL_MARGIN` 银票保证金、信用证保证金、存单质押、保证金质押）仍经 `GUARANTEE_NAME_MAP` **中文回显**、不再作为新下拉可选项；`measure_type` 字段本身不受限（后端 `CcrGuaranteeMeasure` 承载存量编码），与前端主类型解耦。

#### 10.3.15 承诺跟踪（关键表）

- `ccr_commitment_plan`：`plan_no`、`application_id`、`resolution_id`、`customer_id`、`plan_status`（ACTIVE/CLOSED）、`evaluate_cron`（月报频率）、`next_evaluate_time`、`start_date/end_date`。
- `ccr_commitment_metric`：`plan_id`、`metric_code`、`metric_name`、`metric_scope`、`baseline_amount`（DECIMAL(20,4) 承诺基线=分子）、`actual_amount`（最新当前贡献度实际值=分母）、`achievement_rate`（达成率）、`gap_amount`、`data_dt`；**"其它"项**：`metric_code='OTHER'`，`baseline_amount/actual_amount/achievement_rate/gap_amount` 均空，新增 **`commitment_desc`**（录入目标描述，金额或文本）与 **`track_desc`**（跟踪手工描述，textarea，留痕），不做数值达成率计算（见 §6.4）。
- `ccr_tracking_policy` / `_version`：策略 + 版本（版本化配置）。
- `ccr_tracking_threshold`：`policy_version_id`、`metric_code`、`warning_level`（GREEN/YELLOW/RED）、`threshold`（如达成率 < 80% 为 RED）、`action`（NOTIFY/ESCALATE）。
- `ccr_notification_rule`：`rule_code`、`trigger_event`（WEEKLY/MONTHLY/ON_THRESHOLD）、`channel`（APP/PC）、`template`。
- `ccr_notification_recipient`：`rule_id`、`recipient_role`（CUSTOMER_MANAGER/BRANCH_MANAGER/VOTE_MEMBER）、`resolve_mode`（STATIC/DYNAMIC）。
- `ccr_notification_log`：`message_key`（唯一去重）、`send_channel`、`status`、`retry_count`、`send_time`。

#### 10.3.16 `ccr_metric_definition`（指标定义）

`metric_code`、`metric_name`、`metric_scope`（PUBLIC/PRIVATE_SELF/RELATED/GROUP/GROUP_MEMBER）、`value_type`（AVG_BALANCE/INCOME/CONTRIBUTION_AMOUNT）、`unit`（万/户）、`source_table`、`source_field`、`display_name`、`default_order`。

## 11. API 设计

### 11.1 通用约定

- 前缀 `/api/v1`；REST 风格；返回统一 `{code, message, data, traceId}`。
- 认证：Sa-Token `token`（Header `Authorization`）；接口鉴权：角色码 + 数据权限；**会话活跃超时 2 小时（idle timeout，`activeTimeout=7200`），无操作自动失效返回 401，须重新登录（§5.1）**。
- 幂等：写接口支持 `Idempotency-Key` 请求头 + 服务端 `version_no` 乐观锁双保险。
- 错误码分段：`10xxx` 参数、`11xxx` 状态机、`12xxx` 校验、`13xxx` 工作流、`14xxx` 表决、`15xxx` 决议、`16xxx` 快照、`17xxx` 承诺、`18xxx` 配置。

### 11.2 申请域

| 方法 | 路径 | 说明 |
|---|---|---|
| POST | `/api/v1/application` | 新建申请草稿 |
| GET | `/api/v1/application/{id}` | 申请详情（PC 编辑/审批详情） |

- 操作：逐项"同意本项"（primary）；底部"一键通过审批"（primary）+"否决"（danger，原因必填）。

**委员会"分项决策"（匿名）**：
- 表头"每个担保分项分别表决'同意/否决'（与总行行长分项决策同口径）；表决意见匿名留痕，无权修改提交利率"。
- 表格：`担保方式 | 金额（万元）| 申请利率 | 六人票数（approve:oppose）| 当前状态 | 操作`；本人已表决行显示"同意/否决"色标 + "本人意见：{comment}"；未表决行两个按钮"同意/否决"。
- 顶部本人状态徽标："已表决 X / N 项"或"已完成"。
- 匿名 notice："审批小组成员无权修改提交利率；提交后不可修改，后台自动累计 6 票，达到 ≥4 票判通过，表决意见以匿名模板留痕。"
- 操作："一键审批（全部同意）"+"一键否决（全部）"。

**行长"总行行长决策"**：
- 摘要区（4 格 `approval-reference`）：六人审批汇总（如"6:0 通过"）、通过比例（%）、最终建议利率、分项票数（approve:oppose，逐担保）。
- "六人小组表决意见（匿名）"折叠块：逐分项展开，委员以**委员A—F随机代称**展示"同意/否决 + 意见"；默认收起。
- "分项决策"表：`担保方式 | 金额 | 申请利率 | 六人票数 | 当前状态 | 操作`；逐项"同意/否决"；底部"一键同意全部"/"一票否决全部"。
- 提示："六人审批汇总、匿名表决意见和全链路轨迹仅在本节点显示；汇总结果仅行领导可见"。

### 12.12 移动端（仅审批，行内 App 容器）

底部 Tab：**工作台 / 待办 / 历史 / 消息 / 我的**。

| Tab | 内容 |
|---|---|
| 工作台 | 页眉（"移动工作台"）+ 统计卡（待办数/待表决/待决策）+ 快捷入口（利率申请→PC 引导、审批、历史） |
| 待办 | 审批任务列表（分项级：客户 + 担保方式 + 金额 + 申请利率 + 待办类型）；普通节点可调价，委员会仅投票，行长决策 |
| 历史 | 历史审批/历史申请合并视图（只读 + 轨迹） |
| 消息 | 审批流转/审批结果/预警提醒/系统通知 |
| 我的 | 当前用户、岗位、机构、版本、退出 |

**审批详情（移动端）**：复用 PC 数据模型（12.7 全部卡片）响应式呈现；决策区：
- 普通节点：审批利率输入（边界提示）+ 通过/否决；
- 委员会：同意/否决（匿名，提交后锁定）；
- 行长：同意/一票否决。

**两端同步说明（demo 原文）**：
- 节点调价与权限校验：普通审批节点可修改利率并只选择通过/否决；利率低于本节点权限下限时，工作流携带调整结果自动上送。
- 客户历史与支行履约双视角：存量客户查看历次利率优惠、任务和承诺兑现；新增客户改为展示申报支行近 12 个月贡献度达成率。
- 存款与贷款审批详情分口径展示：存款只展示客户基础信息与存款利率提升申请（含产品标准上限比对）；贷款展示担保切分、融资情况与贡献承诺等完整要素。
- **被拒流程关联重提**：表决未达到 ≥4 票时，客户经理可从原决议重新发起，自动带入客户、担保利率和贡献承诺，并串联两轮流程。

**移动端不提供**：新建申请、融资录入、担保/附件上传、承诺录入、数据中心、参数配置（B01/D10）。

### 12.13 参数配置页（PC，管理角色）

> 配置页仅对 admin / 配置复核人可见（§5.6 权限分工）；维护与发布双人制（admin 默认持有全部权限码，可行使维护与发布）。各页签字段与校验规则见 §8A，本节给出页面布局与控件规格。

**页面框架**：左侧"配置域"导航（LPR 管理 / 权限矩阵 / 产品配置 / 产品边界 / 利率规则 / 跟踪策略 / 数据集 / 字典 / 展示模板），右侧主区 = 页签头部（标题 + 描述 + 状态徽标 + 操作按钮）+ 内容区。

**通用状态徽标**：`草稿`（灰）→ `待复核`（橙）→ `已发布`（绿）→ `已停用`（灰）/`已作废`（红）。

**① LPR 管理页签（按指标 × 产品类型，不单行展示）**
- 列表列：版本号 | 生效日 | 发布人 | 复核人 | 状态 | 操作（编辑/提交复核/查看/作废）。
- 新增/编辑版本表单（`form-grid` 两栏）：
  - 版本号（文本，唯一，如 `LPR-2026-08-001`）
  - 生效日期（date）
  - 发布说明（textarea）
- **明细维护（进入版本后）**：按"指标 × 产品"矩阵逐格添加/修改——行=产品类型（参照需求，如对公贷款/个人经营性贷款/对公定期/协定存款/通知存款/银票保证金/信用证保证金），列=LPR 期限（1Y / 5Y+），每格填 `lpr_value`（数字 %，`step=0.05`）与可选加点 `lpr_bp`。**不采用单行 1Y/5Y 两个值展示**。
- 校验提示：LPR 为 0.05 整数倍；生效日 ≥ 发布日；同日仅一版；同版本同产品同期限不重复（提交时校验报错）。
- 操作流：`保存草稿` → `提交复核` → 复核人列表进入待复核 → `复核通过`（发布，二次确认弹层显示生效日与影响范围）或 `复核驳回`（附意见）。配置统一状态机与发布流程由 **admin 配置即可**（§8A.2）。

**② 权限矩阵页签**
- 工具栏：条件筛选（业务大类/新存客/客户类型/担保类型/状态）+ `＋ 新增矩阵` + `模拟路由`。
- 列表列：矩阵号 | 业务大类 | 新存客 | 客户类型 | 金额档 | 期限档 | 担保类型 | 起始节点 | 归属部门 | 边界（`≥3.00%` 或 `LPR1Y+35BP`）| 优先级 | 状态 | 操作。
- 新增/编辑表单：条件选择器（下拉联动）+ 边界配置（`boundary_type` 切换 RATE/BP 两组控件：RATE 显示"边界利率"输入；BP 显示"BP 值/符号/基准 LPR 期限"下拉）+ 起始节点下拉（含归属部门）+ 优先级数字。
- `模拟路由`弹层：输入申请条件 → 输出命中矩阵、路由节点序列、边界利率 → `复制到草稿`/`核对后提交复核`。
- 优先级调整：行内上移/下移或优先级数字编辑；同条件优先级唯一校验。

**③ 产品配置页签**（产品配置化，§8A.5）
- **产品目录 Tab**：列表列 = 产品编码 | 产品名称 | 业务大类 | 产品线 | 适用客户类型 | 币种 | 状态 | 操作（编辑/启用|停用/查看）。
  - 新增/编辑表单：产品编码（唯一、启用后禁改）、产品名称、业务大类、产品线下拉、适用客户类型、币种、默认利率区间、默认期限范围、生效日。
  - 停用校验：被申请/矩阵/LPR 引用时不可删除（仅可停用）；停用后新申请产品下拉不可选。
- **产品审批链路 Tab**：列表列 = 产品编码 | 产品名称 | 路由模式（链式/直接上会）| 起始节点 | 强制上会 | 行长决策 | 上会条件 | 状态 | 操作。
  - 编辑表单：产品下拉（关联产品目录）、route_mode 切换（链式→起始节点选择器；直接上会→隐藏起始节点并提示"支行行长必经，命中即直接上会"）、强制上会开关、行长决策开关、上会条件可视化构建器（金额档/企业性质/利率越界）。
  - `模拟路由`按钮：输入申请条件 → 输出该产品命中链路与节点序列，人工核对后提交复核。
- 复核发布流程同 8A.2（admin 配置即可）。

**④ 产品边界页签**
- 列表列：产品编码 | 产品名称 | 业务大类 | 币种 | 最低利率 | 最高利率 | 期限范围 | 状态 | 操作。
- 编辑表单：产品（下拉复用产品目录）、币种、min/max 利率（%）、期限范围（月）；校验 min<max 且不得低于硬边界；产品编码必须为启用产品。
- 提示条：**"全行业务硬边界，任何节点调价/矩阵边界不得突破"**。

**⑤ 利率规则页签**
- 规则集列表（set_no/set_name/version/状态）+ 规则明细（rule_code/条件 JSON 预览/动作/优先级/enabled）。
- 编辑表单：条件与动作以可视化构建器（字段选择 + 运算符 + 值）为主、JSON 高级编辑为辅。

**⑥ 跟踪策略页签**（三个子页签：策略 / 阈值 / 提醒）
- 策略：策略版本列表（编码、名称、评估频率、cron、状态）；编辑表单含 `evaluate_cron` 与频率。
- 阈值：`指标 | 达成率区间 | 预警级别(GREEN/YELLOW/RED) | 动作(通知/升级)`；级别用彩色徽标；区间不交叠校验；RED 必须选"升级"。
- 提醒：规则列表（触发事件/渠道/模板）+ 提醒对象（角色下拉 + 解析模式 + `预览解析结果`按钮弹层显示实际收件人）。

**⑦ 数据集页签**
- 数据集列表（编码、名称、来源表、时效天数、状态）；字段明细（字段名/类型/来源/脱敏开关/展示名/排序/勾稽标记）；指标明细（指标码/名称/scope/value_type/单位/来源）。

**⑧ 字典管理页签**
- 字典分组（承诺类型/担保类型/客户性质/企业性质/贷款期限档/存款产品/五级分类/信用等级/预警级别/消息类型/审批状态/决议状态/投票类型 等）；每分组列：字典值 | 标签 | 排序 | 状态 | 操作；支持停用（已提交申请沿用历史值快照）。

**⑨ 展示模板页签**
- `ccr_display_schema` 列表（模板编码、名称、适用页面、字段顺序、状态）；编辑用字段拖拽排序。

## 13. 承诺跟踪设计

### 13.1 承诺基线（拟达成贡献度）

- 录入于申请（`ccr_application_commitment`），随申请存档、审批期间不变（D15）。
- 申请级承诺字段包含指标、目标类型、基线值、目标值、单位、指标范围、成员客户号、手工描述与 `end_date`（承诺完成截止日期）；`db/19_application_commitment_end_date.sql` 用于存量环境幂等补列。
- 指标口径与当前贡献度**同码对齐**（`ccr_metric_definition`），便于分子/分母可比；**例外：承诺类型"其它"无对应数仓指标**（客户经理手工录入，见 §6.4），**目标可为金额或描述文本（`commitment_desc`）**，不参与数值达成评估与机构达成率分母，**以客户经理手工描述跟踪**。
- 集团场景支持成员级分配（`ccr_commitment_member_alloc`），聚合到集团与成员两层。

### 13.2 达成评估

**公式**（B 类口径）：
```
达成率 = 数仓当前贡献度实际值（最近批次，同指标码，客户级）÷ 承诺基线（跨申请/分项按指标码加总）
落差 = 基线 − 实际值
```

> **排除项**：承诺类型"其它"（客户经理手工录入、数仓无实际值）**不计入**达成率/落差计算，不参与预警升级与月报提醒（见 §6.4）；其跟踪内容由客户经理**手工描述**（`ccr_commitment_metric.track_desc`，textarea 留痕），以文本替代数值对比。

**评估触发**：
- 定时任务按 `evaluate_cron`（默认每月 1 日 01:00）执行。
- 手动触发（`/api/v1/commitment/plan/{id}/evaluate`）。
- 数仓新批次落地成功事件触发（Outbox 消费）。

**结果落库**：`ccr_tracking_evaluation`（周期、指标、实际值、达成率、落差、预警级别、评估时间、数据日期）。

### 13.3 阈值与升级（全部配置化）

- `ccr_tracking_threshold`：按 `metric_code` + 达成率区间配置 `warning_level`（如 ≥100% GREEN / 80–100% YELLOW / <80% RED）。
- RED 级别自动**升级**：客户经理 → 支行行长 → 审批小组（动态解析，可配置）。

### 13.4 提醒与月报

- 提醒：`ccr_notification_rule` + `ccr_notification_recipient`（动态角色解析），渠道 APP/PC。
- 月报：按机构聚合已通过审批申请的承诺与达成（D19），推送至支行行长与部门。
- 幂等：`message_key` 唯一，同一周期同机构同客户不重复推送。

### 13.5 与审批的边界

- 承诺跟踪**不影响**已审批分项的利率决议（决议已签发不可回溯变更）。
- 跟踪结果仅用于**预警与管理考核**，不做自动调息。

## 14. 状态设计（汇总）

### 14.1 申请状态（§7.9 状态机）

`DRAFT → SUBMITTED → ROUTING → APPROVED_LEVEL / VOTING → COMMITTEE_PASS → PRESIDENT_DECISION → FINAL | VETOED | REJECTED`，另含 `RETURNED`（重提后原申请终态，不可回 DRAFT）。

### 14.2 分项状态

`PENDING → ROUTING → APPROVED / VOTING → COMMITTEE_PASS / PRESIDENT_DECISION → FINAL / VETOED / REJECTED`。

### 14.3 决议状态

`ISSUED → CONTRACT_PENDING → EXECUTED`，可 `VOID`（作废）。

### 14.4 表决批次状态

`OPEN → CLOSED → COUNTED`；结果 `PENDING / PASS / FAIL`。

### 14.5 快照状态

`FROZEN`（提交冻结，不可变）；异常 `RELOADED`（仅归档可读，不参与审批）。

### 14.6 承诺计划状态

`ACTIVE → CLOSED`（到期/结清）；评估 `NOT_EVALUATED / GREEN / YELLOW / RED`。

### 14.7 状态流转约束

- 所有状态流转记录审计（`ccr_approval_action`：`from_status / to_status / action_by / action_time / comment`）。
- 非法流转由状态机校验拦截（错误码 `11xxx`）。
- 终态（FINAL/VETOED/REJECTED/RETURNED）不可回退（B6/B14）。

## 15. 安全、审计与并发

### 15.1 安全

| 项 | 设计 |
|---|---|
| 认证 | 内部工作平台统一认证/SSO（B19）；Sa-Token 会话；演示环境内置测试账号；**会话活跃超时 2 小时自动退出（`activeTimeout=7200`，连续 2 小时无操作失效，须重新登录，§5.1）** |
| 鉴权 | 角色码 + 数据权限（机构/集团/成员/本人任务）三层；接口校验 |
| 密码 | 加盐哈希（演示默认 `admin`/`123456` 首登改密） |
| 脱敏 | 证件号、手机号、地址展示脱敏；敏感字段传输加密 |
| 投票匿名 | `voter_user_id_cipher`/`voter_user_hash` 匿名编码；审计密钥分离保存 |
| 防重放 | 接口幂等键 + 乐观锁 + 唯一约束 |
| 日志 | 操作日志（登录/提交/审批/表决/决策/配置变更/导出）；异常日志分级 |
| 防注入 | MyBatis 参数化；上传白名单 + 大小限制；XSS 过滤 |

### 15.2 审计

- 全程留痕：申请创建/编辑/提交、路由计算、快照冻结、节点审批、投票（含实际投票人）、计票、行长决策、决议签发/回填/核验、配置发布、导出。
- 审计查询需授权（`audit_*` 权限），投票实际人员仅审计可见。
- 配置变更记录（before/after JSON + 版本）。

### 15.3 并发

| 场景 | 手段 |
|---|---|
| 同一申请并发提交 | `id + status=DRAFT + version_no` 条件更新抢占提交所有权；失败后 `SELECT ... FOR UPDATE` 当前读返回已提交结果或版本/状态冲突；快照表以 `application_id` 唯一键兜底 |
| 同一分项并发审批 | 分项 `version_no`；重复审批幂等 |
| 一人一票 | `ccr_ballot` 唯一约束 + 应用层事务 |
| 计票并发 | 计票加锁（`ccr_vote_result` 唯一约束，PASS/FAIL 原子更新） |
| 行长决策并发 | 分项状态校验（仅 COMMITTEE_PASS 可决策）+ 唯一结果 |
| 提交事务并发 | 条件更新 CAS 抢占；失败方锁定当前读并等待赢家提交，业务副作用仅由赢家执行 |
| Outbox 消费 | `event_no` 幂等 + 状态 CAS |

## 20. 与已实现系统的差异修正说明

> 已实现系统 `G:\project\ccr` 技术栈与大部分实现方向正确、可复用；但以下 **5 项业务语义与已实现实现不符，必须按 PRD 修正**。

### 20.1 重提语义（修正项①，最高优先级）

| 项 | 已实现（docs/07 D-7） | 本设计（PRD D18b） |
|---|---|---|
| 已批准类型重提 | 全部重新审批 | **沿用原决议**，仅重审未通过/新增类型 |
| 分项继承 | 无 source/inherit 语义 | `source_pricing_item_id` + `inherit_flag` |
| 修改已批准利率 | 覆盖 | 走新增变更申请，不覆盖原决议 |

### 20.2 状态机（修正项②）

| 项 | 已实现 | 本设计（PRD §7.5/B14） |
|---|---|---|
| 重提 | `RETURNED→DRAFT` 原单回退 | **终态模型**：原申请保持终态，重提创建新申请号并关联 |
| 被否申请 | 可回 DRAFT 修改 | 保持 `VOTED_DOWN/VETOED/REJECTED` 终态不可回退 |

### 20.3 审批端刷新（修正项③）

- demo/已实现保留"刷新外部数据"按钮 → **移除**（PRD B11/D11）。
- 审批端一律读提交时冻结快照，不实时查数仓；仅承诺跟踪读数仓最新批次。

### 20.4 表决文案（修正项④）

- "2/3 通过"等残留措辞 → **统一"≥4 票赞成通过"**（PRD D5/B5）。

### 20.5 技术栈与范围（修正项⑤⑥）

| 项 | 定稿版 V1.0 | 已实现/本设计 |
|---|---|---|
| 后端 | JDK 8 / Spring Boot 2.7 / RuoYi-Vue-Plus 4.3.0-beta2 | **JDK 17 / Spring Boot 3.3**（已落地，以可落地为准） |
| 前端 | Vue 2 | **Vue 3 + Element Plus + design-system** |
| 客户模型 | 集团模型为主 | **单户（个人/企业）+ 集团双轨**（PRD V2 重构，集团保留额度拆分） |
| 审批原子单位 | 担保类型分项 + 存款账户分项 | 一致（B05），逐担保类型独立计票 |

### 附录 B：金额档次判定规则（D6/B18）

- 个人/企业单户：按分项 `pricing_amount` 判定金额档次。
- **对公贷款默认金额档**：`(0, 5000]` 万（低档，权限内终审）/ `(5000, ∞)`（高档，**必经六人小组 + 总行行长决策**）；档位边界为可配置参数（**产品审批链路 `ccr_product_route.vote_condition.amount_tier`，§8A.5②/§8.4**）。
- 集团：按集团综合授信批复总额度 `dw_group_credit_snapshot.approved_total_amount` 判定，再叠加分项金额校验；避免成员拆分规避权限层级。

### 附录 C：路由命中优先级

1. **先按产品命中审批链路**（`ccr_product_route`）：`route_mode`（CHAINED/DIRECT_VOTE）决定是否走链式；`mandatory_vote` / `vote_condition` 决定是否上会、是否必经行长决策（§8A.5②）。
2. `priority` 升序，第一命中生效（贷款链路）；
3. 同一命中下 `dept_code` 决定岗位归属（对公存量→公司金融部；对公新增→授信评审部；个人经营性→零售金融部）；
4. 对公贷款增加 `enterprise_type`（国企/非国企）匹配维度，与客户类型/金额档/期限档/担保类型共同参与命中；
5. 存款/保证金（DIRECT_VOTE）按产品类型+期限档唯一，命中即上会；
6. 未命中 → 阻断提交并提示配置缺失。
