## 一、背景与问题

### 1.1 业务场景

客户**名下已有存量授信协议**（老贷款在贷），现在需要在**同一授信关系下新增一笔授信分项**。这类业务在风控上属于**新增授信**（新放款、新敞口），应当按新增业务的流程与门槛审批，而不是按存量调息的流程走。

### 1.2 现状为什么做不到

申请类型目前是**申请级单选、二选一**（`frontend/src/views/application/loan.vue:521`）：

| 选项 | 取值 | 行为 |
|---|---|---|
| 存量调息(现有贷款合同) | `EXISTING` | 强制选授信协议，`onBusinessTypeChange` 自动从数仓带出授信拆分项与担保措施 |
| 新增授信(拟签合同) | `NEW` | 清空存量拆分项，手工录总授信额度与分项 |

后端 `newOrExisting` 同样是**申请级**取值：`credit_info_json.businessType`，**整单所有分项共用一个值**。

结果：存量协议下即便手工加了一条分项，它在矩阵里也算 `EXISTING`，按存量调息口径匹配——**不会按新增业务走**，前端的业务类型下拉也没有表达"这笔是新增"的入口。

### 1.3 技术底子（有利条件）

矩阵路由是**逐分项**入口、**整单**取值：提交时逐分项各调一次 `calcRoute`，但**入参里的 `newOrExisting` 来源于申请级 `businessType`**（`buildRouteInput` → `resolveNewOrExisting`）。

**所以本需求不需要改矩阵引擎**：只要让申请级 `newOrExisting` 对这个新类型返回 `NEW`，新增分项即按新增匹配。

## 二、需求目标

新增**第三种申请类型「存量新增」**（`credit_info_json.businessType = EXISTING_NEW`）：

> 在已有授信协议下发起的申请，单内**混合**存量分项（数仓带出）与新增分项（手工录入），**整单按新增授信业务走流程**；存量分项**不参与矩阵匹配**，只是搭着新增分项定出来的那条链一起上送。

**核心口径（2026-09-17 用户原话）**：

> 你这个理解又有错误：你存量不应该匹配矩阵，直接跟着新增的那条链上送就可以了。

即：单内按**来源**分两类，处理方式**不同**——

| | 判据 | 矩阵 | 定链 |
|---|---|---|---|
| **新增行** | `sourceSplitNo` **为空**（客户经理手工录入） | 调 NEW 矩阵 | **锚定整单链**（取其中利率最低者） |
| **存量行** | `sourceSplitNo` **非空**（数仓协议带出） | **不调矩阵** | **不参与**，链冻结后原样搭链上送 |

> 「存量 / 新增」标记同时是**页面标识**（告诉客户经理这行是旧账还是新账）与**分流依据**。

## 四、详细设计

### 4.1 前端（`frontend/src/views/application/loan.vue`）

#### A. 业务类型下拉（`:521`）

新增第三项：

```html
<option value="EXISTING_NEW">存量新增(原协议下新增授信分项)</option>
```

#### B. 业务类型判断的**归类规则**（本需求的核心实现手法）

代码里判断业务类型有**两种写法**，对 `EXISTING_NEW` 的天然行为**相反**，必须区别对待：

| 写法 | `EXISTING_NEW` 的行为 | 处置 |
|---|---|---|
| **黑名单式** `=== 'EXISTING'` / `!== 'EXISTING'` | **自动走新增侧**（因为不等于 `'EXISTING'`） | 需要走存量侧的，用 computed 收口；天然正确的**不动** |
| **白名单式** `=== 'NEW'` | **掉到存量侧**（因为不等于 `'NEW'`） | **必须逐个改**，否则静默走错 |

**收口手法**（把"走存量侧"的判断统一到一个 computed）：

```js
/** 存量类业务类型:存量调息(EXISTING) / 存量新增(EXISTING_NEW,§docs/43)。
 *  两者共用「协议选择、数仓拆分项带出、协议必选校验、集团存量恢复」等存量专属逻辑。
 *  钱与流程(定档金额/矩阵匹配/审批链)则一律走新增侧 */
const isExistingLike = computed(() =>
  form.businessType === 'EXISTING' || form.businessType === 'EXISTING_NEW')
```

**⚠️ 本类型的"两半各归一处"**：**协议与分项来源走存量侧，钱与流程走新增侧。** 所以 `isExistingLike` **不能**无脑替换所有 `=== 'EXISTING'`——"钱"相关的判断必须保留 `=== 'EXISTING'` 原写法。

#### C. 各处判断的归类明细

| 类 | 处数 | 位置 | 处置 |
|---|---|---|---|
| **A. 走存量侧**（需一并纳入） | **11** | `:552` 协议区综合利率块 · `:561` 授信协议区块 · `:652` 拆分项工具栏 · `:701` 协议表单项（原利率字段） · `:1754` 集团存量协议 · `:1769` 早期返回 · `:1835` 集团存量带出 · `:1903` 切换类型带出 · `:2441` 集团协议必选校验 · `:3261` 集团存量恢复 · `:1683` `applyTotalCreditText` | **一个 `isExistingLike` 机械替换** |
| **B. 天然走新增侧**（**不动**） | **6** | `:2074` `syncTotalCredit` · `:2403` `creditTotalAmount` · `:2464` `validateExistingRateCap` · `:2860` `serializeCreditInfo` · `:1457` 单户自动判定 · `:534` 授信概览块 | **零改动**——原写法是 `!== 'EXISTING'`/`=== 'EXISTING'`，本类型自动落到新增分支 |
| **C. 白名单 NEW 式**（**必须改**） | **2** | `:548` 申请综合利率块 `v-if="businessType === 'NEW'"` · `:2393` `groupApplyTotalAmount()` `if (businessType === 'NEW')` | 改法见下 |

> **`:2393` 是集团链路的关键**：`serializeGroupInfo()` 的 `applyAmount` 直接取 `groupApplyTotalAmount()` 的返回值，改这一处，集团定档链路**全对，无额外改动**。

#### D. 页面标记：`存量` / `新增`（新写）

分项卡标题区（`:662` 一带）现有 `<span v-if="g.sourceSplitNo" class="badge badge--info">拆分项 …</span>`，在其旁**追加**来源标记徽标（保留原拆分项号，便于溯源）：

```html
<span class="badge" :class="g.sourceSplitNo ? 'badge--neutral' : 'badge--info'">{{ g.sourceSplitNo ? '存量' : '新增' }}</span>
```

- 判据唯一且现成：**`sourceSplitNo` 非空 = 存量行**（数仓带出）、**为空 = 新增行**（手工录入）；
- 该字段前端已有 6 处既有依赖（换协议清行、切新增清行、去重、带出赋值、落库序列化、草稿恢复），**无需新增任何字段、无需 DDL**；
- **不含任何编辑权限逻辑**（口径 10：两种行全部可改）。

#### E. 定档金额（口径 7）

`syncTotalCredit`（`:2074`）、`creditTotalAmount`（`:2403`）、`serializeCreditInfo`（`:2860`）**三处天然走新增侧，零改动**，直接取 `form.totalCredit`（客户经理手工录入）。

**⚠️ 集团 `groupApplyTotalAmount()`（`:2415`）是本类型最易踩的一处**——它曾用 `!isExistingLike` 判定，会把 `EXISTING_NEW` 判进存量侧去取协议额度，**定档金额被数仓协议额度顶掉**，违反口径 7。已改为：

```js
// 非存量调息(含 NEW 与 EXISTING_NEW)一律手工录入优先——必须用 `!== 'EXISTING'` 判定,
// 不能用 isExistingLike:那会把存量新增判进下方存量侧,定档金额被协议/批复额度顶掉
if (form.businessType !== 'EXISTING') return manual > 0 ? manual : approved > 0 ? approved : 0
```

#### F. 草稿恢复（**必修，见 5.3 坑 2**）

草稿恢复原按"拟签合同"标志推断 `hasPlanned ? 'NEW' : 'EXISTING'`，**完全不读快照** → 本类型单存了草稿再打开**必然变成 `NEW`**。已改为**优先读快照 `businessType`**（含 `EXISTING_NEW`），快照缺失或为老草稿时才回退现有推断。

#### G. 提交校验（`validateStep`，本段新增）

```js
// 存量新增(§docs/43):整单审批链由新增分项锚定,数仓带出的存量拆分项只是搭链上送、不匹配矩阵;
// 若全是存量行则无链可搭 —— 与后端 ApplicationSubmitServiceImpl 提交拦截同口径,前端先拦避免白填到提交
if (form.businessType === 'EXISTING_NEW' && form.guarantees.length
    && !form.guarantees.some((g) => isBlank(g.sourceSplitNo))) {
  return '存量新增须至少录入一个新增授信分项(数仓带出的存量拆分项不参与审批链定档);若本次仅调整存量分项,请改选「存量调息」'
}
```

其余校验（协议必选 `:2441`、分项必填、金额勾稽）**对所有类型一视同仁**；存量行**无任何只读约束**。

> **`:2464` `validateExistingRateCap` 不需要单独改**：其首行是 `if (form.businessType !== 'EXISTING') return null`，本类型天然跳过（见 5.2）。

### 4.3 随 `newOrExisting=NEW` 自动生效的部分

- **业务大类判定**：整单按新增；
- **秘书岗门槛**：本类型插秘书岗（新增授信口径）；

### 4.4 集团维度（适用）

集团存量申请是相对独立的链路（见 `docs/38_集团存量申请自动带出成员拆分项_方案.md`），本类型一并覆盖：

- **集团协议**：来源 `dw_group_credit_snapshot`（集团授信行），选中后按成员带出拆分项；`onBusinessTypeChange` 集团分支**已补本类型**；
- **分项带成员维度**：集团分项携带 `memberCustomerNo`，手工新增分项须归属当前成员页签；
- **定档金额**：**手工录入**（口径 7），落点 `groupApplyTotalAmount` 一处（见 4.1 E），`serializeGroupInfo` 与后端 `loadGroupCreditTotal` **零改动**；
- **勿重复叠加**：`amountBasis=GROUP_TOTAL_CREDIT` 时以 `groupCreditTotal` 为准；
- **连带自动生效**：集团的新增判定同样吃 `newOrExisting`，集团秘书岗门槛等一并按新增走。

## 五、影响面与风险

### 5.1 【已闭环】矩阵匹配 —— 2026-09-16 试算通过

**试算方法**：复现 `RateMatrixRouterImpl.match()` 的匹配维度（业务大类/存新/客户类型/产品/担保/金额档/期限档，**利率不参与匹配**），对本地库全部真实分项穷举「按 `newOrExisting=NEW` 能命中几行」。

**结果**：对公贷款 **57 个分项按 NEW 匹配 100% 命中，零例外**。

**为什么必然命中**：矩阵三档（`LT_1000` / `GE_1000_LT_5000` / `GE_5000`）维度结构完全一致——

| 存新 | 期限档 | 客户类型 | 行数 |
|---|---|---|---|
| EXISTING | **通配（不分期限）** | SOE / NON_SOE | 各 3 行 |
| NEW | **1Y / 3Y / 5Y** | SOE / NON_SOE | 各 9 行 |

- 担保、产品两维在矩阵里**全是通配** → 恒真；
- `toAmountTier` 三档覆盖无缝；金额回退 `pricingAmount` 保证非空；
- `toTermTier` 贷款分轨 1Y(≤12月)/3Y(≤36月)/5Y(>36月) **覆盖无缝**；本库 58 个对公分项实测落 1Y=48 / 3Y=9 / 5Y=1，**零空档**。

> **定稿后试算口径的变化**：**新增行**才需要过矩阵（存量行不调），而新增行都是客户经理手工录入的完整要素（期限必填），**不存在空期限风险**。原「存量分项空期限抛 `RULE_NO_MATCH`」的边界**已随本次定稿消除**。

### 5.2 【连带，已接受】存量利率上限校验在本类型下整单跳过

`existingRatePrecheck` 与 `checkExistingRateCap` 的首句均为：

```java
if (!"EXISTING".equals(resolveNewOrExisting(app, item))) continue;
```

本类型 `resolveNewOrExisting` 返回 `NEW` → **两个校验全部跳过**，即：本类型的存量行**允许把申请利率调到高于原执行利率**，不再拦截（单户 + 集团皆然）。

- 判定：**符合用户口径**（口径 11，用户 2026-09-17 拍板「不受约束」）；
- 前端 `validateExistingRateCap` 首行 `if (form.businessType !== 'EXISTING') return null`，同样天然跳过，**无需改**；
- **回归确认点**：`EXISTING` 存量调息单的两道校验**行为不变**。

### 5.3 【必须处理】业务类型被自动覆盖 —— 会丢类型

**坑 1：选客户时被自动判成存量调息**（`:1457`）

```js
if (creditSplits.value.length && !userPickedBusinessType.value) {
  if (!isExistingLike.value) form.businessType = 'EXISTING'
  …
}
```

- 触发：该客户数仓有有效拆分项 **且** 客户经理尚未手动选过业务类型；
- 后果：强制置 `EXISTING`，需手动切到「存量新增」纠正；但 `onBusinessTypeChange` 会把 `userPickedBusinessType` 置 `true`，手选一次后不再被改回；
- 判定：**可接受**（手选即纠正），但**入口要显眼**。

**坑 2：草稿恢复时按分项推断，第三种类型必然丢失**（**已修**）

- 业务类型**从"拟签合同"标志推断**，**完全不读快照**；
- 存量新增是混合单 → `hasPlanned = true` → 草稿一恢复就变成 **`NEW`**，第三种类型静默丢失；
- **修复**：改为**优先读快照 `businessType`**（含 `EXISTING_NEW`），快照缺失或为老草稿时才回退现有推断。

**坑 3：恢复路径里 `loadCustomerDetail()` 也会跑坑 1**

重提/继续编辑走 `await loadCustomerDetail()`，`userPickedBusinessType` 在该路径**没有被置位**，所以坑 1 的条件在恢复时成立。不过它在草稿恢复赋值**之前**且是串行 await，最终以坑 2 的结果为准——**开发时保持这个先后顺序**。
