## 1. CI 产物部署流程

```text
git push → GitHub Actions(ci.yml)
  ├─ backend : cd backend && mvn -B package   → 产出 ccr-admin/target/ccr-admin-*.jar
  └─ frontend: npm ci && npm run build        → 产出 frontend/dist/(Nginx 静态包)
```

**制品**:后端可执行 jar(Spring Boot 内嵌容器)+ 前端 dist 静态包(Nginx)。
**快速起整套**:`docker compose up -d --build`(MySQL 自动执行 db/ DDL + Redis + 后端 + 前端)。

## 3. 数据归档策略(§16.6)

- **归档范围**:履约明细、快照 bundle、审批历史、数仓推送记录。
- **周期**:按月归档,保留最近 12 个月在线 + 历史按季度导出冷备。
- **方式**:停窗导出为 CSV/SQL 转储 → 压缩 → 加密 → 冷存储;归档后从在线表分区清理,需先验证导出行数=在线行数(勾稽口径一致)。

## 4. 备份脚本(示例,MySQL)

```bash
#!/usr/bin/env bash
# 全量备份,保留最近 7 份
DUMP_DIR=/backup/ccr/$(date +%Y%m%d_%H%M%S)
mkdir -p "$DUMP_DIR"
mysqldump -h "$DB_HOST" -u "$DB_USER" -p"$DB_PASS" --single-transaction --routines --triggers \
  ccr_rate | gzip > "$DUMP_DIR/ccr_rate.sql.gz"
# 备份完整性校验:行数统计 + gzip -t
gzip -t "$DUMP_DIR/ccr_rate.sql.gz" && echo "OK"
```

## 5. 灰度发布方案

1. **灰度批次**:先切 1 个支行/网点 → 观察核心链路(提交/审批/计票/决议)指标与告警;
2. **指标观察期**:≥30 分钟,确认无新增错误率、事务成功率 100% 后扩批;
3. **扩批**:每批增加 25%~50%,逐步放量至全量;
4. **全量收口**:全量后观察 2 小时,Outbox 无积压、缓存命中率正常后宣布上线完成。

## 6. 回滚预案

- **触发**:上线后出现阻断性故障(提交失败率 >5%、计票/决议异常、数据不一致)。
- **步骤**:
  1. 后端:回滚镜像/jar 至上一稳定版本(保存前版制品),重启;
  2. 前端:回滚 Nginx 静态包至上一版 dist;
  3. 数据库:一般**不回滚 DDL**(增量变更),仅对数据修复执行逆向脚本;若确需回滚,用 §4 备份恢复并停写;
  4. 配置:恢复上一版 `config/` 部署配置;
  5. 验证:健康检查 `/health` 通过 + 核心链路冒烟。
- **演练**:上线前按本预案演练一次,记录恢复耗时(目标 <30 分钟)。
