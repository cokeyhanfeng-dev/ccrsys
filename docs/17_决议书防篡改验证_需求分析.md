# 决议书防篡改验证 — 需求分析

> 状态：需求整理中（未开发）
> 提出人：总行行长
> 核心诉求：保证利率定价决议书文件不会被人篡改，支持「上传系统验证」与「转换为一定码值（验真码）验证」。

---

## 1. 背景与目标

利率定价决议书由系统依据审批留痕自动生成，是客户经理/审批人下载、打印、归档、报送的法律性文件。
目前 PDF 已做「加密只读」（禁编辑/复制/提取，仅可打印），但**加密只读只能防「误编辑」，防不了「被篡改后再伪造」**——用户把 PDF 另存、用工具重新生成、改内容后打印，系统无从察觉。

本需求目标：
1. **签发可验证**：系统签发的每一份决议书都带一个唯一「验真码」（一码值），持证方可凭码或文件在线核验真伪。
2. **内容可溯源**：文件是否被改过，上传后能给出明确结论（原件 / 已被篡改 / 无法识别）。
3. **防抵赖**：确认「这份决议书确实由本系统签发、签发时点的内容就是当前内容」。

---

## 2. 现状盘点

| 能力 | 现状 | 缺口 |
|---|---|---|
| PDF 生成 | `ResolutionPdfExporter` 按审批留痕生成，嵌中文字体 | 无「内容指纹」 |
| 只读保护 | PDF 标准加密（Owner 密码解锁、禁编辑/复制/提取、仅打印） | 防「误改」，不防「伪造/重制」 |
| 数据留痕 | 决议、表决、行长决策、审批轨迹均落库（ccr_resolution 等） | 库里有签发要素，但无文件级校验 |
| 下载入口 | 历史档案页「下载决议书」（仅已签发决议） | 无「验证」入口 |

结论：**数据基础完备，缺的是「文件↔数据」的绑定与校验层。**

---

## 3. 可行性结论

**能实现，且成本可控。** 按投入由低到高分三档：

| 档位 | 内容 | 投入 | 防篡改强度 |
|---|---|---|---|
| **一档：文件哈希验真** | 签发时算 SHA-256 存库；上传文件重算比对 | 低（纯后端，加一列/一表） | 中：能检测「字节级被改」 |
| **二档：验真码 + 数字签名** | 关键要素 + 文件哈希，用私钥签名成「验真码」印在 PDF（含二维码）；验证端验签 | 中（引入签名工具/国密） | 高：防伪造 + 防篡改 + 可防抵赖 |
| **三档：验真码 + 区块链/哈希链** | 二档之上，验真码哈希上链 | 高（需链基础设施） | 极高：防「系统内部改库」 |

**推荐：二档为主、一档打底**，三档按行内是否已有联盟链决定（本系统无链，暂不列入）。

---

## 4. 防篡改技术原理（先说清边界）

### 4.1 文件为什么会被「判定为变了」

PDF 是二进制文件，下面任一动作都会改变文件字节（哈希随之变化）：
- 用 Acrobat/WPS 打开后「另存为」
- 打印成 PDF（虚拟打印机重生成）
- 在 PDF 上盖章/加批注再保存
- 编辑工具改内容后重新保存

所以**「字节级哈希比对」会把「重新保存但内容没变」的文件也误判为被篡改**。
这是所有文档验真系统的通病，必须用「双轨验证」兜底（见 §6）。

### 4.2 真「防篡改」要防谁

| 威胁 | 含义 | 对策 |
|---|---|---|
| 外部人员改文件 | 下载后改利率/客户/结论再归档 | 哈希 + 签名检测 |
| 内部人员改库 | 直接改数据库让系统「认」伪造件 | 验真码私钥保管在签名服务，改库也验不出合法签名 |
| 高仿伪造 | 仿造一份「看着像」的决议书 | 验真码唯一性 + 二维码 + 要素回查 |

---

## 5. 方案对比

### 5.1 方案 A：文件哈希比对（一档）
- **原理**：签发时 `SHA-256(文件字节)` 存库 `ccr_resolution.file_hash`；验证时上传文件重算，相等即原件。
- **优点**：简单，无外部依赖。
- **缺点**：重保存即误报；不防「伪造一份哈希对得上的文件」（需结合签名）。

### 5.2 方案 B：验真码 + 数字签名（二档，推荐）
- **原理**：
  - 签发时取「决议要素摘要」（决议编号、客户号、业务类型、金额、最终利率、签发时间、文件 SHA-256），用**签名服务私钥**做数字签名，生成**验真码**（一码值）。
  - 验真码以「二维码 + 明文短码」印在决议书落款处；库中存 `验真码、文件哈希、签名值、签名密钥版本`。
  - 验证端两种入口：
    1. **上传文件**：重算哈希 + 用公钥验签 → 返回「原件/已被篡改/无法识别（要素级比对见 §6）」。
    2. **输入/扫码验真码**：查库返回签发要素清单，与手头文件人工核对。
- **优点**：防篡改 + 防伪造 + 防抵赖；离线也能用公钥验签；符合「一码值验证」诉求。
- **缺点**：需管理密钥（建议行内统一证书体系或国密 SM2）。

### 5.3 方案 C：区块链/哈希链（三档）
- 验真码哈希每日/每批打包上链，防「改库后重签」。**需行内已有链**，本系统不引入，文档留接口。

### 5.4 方案 D：仅加密/水印
- 现状已做（加密只读 + 水印行），不足以满足「验证」诉求，不作为本需求方案，仅作辅助。

## 6. 推荐方案（二档双轨）

```
签发（系统内，行长决策通过→决议生成时）
  PDF 生成(中文版) ──→ SHA-256 ──→ 要素摘要+哈希 ──私钥签名──→ 验真码(一码值)
                                                             │
                               PDF 落款嵌入 二维码(验真码) + 明文验真码
                                                             │
                                                             ▼
验证（任何持有决议书的人）
  入口① 上传 PDF ─→ 重算 SHA-256 ─┬→ 哈希命中 → 「系统签发原件」
                                   ├→ 哈希不中 → 再比「要素摘要」→ 要素全对 → 「原件重制(内容未变)」
                                   └→ 要素也不对 → 「内容已被修改或非系统签发」
  入口② 输入/扫码验真码 ─→ 查库返回 签发要素(客户/金额/利率/时间/结论) → 人工核对
```

**「要素级比对」为何能救误报**：
文件被重保存导致哈希变，但关键要素（客户名称、金额、利率、决议编号、签发时间）没变时，
验证端从 PDF 文本层提取要素（或 OCR），与库中签发要素逐项比对，可判「内容未变」而非「被篡改」。
即：**字节级哈希负责「精确防改」，要素级比对负责「容忍重制」**，两者互补。

## 7. 功能需求明细

### 7.1 签发（后端）
1. 决议书生成时（`ResolutionPdfExporter.build` 后）：
   - 计算文件 `SHA-256`。
   - 组装要素摘要：`决议编号|客户号|客户名称|业务类型|金额|最终利率|签发时间|文件哈希`。
   - 调用签名服务私钥签名 → 验真码（建议格式：`VERIFY<决议号><8位签名短码>`）。
   - 落库：`ccr_resolution_seal`（决议id、file_hash、verify_code、signature、key_version、seal_time）。
   - PDF 落款区追加「验真码：xxxxxx」+ 二维码（需引入 ZXing 生成二维码；二维码内容=验真码+验证地址）。
2. 存量决议（改造前已签发）：可提供「补签」任务，或仅在改造后新签发决议上生效（推荐后者，改造前文件无验真码属正常）。

### 7.2 验证（后端 + 前端）
1. **上传验证**：`POST /ccr/resolutions/verify`（multipart 上传 PDF）
   - 重算哈希 → 查 `ccr_resolution_seal`。
   - 命中 → 返回「系统签发原件」+ 签发要素。
   - 未命中 → 提取 PDF 文本关键要素与库比对 → 「原件重制（内容未变）」/「内容已修改或非系统签发」/「无此决议记录」。
   - 验证动作写 `ccr_audit_log`（谁在何时验证了哪份决议）。
2. **验真码验证**：`GET /ccr/resolutions/verify?code=验真码`
   - 查库返回签发要素清单（决议编号/客户/金额/利率/签发时间/结论），页面展示，供人工核对。
3. **前端入口**：
   - 历史档案页「下载决议书」旁加「验证决议书」（上传对话框）。
   - 系统外人员验证：可做一个**免登录**验证页（仅验真码+文件哈希，不泄露敏感字段，只回「真/假」），行内也可不开。

### 7.3 数据模型（新增）
```sql
CREATE TABLE ccr_resolution_seal (
  id            BIGINT NOT NULL,
  resolution_id BIGINT NOT NULL COMMENT '决议id(ccr_resolution.id)',
  file_hash     VARCHAR(64)  NOT NULL COMMENT '决议书文件 SHA-256',
  verify_code   VARCHAR(64)  NOT NULL COMMENT '验真码(一码值,唯一)',
  signature     VARCHAR(512) NULL COMMENT '要素摘要数字签名(私钥签名)',
  key_version   VARCHAR(32)  NULL COMMENT '签名密钥版本',
  seal_time     DATETIME NOT NULL COMMENT '签发时间',
  create_time   DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,
  del_flag      CHAR(1)  NOT NULL DEFAULT '0',
  PRIMARY KEY (id),
  UNIQUE KEY uk_verify_code (verify_code),
  KEY idx_resolution (resolution_id)
) COMMENT='决议书验真印章(防篡改验证)';
```

### 7.4 签名服务
- 密钥：推荐国密 SM2（行内合规）或 RSA-2048+；私钥存服务端（环境变量/HSM/KMS），不落库明文。
- 验签公钥内置在系统（`ccr-admin` 配置），验证端用公钥即可，不依赖私钥。
- 密钥轮换：`key_version` 支持多版本并存验证。

---

## 8. 一码值（验真码）设计

- **组成**：`VERIFY` + 决议号（如 `RES2026081960969787`）+ 8 位签名短码。
  例：`VERIFYRES2026081960969787A3F9C2B1`。
- **载体**：决议书落款区印二维码（扫码直达验证页/自动带入验真码）+ 明文验真码（供手输）。
- **性质**：验真码 ≠ 防伪码本身；它绑定「库中签发记录 + 文件哈希 + 数字签名」，改文件/改库都验不过。

---

## 9. 边界与限制（必须向使用方说清）

1. **扫描件/拍照件**：图像化后无法做哈希比对，只能走「要素人工核对」（验真码回查 + 关键要素人工比对），不做字节级判定。
2. **重保存误报**：字节级哈希对「另存/重生成」敏感，靠要素级比对兜底判定为「原件重制（内容未变）」，最终以要素比对为准。
3. **改造前存量决议**：无验真码，验证返回「无验真印章」，属正常（可后续补签）。
4. **验证页免登录**：只回「真/假/要素」，不回客户敏感全量信息（防利用验证接口泄露），要素核对在授权后详情页进行。
5. **加密 PDF 提取要素**：现 PDF 已加密（仅打印），程序提取文本需用系统持有权限（PDFBox 带 Owner 密码打开）——验证服务内部打开即可。

---

## 10. 验收要点（供测试参考）

1. **正向**：新签发决议书 → 下载 → 上传验证 → 返回「系统签发原件」，要素与 PDF 一致。
2. **篡改检测**：改 PDF 内任一文字/金额后上传 → 哈希不中 + 要素比对发现差异 → 返回「内容已被修改或非系统签发」。
3. **重制容忍**：PDF 用阅读器「另存为」后上传 → 哈希不中但要素一致 → 返回「原件重制（内容未变）」。
4. **验真码**：输码/扫码 → 返回签发要素清单；伪造码 → 「无此验真码」。
5. **审计留痕**：每次验证写入 `ccr_audit_log`（验证人/时间/决议号/结论）。
6. **存量回归**：改造前决议书验证提示「无验真印章」不报错；下载/打印不受影响。

---

## 11. 安全与合规

- 密码算法：行内如有密评要求，用**国密 SM2/SM3**；无要求可 SM3+RSA。
- 私钥管理：不进代码仓库、不落库明文，走环境变量/HSM/KMS；密钥轮换留版本。
- 免登录验证接口：做**频率限制**（防批量探测验真码），仅返回判定与要素概要。
- 本需求涉及新增表 + 后端服务 + PDF 改动 + 前端入口，不涉及审批主流程变更，风险低。

---

## 12. 待确认问题（评审时需行长拍板）

1. **验证入口是否对外开放**：仅行内（登录后）/ 也向外部（如客户、监管）开放免登录验证页？
2. **算法选型**：国密 SM2/SM3（合规优先，需行内证书体系配合）还是 RSA（实现简单）？
3. **存量决议**：是否需要对改造前已签发决议「补签验真码」，还是仅新签发生效？
4. **二维码依赖**：决议书落款加二维码，是否可接受（引入 ZXing 依赖）？
5. **责任边界**：文件被打印盖章后流转，验真只保证「内容与签发一致」，不保证「物理纸张防伪」。
