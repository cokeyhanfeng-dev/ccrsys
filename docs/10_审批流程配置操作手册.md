# 审批流程配置操作手册

> 适用对象:系统管理员、配置复核人、业务运营人员
> 目的:讲清 CCR 利率审批系统「审批流靠什么跑、每张配置表怎么用、调整审批人/流程怎么操作」,可照着本节逐表维护。
> 核心原则:**审批流全配置驱动**——机构、用户、部门、利率矩阵、节点指派、节点权限全部通过数据表动态调整,无需改代码;唯一代码硬编码项是**角色码**(`branch_manager`/`dept_gm`/`vice_president`/`committee_member`/`president` 等),新增角色需要改代码,日常调整请勿改动角色码本身。

---

## 1. 审批流全景

### 1.1 两条节点链

| 业务 | 节点链 | 说明 |
|---|---|---|
| **贷款**(对公/个人经营) | `BRANCH_MANAGER`(支行行长) → `DEPT_GENERAL_MANAGER`(部门总经理) → `VICE_PRESIDENT`(分管行长) → `SIX_PEOPLE_GROUP`(六人审批小组) | 逐级上报,链尾为六人小组上会表决 |
| **存款/保证金** | `BRANCH_MANAGER`(支行行长) → `SIX_PEOPLE_GROUP`(审批小组) | 无部门层级,支行过手后直接上会 |

代码位置:`backend/ccr-approval/.../support/RouteChains.java`(`LOAN_CHAIN` / `DEPOSIT_CHAIN`)。

### 1.2 终审岗位(route_code)截断

利率矩阵命中后返回一个 `start_node_code`(即 `route_code`),审批链按此**截断**——链只走到该岗位为止,不再往上。

| 场景 | 截断结果 |
|---|---|
| 矩阵行 `start_node_code = BRANCH_MANAGER` | 链 = `[BRANCH_MANAGER]`,支行行长终审 |
| `start_node_code = DEPT_GENERAL_MANAGER` | 链 = `[BRANCH_MANAGER, DEPT_GENERAL_MANAGER]` |
| `start_node_code = SIX_PEOPLE_GROUP`(或未配) | 全链(贷款走到上会;存款走 `[BRANCH_MANAGER, SIX_PEOPLE_GROUP]`) |

> 简单理解:**利率越低、金额越大,终审岗位越高**。矩阵里那行的 `start_node_code` 决定了这笔申请审批到哪一级。

### 1.3 一个申请怎么走

1. 客户经理提交申请 → 系统按**利率矩阵**匹配出每个分项的审批链(含终审岗位);
2. 分项按链逐级流转:每级先做**节点权限**判定(利率是否在本岗位权限内);
   - 权限内 → 本岗位直接通过(所有分项齐套即整单终审);
   - 超权限 → **ESCALATE 上送**到下一岗位;
3. 到 `SIX_PEOPLE_GROUP` → 上会表决(匿名,≥4 票通过);
4. 部分产品可配置**必经总行行长决策**(`PRESIDENT`)或**强制上会**(`DIRECT_VOTE`)。

### 1.4 审批权限两条线(不要混淆)

| 配置 | 管什么 | 表 |
|---|---|---|
| **利率矩阵** `ccr_rate_matrix` | 决定**审批链/终审岗位**、边界利率(路由) | 第 5 章 |
| **节点权限** `ccr_node_permission` | 决定某岗位**能不能直接批**(权限内/超权限上送) | 第 6 章 |

## 2. 用户 / 角色 / 机构体系

审批人的身份由三张基础表决定:**用户 → 角色 + 机构**。

### 2.1 用户表 `ccr_sys_user`

| 列 | 说明 |
|---|---|
| `username` | 登录名(工号),如 `wangwu` |
| `nick_name` | 姓名 |
| `role_code` | 角色码(决定岗位,见 2.2) |
| `org_id` | 归属机构(关联 `ccr_sys_dept.id`,决定数据权限范围) |
| `status` | `ENABLE` 启用 / `DISABLE` 停用(停用即不再作为处理人) |

### 2.2 角色表 `ccr_sys_role`(9 个角色,勿增删码)

| role_code | role_name | 对应节点 |
|---|---|---|
| `customer_manager` | 客户经理 | —(发起申请) |
| `branch_manager` | 支行行长 | `BRANCH_MANAGER` |
| `dept_gm` | 部门总经理 | `DEPT_GENERAL_MANAGER` |
| `vice_president` | 分管行领导 | `VICE_PRESIDENT` |
| `committee_member` | 审批小组成员 | `SIX_PEOPLE_GROUP` |
| `president` | 总行行长 | `PRESIDENT` |
| `admin` | 系统管理员 | —(全部功能) |
| `auditor` | 审计人员 | —(档案/表决/导出) |
| `config_reviewer` | 配置复核人 | —(参数复核与发布) |

> **角色码与节点一一对应**(代码里 `NODE_ROLE` 映射)。新增/改名角色需改代码,日常只增删角色下的**用户**即可。

### 2.3 机构表 `ccr_sys_dept`

机构用**单一数字编码**区分(`org_code`,2026-08-14 已删除 `dept_code` 字母列,统一 org_code):

| 列 | 含义 | 示例 |
|---|---|---|
| `org_code` | 真实机构码(唯一、禁改;数据权限按前缀匹配;部门归属引用) | `3202230000` 总行 / `3202233912` 公司金融部 / `3202233943` 授信评审部 / `3202233991` 零售金融 / `3202233050` 城东支行 / `3202233055` 东虹分理处 |
| `org_type` | `HEAD` 总行 / `DEPT` 部门 / `BRANCH` 支行 / `NETWORK` 网点 | — |
| `branch_code` | 归属支行 org_code(网点用) | — |

**前缀规则**:`3202230000` = 总行;`32022339xx` = 总行部门(`3202233912`=公司金融部、`3202233943`=授信评审部、`3202233991`=零售金融、`3202233931`=计划财务部);`32022330xx` = 支行(如 `3202233050` 城东支行),支行码尾号 `55` 等 = 分理处网点(如 `3202233055` 东虹分理处→城东支行)。数据权限按 `org_code` 前缀匹配(支行行长只看本支行数据)。

## 3. 节点指派 `ccr_node_assignee`

决定**某个节点由谁处理**(人/角色/部门)。审批时按**四层解析,命中即止**。

### 3.1 表结构

| 列 | 说明 |
|---|---|
| `node_code` | 节点编码: `BRANCH_MANAGER` / `DEPT_GENERAL_MANAGER` / `VICE_PRESIDENT` / `SECRETARY`(贷审会秘书岗,需求四) / `SIX_PEOPLE_GROUP` / `PRESIDENT` |
| `assignee_type` | 指派类型: `PERSON` / `GROUP` / `DEPT` / `ROLE` |
| `assignee_code` | 见下表(随类型不同语义不同) |
| `relation` | `OR` 任一(默认) / `AND` 需全员 |
| `delegate_to` | 代理人工号(有效期内替换本人) |
| `delegate_valid_from` / `delegate_valid_to` | 代理有效期 |
| `valid_from` / `valid_to` | 配置有效期(超出则不参与解析) |
| `status` | `ACTIVE` / `INACTIVE` |

### 3.2 四层解析(PERSON → GROUP → DEPT → ROLE,命中即止)

解析时按顺序逐层尝试,**某层解析出非空处理人列表就立即返回**,不再看后续层;全部为空则**不限制**(任何该节点角色用户都可处理)。

| 层级 | assignee_code 写法 | 作用 |
|---|---|---|
| **PERSON** | 用户工号,如 `wangwu` | 指定**某一个人**处理该节点 |
| **GROUP** | 逗号分隔的角色码,如 `committee_member,dept_gm` | 取这些角色下**全部启用用户**的并集 |
| **DEPT** | 两种写法(见 3.3) | 按**机构/部门**取人 |
| **ROLE** | 角色码,如 `dept_gm` | 取该角色下全部启用用户 |

### 3.3 DEPT 层的两种写法(重点)

| 写法 | 语义 | 示例 |
|---|---|---|
| **含冒号** `org_code:role` | 精确匹配:分项的部门归属(`org_code` 机构编码)等于冒号前编码时,取该部门下该角色的启用用户 | `3202233912:dept_gm` = 公司金融部下属部门总经理 |
| **不含冒号** `org_code` | 前缀匹配:申请人的机构 `org_code` 以配置值开头,则取该机构及下级全部启用用户(兼容支行/网点) | `3202233050` = 城东支行及下级(东虹分理处 3202233055)下全部启用用户 |

> **部门分流就靠「含冒号」写法**——同一节点配多行不同 `org_code:role`,分项按自己的部门归属命中对应处理人(详见第 7 章)。

### 3.4 解析结果的消费

- **待办过滤**:`filterByNodeAssignee` —— 只把解析出的处理人列为待办;
- **审批校验**:`guardNodeAssignee` —— 只有解析出的处理人能操作该节点。

代码位置:`backend/ccr-common/.../core/assignee/NodeAssigneeResolver.java`;消费点:`backend/ccr-approval/.../service/impl/ApprovalServiceImpl.java`。

### 3.5 代理(delegate_to)

某处理人出差/休假时,可配置 `delegate_to`(代理人工号)+ 代理有效期,有效期内该节点由代理人处理,到期自动恢复本人。

## 4. 部门分管行长 `ccr_dept_vp`

分管行长(`VICE_PRESIDENT` 节点)的指派**优先查此表**,命中后不再走四层解析。

| 列 | 说明 |
|---|---|
| `dept_code` | 部门归属(机构 `org_code`): `3202233912` 公司金融部 / `3202233943` 授信评审部 / `3202233991` 零售金融部 |
| `vp_user_id` | 分管行长用户 id(关联 `ccr_sys_user.id`) |
| `status` | `ACTIVE` / `INACTIVE` |
| `valid_from` / `valid_to` | 生效/失效时间(超期不参与) |

**一人可分管多个部门**(同 `vp_user_id` 配多行);某部门未配置时回退到普通四层解析。

## 5. 利率矩阵 `ccr_rate_matrix`

决定**审批链、终审岗位、边界利率**。是「这笔利率申请走到哪一级」的核心配置。

### 5.1 关键字段

| 字段 | 含义 | 示例 |
|---|---|---|
| `business_big_type` | 业务大类 | `LOAN_PUBLIC` 对公 / `LOAN_PERSONAL` 个人经营 / `DEPOSIT` 存款 / `MARGIN` 保证金 |
| `new_or_existing` | 新增/存量 | `NEW` / `EXISTING` |
| `customer_type` | 客户类型(空=通配) | `SOE` 国企 / `NON_SOE` 非国企 / `PERSONAL` |
| `product_code` | 产品编码(空=通配) | `LOAN_A` 对公 / `LOAN_P` 个人经营 |
| `amount_tier` | 金额档(空=通配;2026-08-14 需求三改三档) | `LT_1000` <1000 万 / `GE_1000_LT_5000` 1000万含-5000 万 / `GE_5000` ≥5000 万 |
| `term_tier` | 期限档(空=通配) | 贷款 `1Y/3Y/5Y`;存款 `3M/6M/1Y/2Y/3Y` |
| `guarantee_type` | 担保方式(空=通配) | `MORTGAGE`/`PLEDGE`/`GUARANTEE`/`CREDIT` |
| `start_node_code` | **终审岗位**(链截断点) | `BRANCH_MANAGER` / `DEPT_GENERAL_MANAGER` / `VICE_PRESIDENT` / `SIX_PEOPLE_GROUP` |
| `dept_code` | **部门归属**(分流到哪个业务部门,值为机构 `org_code`) | `3202233912` 公司金融 / `3202233943` 授信评审 / `3202233991` 零售 |
| `boundary_type` | 边界语义 | `RATE` 直接利率 / `SPREAD` 存量降幅 |
| `boundary_min_rate` | 边界利率(%) | 贷款=该岗位最低可批利率;存款=期限上限 |
| `boundary_bp` / `bp_sign` / `lpr_term` | LPR+BP 表达 | `boundary_bp=40`、`bp_sign=+`、`lpr_term=1Y` → LPR1Y+40BP |
| `priority` | 匹配优先级(低值优先,链式:1 支行 → 2 部门 → 3 分管 → 4 小组兜底) | 1~4 |

### 5.2 匹配与路由逻辑

1. 按 `customer_type / product_code / guarantee_type / amount_tier / term_tier` 逐维过滤(空=通配,不参与过滤);
2. 多个命中按 `priority` 取最低;同优先级多命中 = 配置错误(需修正);
3. 贷款:从优先级低到高,取**首个满足「申请利率 ≥ 边界」的节点**为终审岗位;全部不满足 → 小组兜底上会;
4. 存款/保证金:首行 `boundary_min_rate` 为上限,利率 ≤ 上限则支行终审,否则上会。

> **金额档取数**:2026-08-14 需求三拍板,一律按**申请/分项金额**定档(`amountBasis=APPLY_AMOUNT`,不再集团授信总额优先);三档:`LT_1000` <1000 万 / `GE_1000_LT_5000` 1000万含-5000 万 / `GE_5000` ≥5000 万。`<1000万` 档对公存量=零售金融部(3202233991)、新增=授信评审部(3202233943),利率区间与个人贷款一致。

### 5.3 部门归属透出

命中的矩阵行 `dept_code` 会**透出并冻结**到分项 `ccr_pricing_item.dept_code`,后续部门分流、部门总经理/分管行长解析都基于它。

| 矩阵 dept_code(= 机构 `ccr_sys_dept.org_code`) | 部门 |
|---|---|
| `3202233912` | 公司金融部 |
| `3202233943` | 授信评审部 |
| `3202233991` | 零售金融部 |

> 注:2026-08-14 机构表已删除 `dept_code` 字母列(原 `GSB/SXSB/LSB`),部门归属统一用机构 `org_code` 数字码;矩阵、`ccr_dept_vp`、节点指派 `3202233912:dept_gm` 等全部对齐,与数仓 `dw_org_performance_snapshot.org_code` 一致。

## 6. 节点权限 `ccr_node_permission`

决定**某个岗位最多能直接批多少利率**——权限内直接通过,超权限整单上送(`ESCALATE`)。

| 列 | 说明 |
|---|---|
| `node_code` | 节点编码 |
| `role_code` | 岗位角色码 |
| `business_type` | `LOAN` / `DEPOSIT` |
| `boundary_min_rate` | **贷款**:本岗位最低可批利率(申请利率 ≥ 此值才在权限内) |
| `boundary_max_rate` | **存款**:本岗位最高可批利率(申请利率 ≤ 此值才在权限内) |
| `effective_from` / `effective_to` | 有效期 |

**判定逻辑**:
- 贷款:申请利率 ≥ `boundary_min_rate` → 权限内,本岗位直接通过;否则超权限,上送下一岗位;
- 存款:申请利率 ≤ `boundary_max_rate` → 权限内;
- 未配置该节点 → 视为权限内(放行)。

> 它与利率矩阵的分工:矩阵决定**审批链走到哪**,节点权限决定**走到某级时能不能直接批**。两者边界利率建议保持一致,避免「矩阵说支行终审、权限又说支行无权」的矛盾。

## 7. 部门分流口径

**部门分流 = 把不同业务的审批分到对应业务部门的处理人**,节点链本身不变。

| 业务场景 | 分流到部门 | 部门归属(dept_code,=机构org_code) |
|---|---|---|
| 对公**存量**(调息) | 公司金融部 | `3202233912` |
| 对公**新增**(授信) | 授信评审部 | `3202233943` |
| 个人经营贷 | 零售金融部 | `3202233991` |

实现路径:
1. 利率矩阵命中行的 `dept_code` 透出,提交时冻结到 `ccr_pricing_item.dept_code`(值=机构 `org_code`);
2. 部门总经理节点指派配 `3202233912:dept_gm` / `3202233943:dept_gm` / `3202233991:dept_gm` 多行(第 3.3 节「含冒号」写法);
3. 审批时按分项的 `dept_code` 精确命中对应行,取该部门下 `dept_gm` 角色用户;
4. 分管行长节点同理,但优先走 `ccr_dept_vp` 映射(第 4 章)。

> 加新部门、调整部门归属,改矩阵行的 `dept_code` + 指派行即可,审批链代码不动。

## 8. 常见调整场景(照步骤改表)

| 场景 | 操作 | 涉及表 |
|---|---|---|
| **换部门总经理** | 给目标机构(`ccr_sys_dept.org_code` 对应 3202233912 公司金融/3202233943 授信评审/3202233991 零售)下新增一个 `dept_gm` 角色启用用户,或停用旧用户 | `ccr_sys_user`(改 role_code/org_id/status) |
| **部门改名** | 只改 `ccr_sys_dept.dept_name` | `ccr_sys_dept` |
| **换支行行长** | 改 `BRANCH_MANAGER` 节点的 PERSON 指派(assignee_code=新工号),或给 `branch_manager` 角色加人 | `ccr_node_assignee` / `ccr_sys_user` |
| **加审批人** | 给对应角色加启用用户(`ROLE`/`GROUP` 层自动纳入) | `ccr_sys_user` |
| **改分管行长分管范围** | 调整 `ccr_dept_vp` 的 dept_code↔vp_user_id 映射 | `ccr_dept_vp` |
| **处理人临时出差** | 配置 `delegate_to` 代理 + 有效期 | `ccr_node_assignee` |
| **调某节点可批利率边界** | 改 `ccr_node_permission` 的 `boundary_min_rate`/`boundary_max_rate` | `ccr_node_permission` |
| **调某笔利率走到哪级终审** | 改 `ccr_rate_matrix` 对应行的 `start_node_code`/`priority`/`boundary_*` | `ccr_rate_matrix` |
| **调整金额档分界** | 改金额档定义(当前硬编码 5000 万阈值,需改代码) | —(代码) |
| **⚠ 新增/修改角色码** | 需改代码(角色码硬编码),并全局同步 | —(代码) |

**改表后的生效**:配置为**即时读取**(审批时动态解析),一般无需重启;涉及缓存字段时可在管理界面触发刷新。

## 附录 C 审批链路机制与部门编码耦合说明

> 本节回答三个问题:**一条申请从提交到终审具体怎么走**、**机构表的部门编码改了会有什么影响**、**分管行长的权限到底怎么控制**。配置维护前建议先读本节。

### C.1 一条申请从提交到终审怎么走

#### C.1.1 提交时刻:算一次路由,结果"冻结"进分项

`RateMatrixRouterImpl.calcRoute`(backend/ccr-rule)在提交时算一次路由:

1. 按 `业务大类 + 存量/新增 + 客户类型 + 金额档 + 期限档` 从利率矩阵取匹配行,按 `priority` 排序;
2. 贷款逐行比较「申请利率 vs 该岗位边界利率」,取**首个 申请利率 ≥ 岗位下限 的行** → 该行 `start_node_code` 即**终审岗位**;
3. 组装链路 `buildChain`:`BRANCH_MANAGER`(必经)→ 中间层级岗位 → 终审岗位;
4. 命中行的 `dept_code`(部门归属)**透出**,随链路一起在提交时冻结到分项 `ccr_pricing_item`(`ApplicationSubmitServiceImpl`)。

> 之后审批推进不再重算矩阵(除非审批人**调价**,`approve` 带 `adjustRate` 会触发重算,见 C.3)。

#### C.1.2 审批时刻:沿冻结链路推进,每步先解析"该谁审"

1. `nextNode` 沿冻结 `route_chain` 取下一节点;
2. 每节点操作前 `NodeAssigneeResolver` 解析处理人(四层 `PERSON→GROUP→DEPT→ROLE`,分管行长优先 `ccr_dept_vp`);
3. 解析结果两个消费点:
   - **待办过滤**:只把解析出的处理人列为该节点待办;
   - **操作校验** `guardNodeAssignee`:处理人名单非空时,不在名单内的登录人直接拒绝(`ApprovalServiceImpl`)。

#### C.1.3 具体例子:个人经营贷「新增」一笔

| 环节 | 值 |
|---|---|
| 矩阵命中行 | `LOAN_PERSONAL / NEW`,`start_node_code = VICE_PRESIDENT`,`dept_code = 3202233943`(授信评审部) |
| 冻结链路 | `[BRANCH_MANAGER, DEPT_GENERAL_MANAGER, VICE_PRESIDENT]` |
| 支行行长节点 | `PERSON` 指派 `wangwu` |
| 部门总经理节点 | 分项 `dept_code=3202233943` → 命中指派 `3202233943:dept_gm` → 授信评审部孙总经理(1020) |
| 分管行长节点 | `ccr_dept_vp` 按 `3202233943` 映射 → 郑分管行长(1023) |

### C.2 机构编码 `org_code`:四方耦合键(改编码必须四方同步)

> 2026-08-14 起机构表**已删除 `dept_code` 字母列**,部门归属(矩阵/分项/节点指派/`ccr_dept_vp`)统一用机构 `org_code` 数字码;`ccr_rate_matrix.dept_code`、`ccr_pricing_item.dept_code`、`ccr_dept_vp.dept_code` 的**列名保留,值即机构 `org_code`**。

#### C.2.1 四张表靠「字符串精确匹配」连接,不是外键

| 表 | 相关字段 | 作用 |
|---|---|---|
| `ccr_sys_dept` | `org_code` | **权威来源**(系统前端已禁止修改,`SysDeptController`) |
| `ccr_rate_matrix` | `dept_code`(值=org_code) | 路由命中行透出、冻结到分项 |
| `ccr_node_assignee` | `assignee_code`(冒号前段) | DEPT 层「`org_code:role`」精确匹配 |
| `ccr_dept_vp` | `dept_code`(值=org_code) | 分管行长按部门精确映射 |

它们全是**快照字符串**,互相靠"字符串相等"耦合。任何一张单边改都会破坏匹配。

#### C.2.2 只改机构表 `org_code` 会发生什么(以 `3202233943→199999` 为例)

```
机构表  ccr_sys_dept.org_code       3202233943 ──→ 改成 199999
矩阵    ccr_rate_matrix.dept_code   仍 3202233943(不会跟着变)
指派    ccr_node_assignee='3202233943:dept_gm'   仍 3202233943
分管映射 ccr_dept_vp.dept_code      仍 3202233943

→ 指派「org_code:role」:分项 deptCode=='3202233943' 仍能命中配置行
→ 但去机构表查 d.org_code='3202233943' → 查不到 → 返回空
→ 静默走角色兜底:部门总经理变成全行所有 dept_gm 角色的人
```

**后果:审批人不再精确限定,而且不报错、是静默的**——这是最危险的一种失败方式。存量分项(已冻结 `dept_code=3202233943`)和新增申请全部中招。

#### C.2.3 安全 / 危险操作对照

| 操作 | 结果 |
|---|---|
| 改机构名称/负责人/排序/类型 | ✅ 安全,只影响展示 |
| 改上级机构 | ✅ 有前缀一致性 + 成环校验 |
| 新增机构 | ✅ 编码唯一校验,新增默认停用 |
| 停用/删除 | ✅ 前置校验存量业务 |
| **改 `org_code`** | ❌ 前端已直接禁止;绕过前端改库必须按 C.2.4 四方同步 |

#### C.2.4 真需要改机构编码:四方同步清单

1. `ccr_sys_dept.org_code`(机构表,权威来源);
2. `ccr_rate_matrix.dept_code`(改后**刷新矩阵缓存** `ccr:cfg:matrix:effective`);
3. `ccr_node_assignee.assignee_code` 的冒号前段(如 `3202233943:dept_gm` → 新码);
4. `ccr_dept_vp.dept_code`(分管行长映射);
5. **存量分项** `ccr_pricing_item.dept_code`(已冻结的历史数据,不处理则历史单解析失效);
6. 其他业务映射:`ApprovalServiceImpl`「机构达成」用 `org_code` 查数仓 `dw_org_performance_snapshot` 等。

> **结论:机构编码当业务常量,定了就不动;要加部门就新增机构+新编码,矩阵/指派/分管映射配置跟上即可。** 这正是需求 E(配置化)想把这套耦合彻底数据化的原因。

### C.3 分管行长(VICE_PRESIDENT)权限:三层控制

分管行长不是"只能看、不能动",他的权限由**三层**独立控制,层层收紧:

#### 第一层:身份——谁能操作这个节点

- **角色兜底**:`CurrentLoginUser.NODE_ROLE` 硬编码映射 `VICE_PRESIDENT → vice_president` 角色,登录人角色不符直接拒绝(`requireNodeRole`);
- **精确指派**:分项 `dept_code` 非空时,**优先查 `ccr_dept_vp`**(不再走四层解析),`dept_code` 精确映射 → 取对应分管行长用户;解析出的名单即该节点处理人(`guardNodeAssignee` 校验登录人必须在内)。
  - 运行库现状:`3202233912→1022`、`3202233991→1022`(同一人分管多部门)、`3202233943→1023`。
- 分项 `dept_code` 为空(旧数据/未分流场景)时回退角色兜底,即"该角色任意启用用户"。

#### 第二层:利率权限边界——他能批到多少利率

- 表 `ccr_node_permission` 按 `(node_code, business_type)` 配置:
  - 运行库现状:`VICE_PRESIDENT / LOAN` 的 `boundary_min_rate = 3.2%`;
  - 判定(`ApprovalServiceImpl.inNodePermission`):贷款 **申请/调价利率 ≥ 3.2%** 才在权限内;
  - **主动调价** `adjustRate` 不得突破本节点边界(突破抛 `NODE_PERMISSION`),且不得突破产品硬边界。

#### 第三层:终审资格——他能不能直接批(还是只能过手)

- **矩阵冻结** `route_code`:`提交时命中矩阵行` `start_node_code` 就是 `route_code`。只有"**当前节点 == 矩阵冻结的终审岗位**"(`isFinalNode`)才有权限内终审资格;
- 利率在权限内但**当前节点只是链路中间节点**(如强制上会场景的分管行长)→ 只有**知晓/过手权**,沿链上送小组,不能截胡终审(`approve` 的 `escalate` 判定,任务 #13 修复点);
- **三条边界不要混淆**:

| 边界 | 表 | 管什么 | 现值(贷款) |
|---|---|---|---|
| 岗位硬边界 | `ccr_node_permission` | 这个岗位最多能批到多少 | 分管行长 3.2% |
| 矩阵路由边界 | `ccr_rate_matrix` | 这笔业务利率到哪一级终审 | 个人经营贷新增 VP=LPR+80BP(约3.8%) |
| 产品硬边界 | `ccr_product_rate_limit` | 全行不可突破的下限 | 按产品 |

> 举例:一笔 3.5% 的贷款,`ccr_node_permission` 判定 3.5≥3.2 在岗位权限内,但矩阵路由时 3.5 < 个人经营贷新增的 VP 边界(≈3.8%),`route_code` 落在小组 → 分管行长是中间节点,只能过手上会,不能直接批。**岗位有权限 ≠ 能终审,是否终审看矩阵冻结的 `route_code`。**

### C.4 如何配置「走到哪个分管行长」/ 新增部门分管行长(实操)

#### C.4.1 两个配置点(别记混)

| 问 | 答 | 配置在哪 |
|---|---|---|
| 这笔业务**归哪个部门**? | 看矩阵命中行的 `dept_code`(值=机构 `org_code`) | `ccr_rate_matrix`(有界面:参数管理→权限矩阵) |
| 这个部门**谁分管**? | 查 `ccr_dept_vp` 的 `dept_code → vp_user_id` | `ccr_dept_vp`(**无界面,只能改库**) |

> **分工**:矩阵决定"流程走进哪个部门的分管行长",`ccr_dept_vp` 决定"该部门具体是哪位分管行长"。改矩阵 `dept_code` 就换部门,改 `ccr_dept_vp` 就换人。

#### C.4.2 界面入口现状(哪些能点,哪些不能)

| 配置 | 界面 | 入口 |
|---|---|---|
| 部门总经理指派(部门总经理解析) | ✅ 有 | 流程与审批人员配置 → 节点指派(`ccr_node_assignee`) |
| 业务部门归属 / 终审岗位 | ✅ 有 | 参数管理 → 权限矩阵(`ccr_rate_matrix`) |
| 岗位利率边界 | ✅ 有 | 参数管理 → 节点权限(`ccr_node_permission`) |
| **部门→分管行长映射** | ❌ **无** | 只能直接改 `ccr_dept_vp` 表 |

> `ccr_dept_vp` 目前无维护界面(后端只有读取、无 CRUD 接口)。这是配置化需求的已知缺口,已在需求 E 范围里。

#### C.4.3 新增一个部门及其分管行长(完整 5 步)

以「给**风险管理部(org_code `100104`)** 配一位分管行长(新用户 1024)」为例:

1. **机构表**:确认该部门存在(`ccr_sys_dept` 有 `org_code='100104'`;没有就新增机构,编码唯一、默认停用后启用);
2. **用户表**:确认该分管行长用户存在且 `role_code='vice_president'`(没有就新增用户、授权);
3. **分管行长映射**:`ccr_dept_vp` 插入 `('100104', 1024, 'ACTIVE')`;
4. **(配套)部门总经理指派**:该部门还没有 `dept_gm` 指派时,`ccr_node_assignee` 加 `'DEPT_GENERAL_MANAGER', 'DEPT', '100104:dept_gm'`;
5. **(配套)业务归属**:要让某类业务走新部门,把对应矩阵行 `dept_code` 改为 `100104`(改后刷矩阵缓存)。

```sql
-- 3. 分管行长映射(核心)
INSERT INTO ccr_dept_vp (id, tenant_id, dept_code, vp_user_id, status, del_flag, create_time)
VALUES (10001, '000000', '100104', 1024, 'ACTIVE', '0', NOW());

-- 4. 部门总经理指派(该部门还没有时)
INSERT INTO ccr_node_assignee (node_code, assignee_type, assignee_code, relation, status, del_flag)
VALUES ('DEPT_GENERAL_MANAGER', 'DEPT', '100104:dept_gm', 'OR', 'ACTIVE', '0');

-- 5. 业务归属(把某业务分到新部门,矩阵缓存会失效后自动回源)
UPDATE ccr_rate_matrix SET dept_code='100104' WHERE business_big_type='...' AND new_or_existing='...' AND ...;
```

#### C.4.4 换人 / 一人分管多部门 / 某部门不设分管行长

| 场景 | 操作 |
|---|---|
| **换分管行长** | 改 `ccr_dept_vp.vp_user_id`(或停用旧行、加新行) |
| **一人分管多部门** | 同一 `vp_user_id` 配多行(运行库:吴分管行长=3202233912 公司金融+3202233991 零售两行) |
| **某部门不设分管行长** | 该 `dept_code` 不配行 → 回退四层指派解析 / 角色兜底 |
| **新增部门总经理** | 给新部门下加 `dept_gm` 角色启用用户(`ccr_sys_user`),或配 `org_code:dept_gm` 指派行 |
