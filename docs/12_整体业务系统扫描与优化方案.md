# CCRSYS 整体业务系统扫描与优化方案

> 扫描日期：2026-08-12
> 扫描基线：`03f4418`（`修复贡献度跟踪客户名称匹配不到(数仓分批快照)`）
> 审计分支：`codex/business-system-audit-20260812`
> 扫描方式：需求/详设/改动记录对照、后端/前端/DDL 静态扫描、单元测试与前端生产构建验证
> 说明：本报告只给出诊断与整改方案，未修改业务代码、DDL 和测试数据。

## 1. 执行摘要

系统已经形成模块化单体的完整业务骨架，申请、规则路由、快照、普通审批、六人表决、行长决策、决议、承诺、消息、工作流轨迹均有对应模块。LPR/权限矩阵配置、分项计票唯一约束、Outbox、乐观锁、不可变快照模型等关键基础设施已经具备。

当前版本仍存在会影响 UAT 可信度与生产安全的主链路问题，建议完成 P0 闭环后再进入业务验收：

1. 多个敏感接口只有登录校验，缺少角色与对象级数据权限；申请归属字段还可在草稿更新时被请求体覆盖。
2. 产品审批链路的完整节点序列和配置版本未冻结，审批推进仍使用固定节点表，`DIRECT_VOTE` 等配置可能被执行成另一条链路。
3. 审批详情在快照缺失时读取数仓实时数据，集团贡献度、授信、他行融资、关联人、借据等区块也存在读取最新批次的路径，破坏 D11 的冻结口径。
4. 提交缺少数据库级状态抢占和“一申请一快照包”约束，并发提交可能生成多个快照包，幂等返回语义不稳定。
5. 草稿全量重建与逻辑删除唯一键组合不兼容，集团成员首次重建、同合同/账户多次重建存在唯一键冲突风险。
6. D21 要求的“同一客户跨申请按指标聚合承诺基线”尚未落地；当前按申请建计划，并用同一数仓实际值分别评价各申请目标，会导致履约和机构达成口径失真。
7. 当前统一验证未通过，`ccr-approval` 有 2 个节点指派测试与三参数解析接口不一致。

综合建议采用“口径定版 → P0 正确性与授权 → P1 恢复性与测试 → P2 结构和性能”的顺序增量治理，继续沿用现有模块，避免重建同义领域模型。

## 4. P0：UAT 前必须闭环

### P0-01 统一角色授权与对象级数据权限

**需求依据**：PRD §3.1、§4、§8.6；详设 §5.4、§5.9、§15.1；AGENTS.md 对详情、保存、提交、附件、历史、导出要求后端对象权限。

**确认现状**：

- `SaTokenConfig` 对 `/ccr/**` 普遍只检查登录；只有 `/system/**` 和 `WorkflowController` 做了集中角色限制。
- `CcrApplicationController` 的详情、保存、路由预览、提交校验、提交、重提没有对象所有权校验。
- `CcrApplicationServiceImpl.copyForUpdate` 接受请求体的 `applicantUserId`、`applicantOrgId`，草稿可被改写归属。
- `AttachmentController` 上传、列表和下载仅按申请 ID 查询，没有验证登录人与申请关系，也没有验证草稿状态和上传角色。
- `ApprovalController.detail` 直接按分项 ID 聚合客户、融资、贡献度、关联人、附件等敏感资料，没有先验证当前人是否拥有该待办或历史参与权。
- `SnapshotController` 允许任意登录用户创建记录、确认质量结果、冻结快照；`DatacenterController` 注释与代码允许登录即访问，前端却按 admin 隐藏。
- `RuleController` 的规则集创建、送审、发布、驳回、停用只有登录校验。
- 通知规则、手工发送、重试处理、跟踪策略变更、承诺状态/手工评估、决议生成、合同绑定和核验等接口缺少对等角色限制。
- `ResolutionController.create` 接收外部 `finalRate`；任意登录用户可抢在 Outbox 前为已批准分项创建决议，影响最终利率完整性。
- 提交通知用 `recipientType=ROLE, recipientId=branch_manager`，消息服务会解析为全行该角色用户，缺少申请机构上下文，存在跨支行通知泄露。
- 已搭建的 `DataPermissionInterceptor` 只有在 `@DataScope` 上下文存在时生效，当前业务方法没有实际标注使用点。

**优化方案**：

1. 在 `ccr-common` 建立统一 `ApplicationAccessService`/`BusinessObjectAuthorizer`，提供 `requireOwner`、`requireTodoParticipant`、`requireHistoricalParticipant`、`requireFullViewRole`、`requireContractOperator` 等对象授权方法。
2. Controller 只声明动作权限和 DTO 校验；对象权限在 Service 事务内、读取对象后立即执行，避免只依赖 URL 注解。
3. 建立路径级权限表并先覆盖高风险写接口：
   - 申请创建/保存/提交/附件上传：仅 PC 客户经理，且仅本人草稿。
   - 审批详情/动作：当前节点合法处理人或有历史查看权。
   - 快照写接口：改为应用内部调用；外部仅保留 admin 只读诊断与授权确认。
   - 决议创建：仅内部 Outbox handler 调用；合同回填限定合同经办岗，查询沿对象权限。
   - 配置变更：admin 维护、config_reviewer 复核，服务端校验双人制。
   - 数据中心：仅 admin；审计信息仅 auditor/admin。
4. `copyForUpdate` 使用白名单复制，申请人、申请机构、支行编码、状态、快照、冻结版本等服务端字段永不接受请求覆盖。
5. 通知载荷传递 `orgId/applyBranchCode`，支行岗位使用 `ORG_POST` 或带上下文的接收人解析器，禁止全行角色广播。
6. 为每个对象动作增加允许/拒绝接口测试，至少覆盖 SELF、DEPT、参与人、全量角色、跨支行与直接构造 ID。

**验收标准**：T3-02/T3-03、T10-02~T10-06、T11、N3 自动化；任意跨对象详情、附件、提交、决议和策略写入返回 403；请求体修改归属字段不生效并留审计。

**实施进度（2026-08-12）**：第一批已完成统一申请对象授权、归属字段白名单、附件/关联人/审批详情授权、敏感端点角色收口、外部决议创建关闭、合同经办岗、支行通知隔离和节点指派故障关闭式处理。真实角色接口回归与从零建库均已通过。Ponytail 全仓审查随后移除了从未标注使用的 `@DataScope` SQL 改写链，避免空转基础设施形成错误安全预期；现行授权统一由领域服务和服务端列表过滤执行，详见 `docs/13_Ponytail全项目代码审查与精简记录.md`。权限码细化和更多业务对象统一授权可随 P0-02/P0-03 继续扩展。

### P0-02 冻结并执行产品审批链路

**需求依据**：PRD §3.4、§7.2、D11/D20；详设 §7.2、§8.3、§8.5、§8A.5、§8A.10。

**确认现状**：

- `RateMatrixRouterImpl` 已能按 `ccr_product_route` 生成 `routeChain`，支持 `CHAINED`、`DIRECT_VOTE`、`mandatory_vote`、`vote_condition`、`president_decision`。
- 提交只把 `start_node_code`、`route_code`、`boundary_rate`、`matched_matrix_no`、`dept_code` 写入分项；完整 `routeChain` 只出现在响应中，产品链路 ID/版本也未冻结。
- `ApprovalServiceImpl` 用 `RouteChains.nextNode` 的固定贷款链推导下一节点。贷款产品配置为 `DIRECT_VOTE` 时，提交结果可能为“支行行长→六人小组”，实际审批会推进到部门总经理。
- 贷款审批的权限内判定读取实时 `ccr_node_permission`，没有使用提交冻结的分项边界；配置变更可改变在途申请结论。
- 产品缺少已发布链路时路由器会回退到矩阵路径，详设 §7.2 要求产品停用或未配置链路阻断提交。
- `president_decision` 可配置为 N，表决服务又会把所有通过分项置为 `PRESIDENT_DECISION`，配置语义与执行状态不一致。

**优化方案**：

1. 增加冻结模型 `ccr_pricing_route_plan`，或在 `ccr_pricing_item` 增加 `product_route_id/product_route_version/route_mode/route_chain_json/president_required` 等字段。
2. 提交时校验产品启用、链路已发布、LPR/矩阵/产品边界均有效；将计算出的完整节点序列、每节点边界和版本来源一次性冻结。
3. 审批推进只读取冻结路由计划，通过当前节点下标取得下一节点；停止调用固定 `RouteChains.nextNode` 参与业务决策。
4. 每个节点的权限判定使用冻结边界；节点调价仍同时校验产品硬边界冻结值。实时配置只服务新申请和试算。
5. 明确 `president_required`：若 D20 保持“所有上会通过必经行长”，删除可关闭该步骤的配置项；若允许产品差异，表决状态机必须消费冻结标志。
6. 增加 `DIRECT_VOTE` 贷款、强制上会、条件上会、产品停用、配置发布后在途不变的端到端测试。

**验收标准**：试算、提交响应、数据库冻结计划、普通审批下一节点、表决后节点五处结果一致；配置发布后在途申请链路与边界不变。

### P0-03 强制审批数据只读绑定快照

**需求依据**：PRD D11、§8.1、§8.6；详设 §7.4、§9.5、§12.7。

**确认现状**：

- `ApprovalController.detail` 在没有快照记录时设置 `source=REALTIME`，读取客户、合同、贡献度实时表。
- 集团贡献度在详情开始处直接读取 `dw_contribution_metric` 最新批次。
- 授信协议、他行融资、数仓关联人、借据、机构达成等详情区块仍有 `MAX(data_dt)` 查询路径，未全部通过绑定快照还原。
- `SnapshotController` 暴露了独立创建/追加/冻结能力，且 `ccr_snapshot_bundle.application_id` 只有普通索引；单个申请可以存在多个冻结包。
- 详情注释和返回仍展示质量结果/流程路由卡，与详设 §21.3/§21.4 的“不向业务用户展示质量结果、不展示流程路由卡”存在文档和实现漂移。

**优化方案**：

1. 提交后详情若缺少冻结包或必需数据集，返回明确数据完整性异常并告警，禁止回退实时表。
2. 建立 `ApprovalDetailQueryService`，所有审批资料以 `snapshot_bundle_id` 为唯一入口；人工补录数据也在提交时进入冻结记录或冻结申请版本。
3. 为每个展示区块建立“字段 → 快照 dataset/subject”映射和契约测试，移除详情 Controller 中的实时 SQL。
4. 为 `ccr_snapshot_bundle(application_id)` 增加业务唯一约束，重提新申请自然生成新包；沿用分项通过显式来源快照关系引用旧包。
5. 快照写 API 收敛为应用内部端口，业务前端不直接编排快照步骤。
6. 历史档案同样只读冻结数据；质量明细保留 admin/auditor 技术诊断出口。

**验收标准**：提交后修改所有 `dw_/caps_` 最新批次，审批详情和历史档案内容保持不变；删除/损坏绑定快照时接口失败并告警，响应中不出现 `REALTIME`。

### P0-04 提交状态抢占与数据库幂等

**需求依据**：PRD §8.7；详设 §7.2、§15.3；测试 T2-04、非功能“重复提交”。

**确认现状**：

- `submit` 先读 DRAFT，再用只带 `id` 的更新将状态改为 SUBMITTED，没有 `status=DRAFT + version_no` 条件，也没有检查影响行数。
- 两个并发事务可同时通过 DRAFT 判断，各自创建快照包；`ccr_snapshot_bundle` 没有申请唯一约束。
- 后续 Outbox `event_no` 可去重，但无法回收多余快照和重复路由写入；第二请求也无法稳定返回首请求结果。
- 跨申请“一合同/账户一有效分项”主要靠先查后写，数据库唯一键只约束同一申请，无法兜底跨申请竞态。

**优化方案**：

1. 提交入口接受 `versionNo` 或 `Idempotency-Key`，首先执行条件更新：`WHERE id=? AND status='DRAFT' AND version_no=?`，成功者获得提交所有权。
2. 条件更新失败后重读：已提交则返回冻结结果；版本冲突返回 DATA_VERSION_CONFLICT；非法状态返回 FLOW_STATUS_CONFLICT。
3. 增加“一申请一提交记录/快照包”唯一键；提交结果以提交记录为幂等读取模型。
4. 建立贷款合同/存款账户有效占用表，使用唯一业务键表达跨申请活动占用，终态时释放或标记关闭；避免依赖先查后写。
5. 用 MySQL 真库并发测试同时发起 2~10 个提交，验证一份快照、一组任务、一组 Outbox、所有响应可解释。

**验收标准**：T2-04 自动化；并发重复提交只有一个事务执行副作用，其余请求返回同一 `snapshotBundleId` 和路由结果。

**实施进度（2026-08-12）**：已完成提交 CAS 与快照数据库幂等。提交在所有只读校验之后，以 `id + DRAFT + version_no` 条件更新抢占所有权；失败方通过 `FOR UPDATE` 当前读返回赢家的冻结结果，或明确返回版本/状态冲突，且不会创建快照、执行路由或写 Outbox。新增 `db/20_submission_idempotency.sql`，升级前检测历史重复快照包，数据干净时创建 `uk_snapshot_application(application_id)`；冒烟脚本在事务内验证第二个同申请快照包被 MySQL 拒绝。跨申请贷款合同/存款账户活动占用表和 2~10 个真实 HTTP 请求并发压测仍待后续批次。

### P0-05 修复草稿重建与逻辑删除唯一键

**需求依据**：详设 §10.4、§15.3；测试 T7-04、草稿重复保存。

**确认现状**：

- `BaseEntity.delFlag` 标注 `@TableLogic`，`mapper.delete` 会将记录更新为 `del_flag=1`。
- `saveDraft` 通过 `deleteChildren` 后重建成员、分项、合同/账户关系。
- `ccr_application_member` 唯一键为 `(application_id, member_customer_no)`，没有删除标记；集团草稿删除后以同成员重建会撞旧逻辑删除行。
- 合同/账户关系唯一键包含固定值 `del_flag`，同一业务键最多容纳一条已删除记录；再次保存相同业务键时删除阶段或插入阶段会产生冲突。
- 当前测试全部使用 Mockito，没有执行 MySQL 唯一约束，无法捕获该问题。

**优化方案**：

1. 草稿子表采用差量 upsert：稳定业务键匹配后更新，新增项插入，缺失项逻辑删除，避免每次全量换 ID。
2. 若保留重建策略，删除标识使用可重复的删除时间/删除批次，或采用生成列 `active_business_key` 仅对活动行唯一；不要用布尔删除位承载多版本历史。
3. 为集团成员、合同关系、账户关系增加 MySQL 集成测试，覆盖保存两次、删除后恢复、重提继承、并发保存。
4. 对已有逻辑删除重复数据提供迁移前检查 SQL，再创建新约束。

**验收标准**：同一草稿连续保存三次、删除后恢复相同成员/合同/账户均成功，历史行可追溯且只有一条活动记录。

**实施进度（2026-08-12）**：已完成。保留现有草稿全量重建语义，新增 `db/21_draft_active_unique_keys.sql`：三张子表增加 `active_application_id` 存储生成列，活动行映射申请 ID、历史行映射 NULL；唯一索引分别约束成员客户号、合同业务键和非空账户哈希。升级前检查既有活动重复，发现异常时通过 `SIGNAL` 中止迁移；脚本可重复执行。`./dev smoke` 在 MySQL 事务内对三类业务键执行两次逻辑删除、第三次恢复，并确认第二条活动重复记录被唯一键拒绝，连接退出后回滚测试数据。

### P0-06 落实 D21 客户级承诺聚合

**需求依据**：PRD G2、D19、D21、§8.3；详设 §13。

**确认现状**：

- 终态串联按申请创建一份 `ccr_commitment_plan`，并以 `application_id` 判重。
- 同一客户的不同申请会生成不同计划，各计划分别保存自己的指标目标。
- `evaluatePlan` 为每个计划读取同一客户同指标的最新数仓实际值，并分别除以本计划目标。
- PRD 要求将同一客户跨申请/担保类型的承诺按指标聚合为客户级分母；当前模型会重复使用实际值，并影响风险等级、提醒和机构达成率。
- `OTHER` 手工描述采用覆盖更新，无法满足“留痕”语义。

**优化方案**：

1. 保留申请承诺明细作为不可变来源，引入客户指标承诺台账/聚合视图，键至少包含客户、指标、有效周期、机构和状态。
2. 评估时先聚合所有已批准且有效的承诺明细，再与一次数仓实际值比较；结果记录保存参与聚合的申请/决议明细和计算版本。
3. 集团共享/固定分配分别定义客户集合与分母，防止集团和成员重复计算。
4. 机构达成率直接复用同一聚合服务，排除 `OTHER`，避免页面 SQL 和定时任务各算一套。
5. `OTHER` 跟踪改为追加式日志表，保留作者、时间、内容和关联材料；指标表可保存最新摘要。
6. 增加“同客户两申请同指标”“一申请多担保类型”“重提沿用”“承诺到期/终止”“集团成员”参数化测试。

**验收标准**：同一客户两笔目标 100、200，实际 150 时客户级达成率为 50%，数仓实际值只计一次；机构报表、客户详情、月报和预警结果一致。

## 5. P1：上线前完成的可靠性与治理

### P1-01 配置发布事务与并发控制

- 规则集、LPR、矩阵、产品边界、产品链路的发布方法多位于 Controller，包含“停用旧版 → 发布新版 → 写变更日志 → 清缓存”等多步写入，普遍没有统一事务。
- 状态变迁主要先查后改，缺少 `status + version_no` 条件；并发复核可能产生多个生效版本或半发布状态。
- 建议提取配置应用服务，每类发布使用单事务、状态 CAS、数据库唯一有效约束；事务提交后通过事件刷新缓存。双人复核比较使用 `Objects.equals`，避免 Long 拆箱/引用语义混乱。

### P1-02 Outbox 租约、僵尸事件恢复与运维重放

- 消费器以 PENDING→PROCESSING 认领；扫描只查询 PENDING。进程在 handler 执行期间崩溃后，PROCESSING 事件不会自动回收。
- `FlowStartOutboxHandler` 用“先查 flow_instance，再创建”实现幂等，而 `flow_instance.business_id` 没有唯一约束，并发消费者仍可能重复创建。
- 建议增加 `claimed_by/claimed_at/lease_until`，扫描时回收超时 PROCESSING；成功和失败更新均带 claim token。为各 handler 增加数据库业务唯一键，并提供 admin 查询、重放、跳过、告警确认接口。

### P1-03 节点指派与边界配置安全降级

- `NodeAssigneeResolver` 捕获数据库异常后返回空集合，调用方把空集合解释为“不限制”，基础设施故障会扩大审批权限。
- `ApprovalServiceImpl.inNodePermission` 在权限记录缺失时返回可终审，也属于宽松降级。
- 建议区分“确实未配置”和“解析失败”；核心审批节点缺配置/查询失败采用 fail-closed，返回配置异常并告警。只有明确发布的兜底角色规则可以放行。
- **实施进度（2026-08-12）**：节点指派查询异常已返回 `ERROR` 并阻断业务操作与对象详情；真实无配置仍保留角色兜底。其余配置域的依赖故障区分仍待后续批次统一。

### P1-04 审计轨迹不可降级丢失

- 提交审计 `writeSubmitAudit` 捕获异常后继续提交；Warm-Flow 轨迹也采用尽力而为。
- 核心法律/审计事实应与状态变迁同事务写入 `ccr_approval_action/ccr_audit_log`；展示型工作流轨迹可以异步重建。为审计日志增加请求 ID、渠道、IP/设备、前后状态、冻结版本和幂等键。

### P1-05 附件生产化

- 当前附件内容直接存 MEDIUMBLOB，缺少对象授权、扩展名/MIME 白名单、恶意文件扫描、内容哈希和下载审计。
- 建议接入行内对象存储，数据库保存元数据、对象键、SHA-256、扫描状态；上传后隔离扫描，通过后方可提交/下载。保留演示 BLOB 适配器用于本地测试。

### P1-06 测试金字塔与交付门禁

- 当前约 274 个测试注解集中在 Mockito 单测；`ccr-message`、`ccr-workflow` 无模块测试。
- `./dev verify` 在 `ccr-approval` 失败：生产代码调用 `resolveUserIds(node, org, dept)`，两个测试仍打桩旧的两参数重载。
- 后端失败后 `ccr-snapshot`、`ccr-admin` 未执行；CI 当前只跑 Maven test 和前端 build，缺少真库、接口鉴权、并发与 E2E。
- 建议分层建设：
  1. 单测：状态机、路由、聚合计算。
  2. MySQL/Redis 集成测试：唯一键、逻辑删除、事务回滚、Outbox 租约、并发投票/提交。
  3. MockMvc 契约测试：角色、对象权限、DTO、幂等键、错误码。
  4. Playwright：贷款、存款、集团、重提各一条核心路径。
  5. CI 门禁：`./dev verify` → 隔离 Compose 集成测试 → E2E/依赖审计；任何阶段失败停止发布。

业务状态目前由应用/分项状态机驱动，Warm-Flow 同时创建实例、任务和手工轨迹，存在双重事实源。建议明确：领域状态和 `ccr_approval_action` 是业务事实，Warm-Flow 只承担任务分派或只承担展示轨迹，选定一种职责；通过领域事件同步派生状态，并提供差异巡检任务。

### P2-03 查询性能与分页

- 审批详情和历史档案含大量顺序 SQL 与循环查询；列表接口多处固定 LIMIT 或无分页。
- 建议建立按页面契约的批量查询，消除客户/成员/指标 N+1；对申请、待办、决议、消息、承诺、审计统一分页。
- 为 `application_id/status/current_node_code/apply_branch_code`、Outbox 扫描、评估最新期、通知收件人等真实查询补组合索引，并以 `EXPLAIN ANALYZE` 验证。
- 为审批详情、列表、提交建立 P95 基线，对照需求 ≤2s/≤5s。

### P2-04 前端依赖、拆包与自动化

- `npm audit` 报告 2 个漏洞：Vite 直接依赖 high、esbuild 间接依赖 moderate；修复建议跨 Vite 主版本，需要单独升级验证。
- 当前主入口 JS 约 1.25 MB，gzip 约 405 KB；建议按 Element Plus 组件、Excel、图标和页面路由拆包，分析首屏依赖。
- 前端当前只有 build，无组件测试和 E2E。优先为申请步骤校验、提交确认、审批动作、会话过期增加 Vitest/Playwright。

### P2-05 文档与实现同步

- PRD §7.2 写存款/保证金直接上会，§7.3 写高于期限上限才上会；详设 §21.1 又写未超上限由支行行长终审。
- PRD 当前贡献度建议最多 2 天，近期实现与详设统一使用 3 天。
- README 仍写“纠偏完成”和下一步 M3~M8，测试方案仍登记 221 例全绿，当前代码约 274 个测试注解且验证失败。
- 详情是否展示质量结果/路由卡在早期章节、修订章和代码之间不一致。

建议建立“决策编号 → 权威条款 → 状态机/字段/API → 自动化用例”追踪矩阵；修订正文而只在文末追加覆盖说明的方式容易让实现人员读取到旧口径。
