## 〇、已确认决策

| # | 决策 | 结论 |
|---|---|---|
| D-1 | 提交链路 | 两段式:`saveDraft`(DRAFT 反复保存)+ `submit`(终态:校验→差异确认→冻结→路由→发起) |
| D-2 | 差异确认 | `submit-check` 返回"最新批次 vs 预览"差异,客户经理确认后才 `submit` |
| D-3 | 提交失败 | 原子事务回滚到 DRAFT;Outbox 消费失败停 SUBMITTING 告警 |
| D-4 | 承诺计划 | 决议签发(ISSUED)即生成 |
| D-5 | 决议 | 行长同意后自动签发 |
| D-6 | 金额档 | 集团按综合授信总额;单户按申请金额 |
| D-7 | 重提 | 全部重新审批(不沿用原决议) |

## 一、状态机(字段级)

### 1.1 主申请状态 `ccr_application.status`

| 状态 | 描述 | 可进入动作 | 出口 |
|---|---|---|---|
| DRAFT | 草稿,可编辑 | saveDraft | →SUBMITTED |
| SUBMITTED | 已提交/校验快照 | submit 中 | →ROUTING |
| ROUTING | 路由中(审批中) | 分项全部进入审批 | →APPROVED_LEVEL/VOTING/RETURNED/CLOSED |
| APPROVED_LEVEL | 权限内已批(全部分项终审) | 聚合 | →FINAL |
| VOTING | 上会表决中 | 分项进入小组 | →COMMITTEE_PASS/REJECTED |
| COMMITTEE_PASS | 小组通过(待行长) | 计票≥4 | →PRESIDENT_DECISION |
| PRESIDENT_DECISION | 行长决策中 | 行长处理 | →FINAL/VETOED |
| FINAL | 终态(已批/已否) | — | 终态 |
| VETOED | 一票否决 | — | 终态 |
| RETURNED | 退回 | 审批人退回 | →DRAFT(重提) |
| REJECTED | 否决 | — | 终态 |
| CLOSED | 关闭 | 人工 | 终态 |

### 1.2 定价分项状态 `ccr_pricing_item.status`(逐担保分项独立)

`DRAFT→SUBMITTED→ROUTING→(APPROVED_LEVEL→FINAL | VOTING→COMMITTEE_PASS→PRESIDENT_DECISION→FINAL/VETOED | REJECTED | RETURNED)`

**终态守卫**:REJECTED/VETOED/FINAL 不允许回到 DRAFT;仅 RETURNED→DRAFT。

## 二、提交链路(核心,分接口设计)

### 2.1 接口总览

| # | 方法 | 路径 | 用途 | 状态 |
|---|---|---|---|---|
| S1 | POST | `/ccr/applications` | 创建草稿 | DRAFT |
| S2 | PUT | `/ccr/applications/{id}` | 保存草稿 | DRAFT |
| S3 | POST | `/ccr/applications/{id}/route-preview` | 逐分项路由预览(不落终态) | DRAFT |
| S4 | POST | `/ccr/applications/{id}/submit-check` | 最新批次差异 + 质量/硬边界预检 | DRAFT |
| S5 | POST | `/ccr/applications/{id}/submit` | 正式提交(事务) | DRAFT→SUBMITTED→ROUTING |
| S6 | POST | `/ccr/applications/{id}/reapply` | 关联重提(新申请,全部重审) | 原终态,新 DRAFT |

### 2.2 S3 route-preview 详细

**请求**:`{ lprVersionId?: Long, asOfDate?: LocalDateTime }`
- 未传则取当前生效 LPR 版本。

**逻辑**:
1. 校验申请为 DRAFT。
2. 加载分项列表,逐项调 `RateMatrixRouter.calcRoute(input)`。
3. `input` 构造:`businessBigType`(按 business_type+loanType)、`newOrExisting`、`customerType`、`amount`(金额档判定见 D-6:集团取 `dw_group_credit.approved_total_amount`,单户取分项 pricing_amount)、`termValue/termUnit`、`guaranteeType`、`requestedRate`。
4. 汇总返回。

**响应** `RoutePreviewResponse`:
```json
{
  "applicationId": 1,
  "groupCreditTotal": 10000.00,      // 集团授信总额(金额档基准)
  "lprVersionId": 9601,
  "lprVersionCode": "LPR_V1",
  "items": [{
    "pricingItemId": 101, "pricingItemNo": "PI-001", "memberCustomerNo": "MEMBER_A",
    "productCode": "LOAN_A", "requestedRate": 3.40, "rateDirection": "LOWER_BETTER",
    "startNodeCode": "BRANCH_MANAGER", "finalNodeCode": "BRANCH_MANAGER",
    "matchedRuleCode": "M-001", "message": "申请利率≥岗位下限,支行行长终审"
  }]
}
```

### 2.3 S4 submit-check 详细(差异确认前置)

**逻辑**(事务外只读):
1. 锁定申请 `version_no`(乐观锁)。
2. 读取 `application.dataBaselineJson`(草稿保存/上次预览时各数据集 data_dt 基线)。
3. 查询各数仓数据集**最新成功批次 data_dt**(`dw_*/caps_*` 按 MAX(data_dt)),与基线比对 → `diffs`。
4. 质量预检:复用快照 7 条规则(PASS/WARN/BLOCK,只读不落库)。
5. 硬边界预检:逐分项 `RuleEngine.checkHardBoundary`(贷款≥/存款≤)。
6. `blockSubmit = 存在 BLOCK 级`。

**响应** `SubmitCheckResponse`:
```json
{
  "applicationId": 1,
  "baselineSource": "FILL_VIEW",       // 或 LATEST
  "diffs": [{"datasetCode":"caps_corp_cust_basic_info","baselineDataDt":"2026-08-05","latestDataDt":"2026-08-06","changed":true}],
  "qualityPrecheck": [{"ruleCode":"CUSTOMER_SNAPSHOT_REQUIRED","level":"WARN","message":"..."}],
  "hardBoundaries": [{"pricingItemId":101,"boundaryRate":3.0,"requestedRate":2.8,"pass":false}],
  "blockSubmit": true
}
```

### 2.4 S5 submit 详细(核心事务)

**请求**:`{ confirmDiff: Boolean, idempotencyKey?: String }`(`confirmDiff=true` 表示差异已确认)。

**事务步骤**(`@Transactional`,任一失败整体回滚):
1. `selectById` 校验状态=DRAFT;`version_no` 乐观锁。
2. **最终数据校验**:取最新批次重新执行 7 条质量规则 + 硬边界;`BLOCK` → 抛 `QUALITY_BLOCK`。
3. **差异确认**:若与基线存在 `changed=true` 的差异且 `confirmDiff!=true` → 抛 `DATA_EXPIRED`(前端应已确认,二次兜底)。
4. **冻结 LPR/规则**:调 `ccr-rule` 取当前生效 LPR 版本 → `lpr_version_id`;规则集(生效) → `rule_set_version_id`;写 `route_as_of_date`。
5. **创建快照包**:`SnapshotService.submitSnapshot(applicationId, records)` → `snapshot_bundle_id`,FROZEN。
6. **逐分项路由**:对每个 `pricing_item`,构造 `MatrixRouteInput` → `rateMatrixRouter.calcRoute` → 写 `route_code`、`current_node_code`(起始节点)。
7. **状态**:application → SUBMITTED→ROUTING;分项 → ROUTING。
8. **写 Outbox**:`ccr_outbox_event`(event_type=FLOW_START,payload=分项+起始节点+流程定义版本)。
9. 返回 `SubmitResponse`。

**响应** `SubmitResponse`:
```json
{
  "applicationId": 1, "applicationNo": "CCR20260806xxxx", "status": "ROUTING",
  "snapshotBundleId": 501, "lprVersionId": 9601, "ruleSetVersionId": 9001,
  "routeAsOfDate": "2026-08-06T10:00:00", "submitTime": "2026-08-06T10:00:00",
  "submitted": true,
  "items": [{"pricingItemId":101,"pricingItemNo":"PI-001","status":"ROUTING","startNodeCode":"BRANCH_MANAGER","routeCode":"R001"}]
}
```

### 2.5 S6 reapply 详细(D-7 全部重新审批)

**逻辑**(新申请 + 新分项,不沿用原决议):
1. 原申请必须终态(REJECTED/VETOED/FINAL)。
2. 创建新申请:`source_application_id`=原申请;`customer_scope/customer_no/group_no/guarantees/commitments` 复制自原申请(可编辑)。
3. **全部新建分项**:原分项 → 新分项(`source_pricing_item_id` 关联),status=DRAFT,`inherit_flag='N'`。
4. 快照/承诺**不复制**(新提交时重建);人工补录他行融资按 D14 继承引用。
5. 原申请/原分项保持终态,不回 DRAFT。

### 2.6 差异确认前端交互

`submit` 按钮 → 调 S4(submit-check)→ 弹窗展示 diffs/blockSubmit:
- 无差异、无 BLOCK → 直接确认提交(S5)。
- 有差异 → 列出"字段/预览值/最新值",客户经理点"确认并提交"(S5,confirmDiff=true)。
- 有 BLOCK → 阻止,提示原因。

## 三、权限矩阵路由(算法级)

### 3.1 `ccr_rate_matrix` 字段

`matrix_no / business_big_type / new_or_existing / customer_type / amount_tier(LT_5000|GE_5000) / term_tier(1Y|3Y|5Y) / product_code / guarantee_type / start_node_code / dept_code / boundary_type(RATE|SPREAD) / boundary_min_rate / boundary_bp / bp_sign / lpr_term / priority / status / effective_from / effective_to / publish_by / review_by`

### 3.2 边界利率计算(伪代码)

```text
func boundaryRate(row, input, lprMap):
    if row.boundary_type == "SPREAD":           # 存量降幅
        base = input.originalRate
        b = base - row.boundary_bp * 0.01
        return max(b, row.boundary_min_rate)     # 不低于绝对下限
    if row.boundary_bp != null and row.lpr_term != null:
        lpr = lprMap[row.lpr_term]               # "1Y"→lpr1y, "5Y"→lpr5y
        b = lpr ± row.boundary_bp * 0.01         # 按 bp_sign
        return max(b, row.boundary_min_rate)
    return row.boundary_min_rate                 # 纯绝对值
```

### 3.3 链式判定(伪代码)

```text
# 贷款(LOAN_*):从低权限到高权限,首个 rate≥boundary 即终审
rows = matchAndSort(input)   # 按业务维度过滤,priority 升序
for row in rows:
    if row.start_node_code == "SIX_PEOPLE_GROUP": continue   # 小组兜底
    b = boundaryRate(row, input, lpr)
    if b == null: return row.start_node_code                  # 无边界=权限内(D3)
    if input.requestedRate >= b: return row.start_node_code
return "SIX_PEOPLE_GROUP"     # 全部不满足→上会

# 存款/保证金(DEPOSIT/MARGIN):一律直接上会(D16b),行边界为上限
return "SIX_PEOPLE_GROUP"
```

### 3.4 金额档判定(D-6)

```text
if input.businessBigType == "LOAN_PUBLIC" and newOrExisting == "NEW":
    if group场景: amount = dw_group_credit.approved_total_amount   # 集团授信批复总额
    else:          amount = 分项 pricing_amount                      # 单户申请金额
    tier = amount >= 5000 ? "GE_5000" : "LT_5000"
```

### 3.5 互斥与连续性

- 同维度(同矩阵号系列)同优先级多命中 → 抛 `RULE_MULTI_MATCH`。
- 发布前 `validateContinuity` 按维度组检查区间连续、无空档、无重叠。

### 3.6 部门归属与部门分流(§D16a)

矩阵行 `dept_code` 为**机构部门编码**(统一为 GSB=公司金融部 / SXSB=授信评审部 / LSB=零售金融部,经 `ccr_sys_dept.dept_code` 关联机构,消除独立第三套编码)。部门改名只改 `dept_name`,审批流不受影响;改部门编码需同步矩阵与指派配置(配置数据)。

| 业务口径 | business_big_type + new_or_existing | dept_code |
|---|---|---|
| 对公存量 → 公司金融部 | LOAN_PUBLIC + EXISTING | GSB |
| 对公新增授信 → 授信评审部 | LOAN_PUBLIC + NEW | SXSB |
| 个人经营性贷款 → 零售金融部 | LOAN_PERSONAL(EXISTING/NEW) | LSB |

路由计算后 `dept_code` 透出到 `RouteResult.deptCode`,提交时冻结到分项 `ccr_pricing_item.dept_code`(§2.4/§7.2)。部门分流分的是**节点内处理人**——链路 `BRANCH_MANAGER→DEPT_GENERAL_MANAGER→VICE_PRESIDENT→SIX_PEOPLE_GROUP` 不变,部门总经理/分管行长节点按分项 dept_code 解析处理人(见 §4.0)。

## 四、审批 / 表决 / 行长决策(状态级)

### 4.0 节点指派与部门解析(§5.5.1/§D16a)

`ccr_node_assignee` 四层解析命中即止:PERSON(工号)→ GROUP(角色集合)→ DEPT(机构)→ ROLE(角色兜底)。部门类节点配置 `assignee_type=DEPT`,`assignee_code` 用「机构dept_code:角色码」语法(如 `GSB:dept_gm`)——按分项 `dept_code` 精确匹配机构,取该机构下指定角色启用用户;无「:」维持原 org_code 前缀匹配(兼容存量配置)。换总经理/加人只改机构角色配置,不依赖具体工号。

**分管行领导一人分管多部门**:新增 `ccr_dept_vp(dept_code, vp_user_id, ...)` 映射表(一个部门可配多个分管行长、一个分管行长可分管多个部门,纯配置)。VICE_PRESIDENT 节点且分项 dept_code 非空时按映射解析;未命中或无 dept_code 回落原四层/角色兜底(向后兼容)。

- 待办过滤 `filterByNodeAssignee`、权限校验 `guardNodeAssignee` 均按分项 `dept_code` 解析部门类节点(DEPT_GENERAL_MANAGER/VICE_PRESIDENT)处理人,非部门节点传空走原逻辑。
- 越权审批被 `guardNodeAssignee` 拦截(「已配置指定审批人,当前登录人不在指派范围内」)。

### 4.1 普通审批 approve

```text
approve(itemId, nodeCode, operatorId, adjustRate?, comment):
    item = get(ROUTING)
    bizType = application.businessType            # LOAN/DEPOSIT
    perm = node_permission(nodeCode, bizType)     # 岗位权限边界
    if adjustRate != null: saveAdjustment(...); item.currentApprovalRate = adjustRate
    inPerm = (LOAN: rate >= perm.min) or (DEPOSIT: rate <= perm.max)
    if inPerm:
        item.status = APPROVED_LEVEL; item.finalRate = rate     # 终审,不经行长
    else:
        next = nextNode(nodeCode)                  # BM→DGM→VP→GROUP
        if next == null: item.status = APPROVED_LEVEL
        else: item.currentNodeCode = next          # 上送
    insert ccr_approval_action(APPROVE)
    if 全部分项 APPROVED_LEVEL: application.status = APPROVED_LEVEL
```

### 4.2 表决(逐分项独立计票)

| 动作 | 逻辑 |
|---|---|
| 创建批次 | `createRound(appId, pricingItemIds, 6名委员)`:round_no 递增;批次 VOTING;分项→VOTING;委员 assignment(A-F) |
| 投票 | `submitBallot(roundId, itemId, voterId, choice)`:一人一票唯一(`uk_ballot`);提交后不可改;幂等键 |
| 计票 | 全部 6 票提交后:`approve>=4 → COMMITTEE_PASS`,否则 `REJECTED`;写 `ccr_vote_result`;批次→PASSED/FAILED |

### 4.3 行长决策 + 自动决议(D-5)

```text
presidentDecision(itemId, decision, opinion, presidentId):
    voteResult 必须 PASS(COMMITTEE_PASS)
    同意 → item.status=FINAL;finalRate=currentApprovalRate
    否决 → item.status=VETOED(final_reason=opinion)
    # 自动签发决议(D-5):
    resolution = ResolutionService.createResolution(itemId, finalRate,
                    carrierType, carrierBusinessKey, effectiveFrom, effectiveTo, "PRESIDENT_APPROVED")
    # 自动生成承诺计划(D-4):
    outbox(NOTIFY=RESOLUTION_CREATE) → 消费:CommitmentService.createPlan(resolution 冻结指标)
```

## 五、决议与执行核验

### 5.1 决议签发

- `resolution_no = RES+yyyyMMdd+8位随机`;`pricing_item_id` 唯一;status=ISSUED;execution_status=CONTRACT_PENDING。
- 幂等:同分项已存在决议 → 抛 `IDEMPOTENCY_REPEAT`。

### 5.2 合同回填 `contract-bind`

七项一致性校验(任一失败抛 `BAD_REQUEST` + 明细):
1. 客户:回填合同客户 == 分项定价客户
2. 产品:合同产品 == 分项 product_code
3. 金额:合同金额(余额)与分项定价金额匹配(容差)
4. 期限:合同期限与分项 term 匹配
5. 担保主类型:合同担保 == 分项担保组合主类型
6. 最终利率:executionRate == resolution.finalRate
7. 签署日期:在决议有效期内

存量调息强制 `supplement_agreement_no` 非空。幂等:同合同号+同利率重复 → 返回原记录。

### 5.3 两级核验 `execution-check`

```text
level1 = (executionRate == resolution.finalRate)
level2 = 合同下全部有效借据(dw_loan_note_snapshot 最新批次)执行利率 == 合同利率
无借据数据 → level2 = WARN 通过(不误判)
差异写 difference_json;异常 → execution_status=RECONCILE_EXCEPTION
   → 通知客户经理+合同经办岗(message_key=RECONCILE_EXCEPTION:决议号:类型:ID 去重)
通过 → EXECUTED
```

## 六、承诺跟踪

### 6.1 计划生成(决议签发即生成,D-4)

- 按冻结承诺指标建 `ccr_commitment_plan`(PENDING)+ `ccr_commitment_metric`(calc_version 冻结)。
- 集团 FIXED_ALLOCATION 必填 `ccr_commitment_member_alloc`(合计=集团目标);GROUP_SHARED 不校验合计。
- 冻结跟踪策略版本(`ccr_tracking_policy_version`)。

### 6.2 评估公式(§11.3)

```text
INCREMENT     = (当前值 - 基线值) / 承诺新增值
TARGET_BALANCE= 当前值 / 目标值
CUMULATIVE    = 期间累计实际 / 期间目标
实际值口径(D21): dw_contribution_metric 按 cust_no+metric_code 最新批次,优先 CONTRIBUTION_AMOUNT
阈值从冻结策略版本读;计划状态由全部分项指标结果聚合
```

## 十三、缓存设计(Redis)

### 13.1 总体架构

- **唯一入口**:`CcrCacheUtil`(ccr-common)封装 Redis 读写;业务代码一律走它,不直接触 redisTemplate。
- **统一前缀** `ccr:`;key 约定 `ccr:cfg:*`;TTL 写入带 ±20% 随机抖动防雪崩;空值占位防穿透;Redis 异常自动降级直查库,不影响业务。
- **失效信号**:`ccr:cfg:v` 全局版本号,配置发布/变更后 `increment`,读方比对版本失效重建。
- **注解 AOP**:`@CcrCacheable`/`@CcrCacheEvict` + `CacheFallbackAdvice`(占位符 `{i}` 解析、命中短路、未命中回填、evict 前置失效)。

### 13.2 缓存项定义(v2:DB 动态管理)

**演进**:v1 代码写死 3 项(`CacheItem` 枚举:lpr-effective 精确 / matrix-effective 精确 / rate-limit 前缀),yml `ccr.cache.items` 覆盖 TTL/开关;**v2 升级为 DB 完整定义表** `ccr_cache_config`,管理员可动态增删改缓存项,yml 链路废弃(DB 唯一事实源)。

**表结构**(`db/14_cache_config_upgrade.sql` 幂等升级,`uk_cache_key` 精确 key 唯一):

| 列 | 说明 |
|---|---|
| item_key(UNI) | 缓存项编码,如 dw-table:contribution |
| cache_key | 精确 Redis key(与 key_pattern 二选一) |
| key_pattern | key 前缀(前缀匹配,如 ccr:cfg:rate-limit:) |
| description | 展示描述 |
| data_loader | 数据加载器编码(DW_TABLE;空=业务代码写缓存) |
| loader_param | 加载器参数 JSON(如 {"table":"dw_x","limit":5000}) |
| is_system | 内置标记 Y/N;Y 不可删、不可改 key |
| enabled / ttl_seconds | 写入开关 / TTL |

**匹配规则** `CacheConfigHolder.matchDef(key)`:先精确 `cacheKey.equals` 命中,再取最长 `keyPattern` 前缀命中;未命中 → 默认启用 + 显式 TTL/全局默认。确定性,不依赖 DB 顺序。

**内置项保护**:种子 3 项 is_system='Y',可改 enabled/ttl/description/loader,**不可删除、不可改 cacheKey/keyPattern**(后端 400 + 前端禁用)。

**物理删除**:`physicalDeleteByItemKey`(@Delete),规避逻辑删除 + `uk_cache_item` 唯一键导致同 itemKey 无法重建。

### 13.3 配置化刷新

- **`CacheDataLoader` 接口**(ccr-common):`code()/name()/load(loaderParam)`;bean 收集 `@Resource Map<String,CacheDataLoader>`(注入 key 为 bean 名,查找按 `code()` 遍历)。
- **`DwTableCacheLoader`**(ccr-application):code=DW_TABLE;解析 `{"table":"dw_x","limit":5000}` → 表名白名单校验(`[A-Za-z0-9_]+` 且 dw_/caps_ 前缀,防 SQL 注入) → `SELECT * FROM t WHERE data_dt=(SELECT MAX(data_dt) FROM t) LIMIT n`。
- **触发**:管理员手动 `POST /system/cache-configs/{itemKey}/refresh`(返回写入行数);定时 `@Scheduled(cron="${ccr.cache.data.refresh-cron:0 0 * * * *}")` 遍历启用+loader 非空的精确 key 项逐个执行,单项失败不阻断。
- **约束**:带 loader 的缓存项必须为**精确 key 类型**(前缀型无法确定写入目标,校验 400)。
