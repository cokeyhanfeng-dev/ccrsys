# 企业微信节点提醒

## 1. 提醒范围

本次接入审批节点到达提醒：首次提交到首节点；普通审批上送至支行行长、管理综合支行行长、部门总经理、分管行长、秘书岗；六人表决建批；表决委员替补；表决通过后待行长决策。各节点沿用现有业务状态，不改变审批权限或计票规则。

- 普通节点复用 `NodeAssigneeResolver`，携带申请人机构、冻结部门归属；解析失败进入 Outbox 重试，不全行群发。部门节点及管理综合支行节点无有效处理人时告警。
- 小组提醒仅面向该批冻结名单中的启用且尚未提交席位，替补提醒仅面向替补本人；建批事件与替补事件共用批次、用户、渠道去重键。
- 行长决策根据分项 `PRESIDENT_DECISION/COMMITTEE_PASS` 状态判定，同时要求接收人具备 president 主角色与有效节点指派约束。
- 消费节点事件时已流转完成的待办直接略过。进入发送队列后的提醒可能与用户操作交错；页面仍以实时待办及后端权限为准。
- 站内信持续保留；企业微信按独立开关追加渠道记录。新版本从部署后的业务流转开始生成提醒，不批量补发历史待办，不把承诺预警或普通通知自动转为企微消息。

默认文案：`【客户利率审批系统】定价申请 TEST001 已到达“部门总经理审批”节点，请登录系统处理。`
不发送客户明细、利率、投票内容及身份票据；当前仅纯文本，无附加登录链接。

## 2. 网关契约

部署方配置最终完整 URL，路径按提供的网关记录为 `/common/message/send/ent/wechat`。

- 方法：`POST`，`Content-Type: application/json; charset=UTF-8`。
- 请求头复用统一认证 `CCR_INTEGRATION_AUTH_APP_ID`、`API_KEY`、`APP_ID_HEADER`、`API_KEY_HEADER`；默认头名 `X-App-Id` 与 `apikey`。
- 每次 HTTP 尝试生成新的 `X-Sequence-No`（32 位 UUID）和 `X-Timestamp`（与单点登录相同的 `yyyy-MM-dd HH:mm:ss`）。
- 请求体严格按网关示例为 `{ "toUser": "02300001", "text": "提醒正文" }`。`toUser` 从本地用户 ID 查询 `ccr_sys_user.username`，按字符串保留前导零；不使用用户雪花 ID、姓名、手机号或匿名席位号。不添加示例未包含的 `appCode` 参数。
- 仅允许单账号，不接受 `@all`、多人分隔符；本地用户须启用且未删除。正文限制 2048 UTF-8 字节，响应读取上限 64 KiB。
- HTTP 200 且 JSON 顶层 `code` 为字符串 `"200"` 或数值 `200` 才确认成功。业务失败、字段缺失、非 JSON、非 200、重定向、超时均记发送失败。禁止跟随重定向，响应及凭证不进入应用日志。
- 超时复用统一认证配置，连接默认 3 秒、读取默认 10 秒，单项最大 30 秒；企业微信启用独立于登录开关，使用同一组凭证。

## 3. 部署

在服务器部署环境文件中沿用已有认证 APP_ID/API_KEY 及头名，再新增以下两项。地址为示例，需替换为实际完整网关 URL：

```dotenv
CCR_INTEGRATION_WECHAT_ENABLED=true
CCR_INTEGRATION_WECHAT_URL=https://gateway.internal.example/common/message/send/ent/wechat
```

发送默认关闭，URL 默认空；启用前确认本地 username 与企微网关 `toUser` 的绩效码映射。两套 Compose 均透传变量。真实凭证与连接信息只存部署环境文件，不写代码、镜像和版本库。

配置更改需按现有部署流程重建后端容器以加载环境；普通 restart 不会加载新的环境变量。若原部署使用热替换 Jar，重建后按发布手册重新部署新版 Jar。发布时使用含新增环境变量透传的 Compose 文件。无需 SQL、端口变更或重建数据卷。

隔离栈联调应保持 `CCR_INTEGRATION_WECHAT_ENABLED=false`；模拟网关测试使用虚构人员与本机 HTTP 服务。真实发送仅在部署侧确认测试收件人后进行。

## 4. 可靠性与运维

1. 提交、上送、建批、替补和计票在原业务事务中写入 `NOTIFY` Outbox，事件写失败随业务事务回滚。沿用 Outbox 唯一事件号、30 秒扫描、有限重试、处理中恢复与终态告警。
2. 消费者按人员及渠道生成不超过 64 字符的 `message_key`；数据库现有唯一键阻止并发重复插入。SYSTEM 与 WECHAT 各一条；普通用户的电脑端及移动消息列表只显示其中的站内提醒，管理员/审计保留完整渠道日志。失败时不重复发送已成功的其他人员记录。
3. 企业微信日志初始为 `PENDING`，不在业务事务内调用外部 HTTP。通知任务每 30 秒扫描，通常在节点到达后两个扫描周期内发送，实际延迟受队列和网关耗时影响。
4. 发送前数据库条件更新认领为 `PROCESSING`，同时持久化尝试次数。正常失败间隔至少 2 分钟再试；处理中断超过 5 分钟可重新认领。默认最多 **3 次总尝试（含首次）**，由 `ccr.message.max-retry` 配置。最终状态更新带本次尝试号，阻止旧发送者覆盖新结果。
5. 成功置 `SUCCESS/SENT`，耗尽次数置 `FAILED` 并记录 ERROR 告警，由已有运行日志采集入库。管理员可通过通知日志查询和 `/ccr/notification/logs/process` 触发一次符合条件的处理；终态失败不会无限重试，需人工核查接收账号、配置及网关结果。
6. 网关示例未提供服务端幂等键或结果查询能力。若网关已发送成功但响应丢失，或成功后本地进程中断，恢复重试可能造成重复送达；当前保证本地事件与记录幂等，不承诺外部严格一次送达。后续如网关支持幂等键，再补双方协同去重。

本次复用现有表，`send_status` 新增应用语义 `PROCESSING`，不改变表结构。原有通知日志访问控制不变，普通用户仅查询自己的通知，手工发送/处理仍限管理员。

## 5. 验证与联调

自动回归覆盖：业务事件产生、建批和替补冻结名单、部门/管理行/行长隔离、过期节点、事件重放与人员渠道去重、提交事务内仅落队列、数据库认领竞争、恢复与尝试上限；本机 HTTP 模拟网关覆盖请求方法、两字段正文、绩效码前导零、复用/自定义请求头、字符串及数值成功码、业务失败、HTTP 错误、重定向、超时、过大响应、账号和文本边界。

验证入口：`./dev backend-test`、`./dev app-up`、`./dev smoke`。实际执行结果见本日期开发改动记录。

真实网关待验收：使用指定测试人员完成首节点→上送→小组建批/替补→行长决策，核对逐人送达、节点名称与重复请求；模拟网关失败和恢复，核对通知日志及终态告警。当前未进行真实企业微信发送联调。
