## 三、变更内容明细

### 3.1 数据改动（对公贷款 `LOAN_PUBLIC` + `amount_tier='LT_1000'`，12 行 → 24 行）

| # | 动作 | 行 | matrix_no | 变化 |
|---|---|---|---|---|
| 1 | **原地改** | 现有 12 行 | `M-PUB-EX-LT1000-{GM,VP,GROUP}`、`M-PUB-NEW-LT1000-{1Y,3Y,5Y}-{GM,VP,GROUP}` | `customer_type` 由 **NULL → `NON_SOE`**，边界改按非国企口径。**matrix_no 一个都没改** |
| 2 | **新增** | 12 行 SOE | `M-PUB-EX-LT1000-SOE-*`、`M-PUB-NEW-LT1000-SOE-*-*` | 国企口径，边界照抄参照档国企行 |

**为什么 matrix_no 不改名**：`ccr_application.matched_matrix_no` 与 `ccr_pricing_item.matched_matrix_no` **持久化**了路由时命中的矩阵号，改名会断掉历史单的溯源。因此本次做法是让原有那批「不带 SOE 后缀」的行**直接充当 NON_SOE 行**，国企行另起新号。

**唯一例外**：存量（`EXISTING`）行的**部门归属保留零售金融部 `3202233991`**（参照档 `GE_1000_LT_5000` 用的是公司金融部 `3202233912`）—— 这正是需求里「存量审核是零售金融部」的落点。新增行仍为授信评审部 `3202233943`。

### 3.2 对齐后的审批门槛（基准 LPR_V1：1Y=3.000%、5Y=3.500%）

| 场景 | 部门总经理终审 | 分管行长终审 | 低于则上会（→ 六人小组 ≥4 票 → 行长） |
|---|---|---|---|
| 新增 · 非国企 1Y / 3Y | ≥ **3.40%** | ≥ **3.20%** | < 3.20% |
| 新增 · 非国企 5Y | ≥ **3.60%** | ≥ **3.40%** | < 3.40% |
| 新增 · 国企 1Y / 3Y | ≥ **3.00%** | ≥ **2.90%** | < 2.90% |
| 新增 · 国企 5Y | ≥ **3.40%** | ≥ **3.30%** | < 3.30% |
| 存量 · 非国企 | 原利率 −20BP，不低于 **3.00%** | **3.00%** | < 3.00% |
| 存量 · 国企 | 原利率 −30BP，不低于 **3.00%** | **3.00%** | < 3.00% |

### 3.3 改动前后对比（**请注意放宽幅度**）

| 场景 | 改前（已作废） | 改后 |
|---|---|---|
| 新增 · 部门总经理 | LPR + 100BP（4.0% / 4.5%） | 非国企 +40BP、国企 +0（1Y/3Y）；5Y 非国企 +10BP、国企 −10BP |
| 新增 · 分管行长 | LPR + 80BP（3.8% / 4.3%） | 非国企 +20BP、国企 −10（1Y/3Y）；5Y 非国企 −10BP、国企 −20BP |
| 存量 · 下限 | **3.8%** | **3.0%** |
| 存量 · 部门总经理降幅 | 0–20BP | 非国企 0–20BP、国企 0–30BP |

> **业务影响**：大量原先必须**上会**（六人小组 + 行长）的单子，改后落进**部门总经理 / 分管行长**的岗位权限内即可终审。这是本次改动的**主要效果**，不是副作用。
> **改前那套的备注文案里写着「利率区间同个人贷款」，随本次改动一并失效** —— 个人贷款（`LOAN_PERSONAL`）口径本身**不受本次影响**。

### 3.4 明确不受影响

- 个人经营性贷款 `LOAN_PERSONAL`（不分金额档，口径与部门归属均不变）
- 对公 ≥1000万 各档（`GE_1000_LT_5000` / `GE_5000`）—— 本次是**向它们对齐**，它们本身不动
- 存款全部档位
- 秘书岗门槛（按集团综合授信总额 ≥1000万 判定，<1000万 本就不触发）
- 零售支行 `retailBranch` 额外节点（`PARENT_BRANCH_MANAGER`）逻辑不变

## 五、执行步骤

```bash
# 1) 备份（见上）

# 2) 执行增量 SQL（幂等，可重复执行）
docker exec -i ccr-prod-mysql mysql -uroot -p"$MYSQL_ROOT_PASSWORD" ccr_rate < ccr_incr_20260916.sql

# 3) ★ 清矩阵缓存（漏做 = 改了等于没改）
docker exec ccr-prod-redis redis-cli DEL ccr:cfg:matrix:effective

#    （备选：走系统内「流程配置 → 矩阵维护」任意保存一次，同样会触发失效）

# 4) 确认缓存确实已清
docker exec ccr-prod-redis redis-cli GET ccr:cfg:matrix:effective   # 期望 (nil)
```

**关于第 3 步为什么必须手动做**：`RateMatrixRouterImpl` 只在**缓存未命中**时才查库，而全系统对矩阵缓存的失效点只在 `FlowConfigController`（即系统内的矩阵维护接口）。**直接改库不会触发失效**，不清缓存就一直读旧矩阵。

|---|---|
| ① 分组计数 | NON_SOE 12（EXISTING 3 + NEW 9）、SOE 12（EXISTING 3 + NEW 9），共 **24 行** |
| ② 同 `(new_or_existing, customer_type, term_tier, priority)` 重复检查 | **返回 0 行**（有重复会在路由时抛 `RULE_MULTI_MATCH`） |
| ③ 与参照档 `GE_1000_LT_5000` 逐字段比对 | 口径列**完全一致**；仅 `EXISTING` 的 `dept_code` 按设计不同（`3202233991` vs 参照档 `3202233912`） |

## 八、风险与注意事项

| # | 风险 | 说明与处置 |
|---|---|---|
| 1 | **漏清缓存** | 最高频的踩坑。改库成功但审批仍按旧边界跑，且无任何报错。务必执行并 `GET` 确认 `(nil)`。 |
| 2 | **在途单重算** | 本次为「直接改现有行、立即生效」（用户已确认），**不版本化**。已提交的单若发生**审批调价重算**，会按**新边界**计算，而非提交时冻结的旧边界。 |
| 3 | **放宽带来的审批量变化** | 门槛放宽后，原先上会的单子改为岗位内终审。若业务侧希望保留部分上会门槛，需另提需求调整边界值（改动同样走本脚本的 `UPDATE` 段即可）。 |
| 4 | **幂等性** | SQL 可安全重复执行：`UPDATE` 按 `matrix_no` 定位；`INSERT` 的 id 由 `MAX(id)` 自适应递推、靠 `uk_matrix_no` 冲突转更新，**不会产生重复行**（本地重跑验证：总数与 `max_id` 均不变）。 |
| 5 | **id 占用** | 生产若曾有人手工加过矩阵行，`MAX(id)` 会大于初始化时的 9815；脚本已按自适应处理，**无需手工改 id**。 |
| 6 | **matrix_no 不可改名** | 后续任何人再动这批矩阵，**不得修改 `matrix_no`**，否则历史单溯源断裂。 |
