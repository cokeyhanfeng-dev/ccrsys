# 离线增量部署手册（生产无网络环境）

> 适用范围：生产环境无法联网（不能拉镜像、不能 yum/npm/maven）的部署。
> 配套脚本：`scripts/incr-release.sh`（开发机打包，既有）+ `scripts/deploy-incr.sh`（生产机部署，2026-09-01 新增）。

---

## 1. 总原则

**所有构建都在能联网的开发机完成，生产机只做四件事：解压、执行 SQL、替换 jar/dist、冒烟。** 生产机永远不执行 `docker compose build` / `docker pull`。

## 2. 首次全量部署（只做一次）

开发机（有镜像缓存或可联网）：

```bash
# ① 导出基础镜像(约 1.5GB,只带一次)
docker save mysql:8.0 redis:7-alpine nginx:1.27-alpine maven:3.9-eclipse-temurin-17 \
  | gzip > base-images.tar.gz

# ② 构建并导出应用镜像
docker compose build
docker save ccr-backend-local:latest ccr-frontend:latest | gzip > app-images.tar.gz
```

生产机：

```bash
docker load < base-images.tar.gz
docker load < app-images.tar.gz
# 全量建库(空数据卷时 compose 自动执行 db/*.sql;已有库则手工执行 publish_full.sql)
docker compose up -d
```

## 3. 后续增量部署（每次发布）

### 3.0 无 SQL 的轻量更新（Jar/dist）

仅更新后端或前端时，可使用交互式轻量脚本：

```bash
./dev release 1    # 后端
./dev release 2    # 前端
./dev release 12   # 后端 + 前端
```

把 `release/ccr-release-*.tar.gz` 和 `release/deploy-release.sh` 上传至服务器 `/tmp`，然后运行 `bash /tmp/deploy-release.sh 1|2|12`。服务器脚本只使用已有容器和宿主机目录，不构建镜像；默认把 Jar 更新到后端容器 `/app/app.jar`，把前端更新到 `/data/ccr/frontend`，旧版本备份在 `/data/ccr/backup/<时间>/`。

### 3.0a Windows 开发机打包

支持 Windows PowerShell 5.1+（Windows 10/11 自带），无需 Git Bash、WSL 或 Docker。复用既有 Linux 服务器部署脚本和 `ccr-release-*.tar.gz` 包结构。

准备工具（只准备所选部分需要的工具）：

- 通用：`git.exe`、`tar.exe` 可用，Windows 10/11 通常自带 tar。
- 后端：Windows JDK 17 解压到 `.tools/jdk-17/`，确保存在 `bin/java.exe`；Maven 3.9.x 解压到 `.tools/maven/`，或复用已有 `mvn.cmd`。若 JDK 已在其他位置，用当前会话变量 `$env:CCR_JAVA_HOME = 'D:\tools\jdk-17'` 指定。
- 前端：已有 Node.js 20+ 和 npm。首次构建需能访问依赖仓库。
- 不自动安装软件或修改全局 Java/PATH/npm 设置；Maven/npm 缓存分别位于项目 `.cache/m2/repository`、`.cache/npm`。

在项目根目录 CMD 或 PowerShell 执行：

```powershell
.\release.cmd 1              # 后端
.\release.cmd 2              # 前端
.\release.cmd 12             # 全部
.\release.cmd 12 -CheckOnly  # 仅检查工具，不构建
```

双击 `release.cmd` 也可交互选择，执行结束暂停显示结果。入口只为当前 PowerShell 进程设置执行策略，不修改系统持久策略；企业策略禁止运行时请由管理员按组织规范放行。

Windows 后端默认执行测试，任何构建/测试失败均退出且不生成新发布包。已完成独立测试、仅需构建时，可显式使用 `.\release.cmd 1 -SkipTests`（全部打包同理）；这只跳过后端单测，不能视为验证通过。macOS 既有打包脚本行为保持不变。

成功后上传 `release/ccr-release-<时间>-<类型>.tar.gz` 与 `release/deploy-release.sh` 到服务器 `/tmp`，运行 `bash /tmp/deploy-release.sh 1|2|12`。打包脚本统一转换服务器脚本为 UTF-8 无 BOM/LF，生成兼容 Linux 的 `SHA256SUMS`，记录 Git 版本及已跟踪文件是否有改动。失败时清理本次临时目录及未完成压缩包，不清除旧发布包。Jar 会包含构建时的资源配置，请检查实际部署配置，勿传播含凭据的发布包。

验收：分别验证 1/2/12 的包内目录和 SHA-256；错误模式、缺少工具、构建失败应非零退出；在 Linux 解包后执行 `sha256sum -c SHA256SUMS` 并用原部署脚本验收。当前开发机为 macOS，Windows 实机执行仍需同事验收。

### 3.1 开发机打包（既有脚本）

```bash
./scripts/incr-release.sh <序号>            # 例: ./scripts/incr-release.sh 026
# 产物: release/incr_<日期>_<序号>/{README.md, db/, backend/ccr-admin.jar, frontend/dist/}
tar czf ccr-incr-<日期>_<序号>.tar.gz -C release incr_<日期>_<序号>   # 打成 tar 便于传输
```

### 3.2 生产机部署（新脚本，全程离线）

```bash
# 方式一:解开的目录
./scripts/deploy-incr.sh release/incr_20260901_026
# 方式二:直接给 tar 包(脚本自动解压到临时目录)
./scripts/deploy-incr.sh /tmp/ccr-incr-20260901_026.tar.gz
# 部分部署:
./scripts/deploy-incr.sh <包> --skip-backend --skip-sql     # 只发前端
./scripts/deploy-incr.sh <包> --skip-frontend               # 只发 SQL+后端
```

脚本流程与行为：

| 步骤 | 行为 |
|---|---|
| 前置检查 | docker 可用、目标容器在运行，否则立即失败不碰任何数据 |
| 1/4 SQL | 包内 `db/*.sql` 按文件名升序 `docker exec -i ccr-mysql mysql ... <` 逐个执行（脚本均幂等） |
| 2/4 后端 | 旧 jar 备份到 `release/rollback/<时间戳>/` → 替换 `/app/app.jar` → 重启容器 → 轮询登录接口直到就绪（60s 超时失败退出） |
| 3/4 前端 | 旧静态目录备份（tar.gz 存 rollback）→ 替换 `/usr/share/nginx/html`（nginx 静态文件即时生效，无需 reload） |
| 4/4 冒烟 | 前端首页 200 + 登录接口经 nginx 代理 200，任一不过则非零退出并提示 |

### 3.3 环境变量覆盖（生产与本地不一致时用）

```bash
CCR_MYSQL_CONTAINER=ccr-mysql CCR_MYSQL_PWD=<生产密码> CCR_MYSQL_DB=ccr_rate \
CCR_BACKEND_CONTAINER=ccr-backend CCR_FRONTEND_CONTAINER=ccr-frontend \
./scripts/deploy-incr.sh <包>
```

### 3.4 回滚

每次部署自动备份到 `release/rollback/<时间戳>/`（旧 jar + 旧静态目录 tar.gz）。回滚 = 反向 SQL（见包内 README）+ 把备份 jar/dist 用同样方式替换回去并重启。

## 4. 离线环境的三个坑（都踩过/预判过）

1. **不要在生产机上 `compose build`/`up --build`**——会触发拉基础镜像直接失败。应用更新只走 jar/dist 替换（本脚本方式），基础镜像只在首次 load。
2. **`docker compose up -d` 重建容器会丢容器内热替换的文件**——本脚本同时把备份落在宿主机 `release/rollback/`，且建议后续给 frontend 服务加 dist 挂载（见下）彻底免疫。
3. **生产 MySQL 密码与本地 `root123` 不同**——必须用 `CCR_MYSQL_PWD` 传入；台账里 `root123` 仅限隔离测试环境（AGENTS.md 红线）。

## 5. 建议的 compose 加固（可选，下次维护窗口做）

给 `docker-compose.yml` 的 frontend 服务加 dist 挂载，容器重建也不丢静态文件：

```yaml
  frontend:
    volumes:
      - ./release/dist:/usr/share/nginx/html:ro   # 宿主机目录优先于镜像内 dist
```

加固后前端增量只需解压覆盖 `release/dist/`，连容器都不用碰（deploy-incr.sh 已兼容两种方式）。
