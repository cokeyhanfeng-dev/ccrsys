> 面向配置与运维人员。目的：看懂权限矩阵怎么算、审批流程怎么走、出问题怎么自己定位和配置。
> 代码基线：当前仓库 HEAD（含 commit `9a3ba99` 取消硬边界阻断）。所有引用格式为 `文件:行号`。

## 1. 总览：一次提交背后发生了什么

```
客户经理提交申请
  └─ ApplicationSubmitServiceImpl.submit()          (ccr-application)
      a. 状态守卫(仅 DRAFT) + 幂等
      b. 完整性校验(分项必填/存款账户关系/担保措施/承诺截止日期)
      c. 集团约束(成员有效性/额度勾稽)
      d. 一合同/账户一有效分项(防重复在途)
      e. 逐分项硬边界 checkHardBoundary —— 当前版本只返回边界值,不阻断
      f. 主申请置 SUBMITTED
      g. 快照采集 + 质量校验(BLOCK 即拒绝) + 快照冻结
      h. 逐分项矩阵路由 RateMatrixRouterImpl.calcRoute()
           → 冻结:终审岗位 route_code、路由链 route_chain、部门 dept_code、
                  边界值、LPR 版本、命中矩阵行号
           → 置 ROUTING,经 Outbox 启动 Warm-Flow 流程实例
  └─ 审批推进 ApprovalServiceImpl.approve()         (ccr-approval)
      权限内:沿冻结链逐级过手 → 终审岗位批准后整单 APPROVED_LEVEL → FINAL
      超权限:整单上送 → 六人小组表决(VOTING,≥4票,一票否决) → COMMITTEE_PASS
             → 总行行长决策(PRESIDENT_DECISION) → FINAL / VETOED / REJECTED
  └─ 决议核验(ccr-resolution) → 承诺履约(ccr-commitment) → 通知(ccr-message)
```

关键设计：**路由在提交时一次性算好并冻结**。审批阶段不再重算矩阵（仅审批人调价后贷款会按新利率重算路由），所以"审批走到哪、谁有终审权"在提交那一刻就定了，全部留痕可查。

## 2. 权限矩阵表 `ccr_rate_matrix`

DDL：`db/07_rate_matrix.sql:26-64`。一行 = 某业务维度下某岗位的权限边界。

| 字段 | 含义 / 取值 |
|---|---|
| `matrix_no` | 矩阵行编码，唯一，如 `M-PUB-NEW-LT-NSOE-1Y-BM` |
| `business_big_type` | `LOAN_PUBLIC` 对公贷款 / `LOAN_PERSONAL` 个人贷款 / `DEPOSIT` 存款（保证金也落 DEPOSIT，靠产品码区分） |
| `new_or_existing` | `NEW` 新增 / `EXISTING` 存量 |
| `customer_type` | `SOE` 国企 / `NON_SOE` 非国企 / `PERSONAL` 个人；**空 = 通配** |
| `product_code` | 产品编码；空 = 通配。存款：`AGREEMENT_DEPOSIT` 协定 / `NOTICE_DEPOSIT` 通知 / `CORP_TIME_DEPOSIT` 对公定期 / `BILL_MARGIN` 银票保证金 / `CREDIT_MARGIN` 信用证保证金 |
| `amount_tier` | `LT_1000`(<1000万) / `GE_1000_LT_5000` / `GE_5000`(≥5000万)；空 = 通配 |
| `term_tier` | 贷款 `1Y/3Y/5Y`；存款 `3M/6M/1Y/2Y/3Y`；通知存款 `1D/7D`；空 = 通配 |
| `guarantee_type` | 担保主类型；空 = 通配（种子未用） |
| `start_node_code` | **该行的岗位**：`BRANCH_MANAGER` 支行行长 / `DEPT_GENERAL_MANAGER` 部门总经理 / `VICE_PRESIDENT` 分管行领导 / `SIX_PEOPLE_GROUP` 六人小组（兜底行） |
| `dept_code` | 部门归属（D16a 部门分流），存机构 org_code：`3202233912` 公司金融部 / `3202233943` 授信评审部 / `3202233991` 零售金融部 |
| `boundary_type` | `RATE` 直接利率（可含 LPR±BP）/ `SPREAD` 存量降幅 |
| `boundary_min_rate` | 绝对值利率(%)：贷款新增=该岗位最低可批利率；存量=绝对下限；**存款=上限（高于它才上会）** |
| `boundary_bp` + `bp_sign` + `lpr_term` | 按 LPR 浮动配置：边界 = LPR(`1Y`/`5Y`) ± BP/100；SPREAD 时 `boundary_bp` = 最大可降 BP |
| `priority` | 优先级，**低值优先**。链式约定：1 支行 / 2 部门总经理 / 3 分管行领导 / 4 小组 |
| `effective_from` / `effective_to` | 生效窗口 |
| `status` | `DRAFT` 草稿 → `REVIEW` 待复核 → `EFFECTIVE` 生效 → `INVALID` 停用 |
| `publish_by` / `review_by` / `publish_time` | 双人复核留痕 |

**匹配规则**：所有维度"行里配了值就必须相等，空 = 通配"。同一申请维度下，同优先级命中多行直接报错（互斥配置错误），所以**配置矩阵时同维度行的优先级必须唯一、条件必须互斥**。

金额档/期限档的换算（`RateMatrixRouterImpl.toAmountTier/toTermTier`）：
- 金额定档基准：集团申请默认按集团综合授信批复总额度，无集团额度或显式 `APPLY_AMOUNT` 时按本笔申请金额（§B18）
- 期限换算：贷款按月数 ≤12→`1Y`、≤36→`3Y`、>36→`5Y`；存款 ≤3→`3M`、≤6→`6M`、≤12→`1Y`、≤24→`2Y`、>24→`3Y`；按天 → `1D`/`7D`

**种子数据全景**（`db/07_rate_matrix.sql:75-465`，共 90 行）：对公存量 11 行、对公新增 45 行（SOE 无支行行长终审行=支行只过手；NON_SOE 及 <1000万档含 BM 行=支行行长有终审权）、个人 15 行、存款 10 行（全部终审 `SIX_PEOPLE_GROUP`、`boundary_min_rate` 为期限上限，如定期 1Y 1.25%、协定 0.25%，低于上限支行行长权限内终审，高于才上会）。

## 3. 路由计算逻辑（`RateMatrixRouterImpl.calcRoute`，ccr-rule 模块）

入参 `MatrixRouteInput`：业务大类、存量/新增、客户类型、产品码、金额、期限、担保类型、申请利率、原执行利率（存量降幅基准）、冻结 LPR 版本、冻结生效日期。

主流程（`RateMatrixRouterImpl.java:103-197`）：

1. 按产品码查**产品审批链路**（`loadProductRoute`），命中最新 PUBLISHED 版本；没配置则矩阵纯驱动
2. 取全量 `EFFECTIVE` 矩阵行（整体缓存 `ccr:cfg:matrix:effective`），按业务大类/存量新增/生效窗口过滤，再按 §2 维度匹配
3. 按 `priority` 升序；**空命中 → `RULE_NO_MATCH`；同优先级多命中 → `RULE_MULTI_MATCH`**
4. 取产品硬边界（生效窗口内最新一版），用于终审边界交集

然后分流：

- **产品链路 `DIRECT_VOTE`（直接上会）**：链路固定 `支行行长 → 六人小组 → 总行行长`，不参与链式优先级（`buildVoteResult` :314）
- **存款/保证金（上限语义）**：`mandatory_vote=Y` 强制上会；申请利率 ≤ 上限（含等于）→ 支行行长权限内终审；高于上限 → 终审六人小组，且**凡上会必追加总行行长决策**
- **贷款（链式，下限语义）**：加载 LPR（冻结版本优先，否则当前生效版；查不到抛 `LPR_NOT_EFFECTIVE`），按 priority 升序逐岗位计算边界：
  - `calcBoundary`（:457）：`SPREAD` → 边界 = 原执行利率 − BP/100，且不低于 `boundary_min_rate`；`RATE`+BP → 边界 = LPR ± BP/100，以 `boundary_min_rate` 托底；纯 `RATE` → 直接取 `boundary_min_rate`
  - 某岗位边界算不出（null）或 **申请利率 ≥ 该岗位边界 → 该岗位即终审**；都不满足 → 找 `SIX_PEOPLE_GROUP` 兜底行，没有兜底行报 `RULE_NO_MATCH`
- **特殊节点**：贷款且金额 ≥1000万 且利率 <2.6% 时，在分管行领导后插入"秘书"节点（`applySecretaryGate` :384，常量 `SECRETARY_MIN_AMOUNT=1000` / `SECRETARY_RATE_GATE=2.6`）
- 终审边界 = 矩阵边界 ∩ 产品硬边界（`intersectBoundary` :566）：**贷款取下限 max，存款取上限 min**

路由链构建（`buildChain` :605）：恒以支行行长开头，沿 priority 升序追加各命中岗位，到终审岗位截断；小组行仅当终审=小组才入链。

## 4. 产品审批链路 `ccr_product_route`（矩阵之上的叠加层）

DDL：`db/03e_config.sql:423-462`。按产品定制审批路径，**不替代矩阵，而是改终审**。

| 字段 | 含义 |
|---|---|
| `product_code` | 关联产品目录 `ccr_product` |
| `route_mode` | `CHAINED` 链式逐级 / `DIRECT_VOTE` 直接上会（存款/保证金典型用法） |
| `mandatory_vote` | `Y` 强制六人小组 |
| `president_decision` | `Y` 必经总行行长决策（注意：路由引擎里凡上会已全局强制追加行长节点） |
| `vote_condition` | JSON 上会条件，**AND 语义**：`amount_tier` + `enterprise_type` 全命中才上会 |
| `flow_key` | Warm-Flow 流程定义 key，空 = 默认流程 |
| `status` | `DRAFT/PENDING_REVIEW/PUBLISHED/OBSOLETE`（与矩阵状态机不同） |

命中：按产品码 + 生效日 ≤ 冻结日期，生效日降序、优先级升序取第一条（缓存 `ccr:cfg:product-route:effective`）。

## 5. 配置后台：怎么配、谁来复核

入口页面：`系统管理 → 参数配置`（`frontend/src/views/system/params.vue`，多 tab：LPR / 权限矩阵 / 产品边界 / 产品配置(含审批链路) / 变更日志 / 路由试算）。流程定义管理在 `系统管理 → 流程`（`flow.vue`）。

后端接口：`FlowConfigController`（`/system/flow/thresholds/...`，LPR/矩阵/产品硬边界）+ `ProductConfigController`（`/system/product/routes`，产品链路）。

**统一生命周期**（四类配置一致）：

```
新增(DRAFT) → 送审(REVIEW) → 复核发布(EFFECTIVE/PUBLISHED) → 停用(INVALID/OBSOLETE)
                              ↘ 驳回(意见必填) → 回到 DRAFT
```

铁规矩：

- **双人复核**：发布人与创建人不得同一人，否则 403
- **生效行禁止原位修改**：要调整 = 新建一行发布，系统自动把同维度旧生效行置 INVALID 并回填 `effective_to`
- **发布前校验**：LPR 限 0.5%–8%、0.05 整数倍、同生效日仅一版；矩阵校验 RATE/BP/SPREAD 字段互斥必填、同条件组优先级唯一、贷款矩阵下限不得低于产品硬边界
- **每次操作写审计** `ccr_config_change_log`（含 old_json/new_json 快照、操作人、驳回意见），前端"变更日志"tab 可按配置域过滤查询
- **发布即清缓存**：矩阵发布/停用删 `ccr:cfg:matrix:effective`，LPR 删 `ccr:cfg:lpr:effective`，产品链路删 `ccr:cfg:product-route:effective`，并递增全局版本号 `ccr:cfg:v`

角色口径：维护 = `admin`；复核放行 = `admin` 或 `config_reviewer`。

**权限矩阵 tab 使用要点**：页面已写明"生效行禁止原位修改，调整=新建行发布替换"；`matrix_no` 自取不重复的业务编码（参考种子命名习惯 `M-业务-新旧-金额档-客户-期限-岗位`）；存款行 `boundary_type=RATE`、`boundary_min_rate` 填上限、终审岗 `SIX_PEOPLE_GROUP`；改完用"路由试算"tab 输入同样维度验证终审岗位和链路，再通知业务提交。

## 6. 审批流程的后台实现（Warm-Flow + 业务状态机）

**两层结构**，这是理解排查的关键：

- **Warm-Flow（ccr-workflow）只做"流程轨迹"**：启动时 `StandardFlowInitializer` 确保两条已发布流程定义——贷款 `rate_approval`（BM→GM→VP→SECRETARY→GROUP→PRESIDENT）、存款 `deposit_approval`（BM→GROUP→PRESIDENT）。提交后经 Outbox 消费者 `FlowStartOutboxHandler` 按路由起始节点启动实例；每次审批动作 `recordBusinessTrail` 同步轨迹，**失败只记日志不阻断业务**
- **真正的状态推进在 `ApprovalServiceImpl.approve`**（ccr-approval，:168），不走 Warm-Flow 状态机

`approve` 关键分支：

1. **节点守卫**：`checkOperatorAndNode` 校验当前人是否该节点审批人（按分项 `dept_code` 部门分流）；存款分项仅支行行长可过手；支行行长只能批本支行申请；GROUP/PRESIDENT 节点放行给表决/行长流程
2. **调价校验**：审批人改利率先过节点权限（`ccr_node_permission`）+ 硬边界（仅提示）；**贷款调价后按新利率重算矩阵路由并刷新冻结链**（存款链固定不重算）
3. **整单口径**：同一申请的全部分项一起推进。中间节点只有过手权；当前节点 = 冻结终审岗位才有终审权
4. **权限内终审**：全部分项在本节点齐套（都有 APPROVE 动作）→ 整单 `APPROVED_LEVEL`，触发决议/承诺/主申请聚合
5. **上送（escalate）**：整单送下一节点；目标是六人小组时 → `voteService.createGroupRound()` 建表决轮次，分项置 `VOTING`；贷款的分项按各自冻结终审岗分流（自己权限内的就地终审，不进小组），存款分项无条件随整单上会
6. 表决 ≥4 票通过 → `COMMITTEE_PASS` → 必经行长决策（`PRESIDENT_DECISION`）→ `FINAL`；一票否决 → `VETOED`

状态枚举见 `ccr-application/.../enums/ApplicationStatus.java` 与 `PricingItemStatus.java`（主申请与分项各一套，编码一致）。

### 6.1 六人表决与行长决策（ccr-vote 模块，`VoteServiceImpl`）

- **建批**（`createGroupRound` :103）：同申请下、当前在小组节点且未入任何进行中批次的分项合为一批；**冻结 6 人委员名单**——小组节点配置了有效指派时按指派取前 6 名启用用户，未配置按"小组成员"角色兜底取 6 人，**不足 6 人直接抛配置错误**（建批失败，申请卡在 ROUTING）
- **投票**（`submitBallot` :179）：票型仅 `APPROVE/REJECT`；委员身份取登录人，只能投本人任务；每人每分项一票（唯一键 `uk_ballot_idem` + 分项重复票 `DuplicateKeyException` 兜底）；投票人存哈希实现匿名（行长只能看匿名码 A-F + 票型 + 意见）
- **计票**（`countItem` :562）：**分项收齐全部委员票才计票**，赞成 ≥ 通过线（默认 ≥4）→ 分项置 `PRESIDENT_DECISION`；未过 → 分项 `REJECTED` 并**整单否决**——同申请其余未终态分项（含还在其他节点审批的）一并置 REJECTED，生成否决决议，不回退草稿
- **超时强制计票**（`scanTimeoutRounds` :418）：批次 VOTING 超过 `ccr.vote.round-timeout-hours`（默认 72h），定时任务按已投票数强制计票；一票都没有按不通过处理。生产上"VOTING 卡很久忽然被否"先查这个
- **行长决策**（`presidentDecision` :269）：整单口径，仅 `PRESIDENT` 角色；PRESIDENT 节点配置了指定决策人时仅指派范围内的人可决策；`VETO` 必须填意见；同意 → 分项 `FINAL`，否决 → `VETOED`（幂等由唯一键 `uk_president_pricing` 兜底）
- 表决相关表：`ccr_vote_round`（批次）/ `ccr_vote_round_item`（批次-分项）/ `ccr_vote_assignment`（委员任务，支持替补 `substitute`）/ `ccr_ballot`（票）/ `ccr_vote_result`（计票结果）/ `ccr_president_decision`（行长决策）

## 7. 缓存机制与手动刷新

| 数据 | Redis key | 失效方式 |
|---|---|---|
| 权限矩阵生效行（全量） | `ccr:cfg:matrix:effective` | 矩阵发布/停用自动删；手动 `DEL` |
| 当前生效 LPR | `ccr:cfg:lpr:effective` | LPR 发布/停用自动删 |
| 产品审批链路（全量 PUBLISHED） | `ccr:cfg:product-route:effective` | 链路发布/停用自动删 |
| 产品硬边界（按产品） | `ccr:cfg:rate-limit:{LOAN\|DEPOSIT}:{产品码}` | **发布接口不主动删**，靠 TTL 过期或手动 `DEL`——生产改硬边界后必须手动清 |
| 全局配置版本号 | `ccr:cfg:v` | 每次发布递增，读路径感知 |

缓存项定义存在 `ccr_cache_config` 表（精确 key 或 key 前缀、TTL、写入开关），管理员可在 `系统管理 → 缓存` 页增删改，改配置立即生效。内置 3 项（lpr/matrix/rate-limit）受保护不可删。读缓存时若 JSON 反序列化异常会视为失效、直查库重建，所以**手动 `DEL` 是安全的**。

## 8. 排查手册：报错 → 定位 → 处理

先用两个免提交接口自测（返回里直接写明哪项挡住）：

```
POST /ccr/applications/{id}/submit-check    # 批次差异+质量预校验+逐分项硬边界+blockSubmit
POST /ccr/applications/{id}/route-preview   # 逐分项路由结果或 errorMessage
```

| 报错文案 | 根因 | 定位 SQL / 动作 | 处理 |
|---|---|---|---|
| `突破业务硬边界:产品[x] 硬边界利率...,申请利率...` | **生产 jar 旧于 commit `9a3ba99`(2026-08-19)**，当前代码硬边界已不阻断 | 核对部署包构建时间/对应增量包号 | 重发新版 jar；临时方案：`UPDATE ccr_product_rate_limit SET status='INACTIVE' WHERE business_type='DEPOSIT'` + `DEL ccr:cfg:rate-limit:DEPOSIT:*` |
| `权限矩阵无匹配(业务大类=...)` | 该维度没有 EFFECTIVE 矩阵行 / 生效窗口不符 / 期限档落不进去（如对公定期 4 个月不在任何 `term_tier`） | `SELECT * FROM ccr_rate_matrix WHERE business_big_type=? AND new_or_existing=? AND status='EFFECTIVE'` 对照申请维度 | 补配矩阵行并复核发布；注意保证金行必须是 `DEPOSIT`（历史增量 `db/incr/20260819_001`，包 009） |
| `权限矩阵多匹配:优先级N命中M行` | 同维度同优先级多行命中，条件不互斥（旧库定期行 product_code 通配互撞就是这个） | 按维度+优先级分组查重：`SELECT business_big_type,new_or_existing,customer_type,product_code,amount_tier,term_tier,priority,COUNT(*) FROM ccr_rate_matrix WHERE status='EFFECTIVE' GROUP BY 1,2,3,4,5,6,7 HAVING COUNT(*)>1` | 新建互斥行发布替换旧行；发布后确认 `DEL ccr:cfg:matrix:effective`（正常自动清） |
| `当前无生效的LPR版本` | 没有 EFFECTIVE 且生效窗口覆盖今天的 LPR 版本 | `SELECT * FROM ccr_lpr_version WHERE status='EFFECTIVE' ORDER BY effective_from DESC` | 参数配置页发布 LPR；或调整生效窗口 |
| `数据质量阻断,不能提交` | 快照质量校验 BLOCK | `SELECT rule_code,subject_id,message FROM ccr_snapshot_quality_result WHERE bundle_id=(SELECT MAX(id) FROM ccr_snapshot_bundle WHERE application_id=?) AND level='BLOCK'` | 全部申请都报 → 数仓断更超容忍天数（默认 3 天，`ccr.snapshot.data-stale-days`），找数据中心刷新批次；单笔报 → 查该客户主数据唯一性/贡献度勾稽 |
| 提交卡住无报错但状态停在 ROUTING | Outbox 未消费 / Warm-Flow 启动失败 | 查 `ccr_outbox`（或对应 Outbox 表）未处理记录；查后端日志 `FlowStartOutboxHandler` | 流程轨迹失败不阻断业务，但实例未启动需看日志重放 |
| 审批人看不到待办 / 提示无权限 | 节点审批人指派或部门分流问题 | 查分项冻结的 `dept_code`、当前节点；查用户-机构绑定 `ccr_user_binding`（表名以实际为准） | 系统管理核对用户角色与机构绑定；支行行长只能批本支行 |
| 改了配置不生效 | 缓存未失效 | `KEYS ccr:cfg:*` 对照 §7 | 矩阵/LPR/链路发布会自动清；**硬边界必须手动 `DEL ccr:cfg:rate-limit:...`**；或在缓存管理页刷新 |
| `表决委员配置不足...需 6 人` | 上送建批时小组节点指派/小组成员角色下启用用户不足 6 人（`VoteServiceImpl.resolveRoundMembers`） | 查小组节点指派配置；`SELECT id,username,status FROM sys_user WHERE role_code='COMMITTEE'`（表名/角色码以实际为准） | 系统管理补齐 6 名启用委员或配置节点指派，再重新上送 |
| VOTING 卡很久后突然被否 | 批次超 72h（`ccr.vote.round-timeout-hours`）被定时任务**超时强制计票**，按已投票数计 | `SELECT id,status,round_start_time FROM ccr_vote_round WHERE application_id=?` + `ccr_vote_result` 的 `submitted_count` | 属正常机制；催促委员及时投票，超时计票结果不可回退，只能重新申请 |
| 行长决策提示"不在指派范围内" | PRESIDENT 节点配置了指定决策人，当前登录人不在内 | 查 PRESIDENT 节点指派配置（`VoteServiceImpl.presidentDecision` :290） | 调整节点指派或用指派账号决策 |
| 小组否决后其他分项也被否 | 设计如此：**整单否决**，同申请未终态分项一并 REJECTED（`countItem` :626） | `ccr_approval_action` 留痕可溯源 | 不出问题不用处理；重新申请走"关联重提" |

通用排查顺序：

1. 拿申请号 → `SELECT id,status FROM ccr_application WHERE application_no=?` 看主状态
2. → `SELECT pricing_item_no,status,route_code,route_chain,dept_code FROM ccr_pricing_item WHERE application_id=?` 看分项冻结的路由（字段名以实际表结构为准）
3. 状态在 DRAFT 提交失败 → 按上表对报错文案
4. 状态在 ROUTING/VOTING 卡住 → 查 Warm-Flow `flw_instance`/`flw_task` + 表决轮次表 + 后端日志
5. 怀疑配置问题 → 变更日志 tab 查最近谁发布了什么（`ccr_config_change_log`）
