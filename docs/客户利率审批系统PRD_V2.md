## 1. 背景

为加强对全行经营性贷款投放的统一考核与利率定价管理，并为各支行综合营销方案提供利率定价策略与建议，需建设「客户贡献度管理与利率决策系统」。系统将客户贡献度量化、承诺跟踪与分级利率审批打通，实现"定价有依据、审批流程简明、进度可追踪"。

当前已有 PC 端（v3.3-html-demo）与手机端（mobile-demo）交互原型，但原型存在与需求文档不一致的偏差（见对齐报告 B1–B11）。本 PRD 以需求文档为权威依据，修正原型偏差后作为系统开发基准。系统业务数据**统一由内部数据仓库加工提供**，本系统不直接对接外部系统。

## 2. 目标

| 编号 | 目标 | 说明 |
|---|---|---|
| G1 | 当前贡献度展示 | 直接展示客户及关联人的**当前贡献度**（数据仓库取数），反映客户现有综合贡献；总额与明细勾稽一致 |
| G2 | 拟达成贡献度录入与承诺跟踪 | 客户经理申请时录入**拟达成贡献度**（即承诺贡献）作**承诺基线**；系统以**数仓最近批次当前贡献度**为实际达成值对比该基线（客户级·逐指标），按月跟踪达成/落差并提醒，作为下次申请差异化处理依据 |
| G3 | 定价有依据 | 审批时并列参考**当前贡献度（数仓）**与**拟达成贡献度（申请录入）**，结合数据快照实现科学定价 |
| G4 | 审批流程简明 | 按金额/利率/客户类型自动分级，6 人对申请利率投票，≥4 票赞成即通过 |
| G5 | 流程更高效 | 审批进度实时推送，消息自动通知 |
| G6 | 审批口径稳定 | 审批全过程只读取申请绑定的数据快照，不随数据变动 |

> **贡献度双概念**：①**当前贡献度**——数据仓库取数，反映客户现有贡献，供审批人参考，**同时作为"拟达成贡献度"达成跟踪的实际达成值**；②**拟达成贡献度**（=承诺贡献）——客户经理申请时录入的预期贡献，作为承诺基线，**按指标 code 聚合到客户级后，与数仓最近批次当前贡献度逐项对比判定达成/落差**。两者并列展示给审批人，来源与规则不同（见 §8、§9）。

## 3. 范围与总体原则

### 3.1 端侧边界（决议 D10）

| 业务能力 | PC 端 | 移动端 |
|---|---|---|
| 客户经理新建/重新发起申请 | 保留 | 移除 |
| 客户/关联人/融资/证明材料录入 | 保留 | 移除 |
| 拟达成贡献度（承诺）录入与跟踪 | PC 客户经理端保留 | 移除 |
| 待办审批、节点调价 | 保留 | 保留 |
| 六人匿名表决 | 保留 | 保留 |
| 行长同意/一票否决 | 保留 | 保留 |
| 历史审批 | 保留 | 保留 |

> 移动端最终只保留：**审批工作台、待办列表、审批详情、历史审批、消息、我的**。移动端不暴露新建申请、融资录入、附件上传、数据中心数据刷新等接口。角色、菜单、接口权限三层一并收敛。

### 3.2 数据一致性原则（决议 D11）

1. 业务数据采用**追加式不可变快照**，不覆盖历史批次，可还原某次审批当时使用的数据。
2. 申请提交时将客户、融资、关联、贡献度、机构达成的快照**固定绑定**到申请；审批过程与历史审批只读取已绑定快照。
3. 人工/Excel/OCR 补录与数据仓库权威数据**分离存储**，并关联证明材料；补录不回写仓库权威数据。
4. 移动端**不直连**数据仓库，只通过审批详情接口读取已绑定快照。
5. 产品利率参数（LPR、权限利率）作为**系统参数**维护，不由数据仓库提供。

### 3.3 LPR 参数机制（修正 B1，决议 D1）

- **LPR 作为系统参数维护**，权限阈值以「LPR±BP」形式存储并自动换算；LPR 调整后由系统自动更新，无需修改规则代码。禁止写死数值。
- 系统须区分存储：一年期 LPR、五年期以上 LPR 两个参数值。
- **配置方式（业务方确认）**：LPR **按指标（1Y/5Y+）× 产品类型逐行维护**，不做"一版一行只含 1Y/5Y 两值"的单行展示；产品类型划分参照本需求（对公贷款/个人经营性贷款/存款各产品）。**配置统一状态机与发布流程由 admin 配置即可**（详见详设 §8A.2/§8A.3）。
- **维护机制（已定 D12）**：LPR **人工维护**，维护责任部门为**计划财务部**；LPR 变更时由计划财务部人工录入新值，系统据此自动换算全部权限阈值。
- **D1 · 切换存量处理**：切换时间点前创建的在途申请沿用旧规则（写死基准）冻结结办；切换时间点后的新申请走 LPR±BP 新引擎。

### 3.4 产品配置化（业务方确认：所有产品配置化 + 配置化审批链路）

- **所有产品统一配置化**：产品（对公贷款 / 个人经营性贷款 / 存款各产品：对公定期 3/6/12/24/36 月、协定存款、通知存款 1/7 天、银票保证金、信用证保证金等）**统一在产品配置中心登记**（产品目录 `ccr_product`），产品新增/停用、利率区间、期限范围均通过配置维护，**不写死在代码**；申请页产品下拉、LPR 明细产品类型、权限矩阵、产品边界统一以产品目录为**权威来源**。
- **配置化的审批链路**：每个产品可配置自身审批链路（`ccr_product_route`）：路由模式（`CHAINED` 链式逐级 / `DIRECT_VOTE` 直接上会）、起始节点、是否强制六人小组上会、上会条件（金额档 / 企业性质 / 利率越界）、是否必经总行行长决策。审批时系统按产品命中其审批链路生成节点序列，**替代硬编码的分级/上会判定**。
- **支行行长节点恒必经（B13，全局强制）**：客户经理提交申请后，无论产品与审批链路如何配置（含 `DIRECT_VOTE` 直接上会），**审批首节点恒为支行行长**（系统固定注入，非可配置项）；`DIRECT_VOTE` 表示支行行长之后直接进入六人小组 + 行长决策，不再走链式层级。
- **产品停用规则**：产品停用后新申请不可选该产品，在途审批/已冻结申请不受影响（D11）。
- **配置统一状态机与发布流程由 admin 配置即可**（详见详设 §8A.2/§8A.5）。

## 5. 用户故事（摘要）

- 作为客户经理（**仅 PC 端**），我希望录入客户融资/基本信息与关联人，并录入本笔申请的**拟达成贡献度**（承诺），提交时系统将数据快照固定绑定到申请，以便进入审批流程且口径稳定。
- 作为审批人（PC+移动），我希望系统并列展示客户**当前贡献度（数仓）**与申请录入的**拟达成贡献度**，以便在定价决策时参考，且只读申请已绑定的数据快照。
- 作为利率审批小组成员，我希望就申请利率逐项投票，以便≥4票时执行申请利率。
- 作为总行行长，我希望在小组表决后行使同意或一票否决，以便形成最终决议。
- 作为支行行长，我希望实时追踪客户**拟达成贡献度**的达成情况（以数仓当前贡献度为实际达成值对比承诺基线）并接收落差提醒，以便下次申请时差异化处理。

## 7. 业务流程

### 7.1 总体流程

```
支行发起利率申请（提交各担保类型的申请利率）
   → 提交前校验数据中心快照（时效/质量/一致性）+ 绑定快照
   → 判断业务类型/金额区间/客户类型分档/贷款期限
   → 权限内审批（支行行长/部门总经理/分管行领导，按权限矩阵自动路由终审岗位）
        ├─ 权限内：直接确定最终利率（可在权限内调价）→ 权限内终审
        └─ 超出权限：提交存贷款利率审批小组
   → 小组 6 人投票（就申请利率逐项赞成/反对）
        ├─ 赞成票 ≥ 4：审批通过，执行申请利率
        └─ 赞成票 < 4：审批否决，申请退回
   → 行长一票否决（如适用）
   → 形成最终决议
```

### 7.2 分级路由规则（权限矩阵，权威依据 §7.5 + 议案）

系统按以下维度自动路由终审岗位：业务类型（存量/新增授信）、客户类型（对公按国企/非国企分档；个人经营性贷款）、金额区间（5000 万以下/以上）、贷款期限（一/三/五年期）、申请利率。**路由链路（是否链式、是否上会、是否必经行长决策）由产品审批链路配置驱动（产品配置中心，§3.4/详设 §8A.5②）：按产品命中 `ccr_product_route`（route_mode / mandatory_vote / vote_condition），替代硬编码判定；权限矩阵 `ccr_rate_matrix` 决定边界利率与起始节点。**

**LPR 现行换算值**：一年期 3.0%、五年期以上 3.5%（LPR 调整后系统自动换算，见 §3.3）。

**岗位部门归属（已定 D16a）**：权限矩阵中的"部门总经理/分管行领导"按业务类型归属具体部门——**对公存量** → 公司金融部；**对公新增授信** → 授信评审部；**个人经营性贷款** → 零售金融部。审批沿该归属自动路由对应部门岗位。

| 信用证保证金 | 存贷款利率审批小组 | 高于年化利率 1.05%（≥4 票通过） |
| 对公定期存款 | 存贷款利率审批小组 | 三个月>0.85% / 六个月>1.05% / 一年期>1.25% / 两年期>1.4% / 三年期>1.58%（≥4 票通过） |
| 协定存款 | 存贷款利率审批小组 | 高于 0.25%（≥4 票通过） |
| 通知存款 | 存贷款利率审批小组 | 一天通知>0.2% / 七天通知>0.35%（≥4 票通过） |

> **存款/保证金一律直接上会（已定 D16b）**：表 7.2.4 中存款/保证金类业务**不设部门权限内层级**，凡申请**先必经支行行长（B13），再**直接进入存贷款利率审批小组表决（≥4 票通过）。权限矩阵**命中唯一性按存/贷链路分轨**：贷款走 `priority` 升序第一命中（链式逐级上送），存款/保证金按产品类型+期限档唯一（无链式层级，支行行长必经）。
>
> **逐担保类型路由与校验（已定 D18a）**：综合授信含多种担保类型时，**每种担保类型各自路由、各自执行利率下限校验、各自独立计票**（D2 校验按类型粒度，与 D5 独立计票同构）；各类型结果互不影响。

### 7.3 上会条件（§7.6）

自 V3.3 起，上会条件与 §7.5（本 PRD §7.2）权限表统一：贷款利率申请利率低于对应部门总经理/分管行领导权限下限的，提交小组表决；存款利率高于对应期限上限的，提交小组表决。

### 7.4 综合授信分类型展示（§7.7，决议 D5）

授信方案涉及多种担保类型时，按类型分别展示、分别审批、**独立计票**：审批人对每种担保类型独立投票，各自≥4票通过才执行该类型申请利率；任一类型未过则仅该类型退回，其余类型按各自结果执行/退回。

### 7.5 退回与重新提交流程（补齐 C4）

**被否决/被退回后的处置规则：**

| 退回类型 | 触发 | 处置 |
|---|---|---|
| 小组表决否决（逐类型） | 某担保类型赞成票 < 4 | **该担保类型**标记否决退回；其他已通过类型保留（D18a/D18b） |
| 行长一票否决（整笔/逐类型） | 行长对某担保类型行使否决 | 该类型标记否决；行长对整笔行使否决则整笔否决任一类型，无论小组结果 |
| 审批人退回修改 | 审批人退回（材料/利率需调整） | 申请回滚至申请人可编辑状态 |

**重新提交（重提）规则：**
1. 重提**创建新申请号码**，不覆盖原申请；原申请及其快照引用完整保留（可审计追溯）。
2. 未通过/新增加的担保类型，重提时**重新校验并绑定最新落地数据**（生成新的申请-数据绑定，标记为重提场景）。
3. 重提后路由**按新申请重新计算**（LPR/权限矩阵/客户性质以绑定快照为准），不沿用原否决结论。
4. **人工补录他行融资（已定 D14）**：重提时**继承引用原申请的人工补录他行融资数据**，不要求重新录入；若需调整，可在新申请上修改后重新随申请存档。
5. **已批准担保类型直接沿用（已定 D18b）**：重提仅重审未通过/新增类型；**已批准的担保类型连同其最终利率与绑定的数据快照一并保留**，不重新校验、不换绑最新数据。
6. 原申请记录、否决意见、历史意见在新申请的"历史申请"中可查阅。

### 7.6 申请状态机（补齐）

```
DRAFT(草稿) → SUBMITTED(已提交/校验快照) → ROUTING(路由中，权限内审批 or 上会)
   ├─ 权限内审批：APPROVED_LEVEL(权限内已批) → FINAL(终态)                      [不上送]
   ├─ 上会：VOTING(表决中) →
   │      ├─ ≥4 票：COMMITTEE_PASS(小组通过) → PRESIDENT_DECISION(行长决议, 必经)
   │      │        ├─ 同意：FINAL(终态，执行)
   │      │        └─ 一票否决：VETOED(否决) → FINAL
   │      └─ <4 票：REJECTED(否决) → 退回 DRAFT(重提) 或 CLOSED(结束)
   └─ 审批人退回：RETURNED(退回) → DRAFT(重提)

终态：FINAL（含已批/已否/已否决）
```
> **上会必经行长决议（已定 D20a）**：凡上会申请，小组 ≥4 票通过后**必须**经总行行长最终决议（同意→执行；一票否决→否决）才进入终态；权限内终审的申请**不**经过总行行长。

## 8. 数据与数据支撑

> 本节定义系统业务数据（客户/融资/贡献度/征信等）的**来源与数据规则**：数据由**内部数据仓库统一加工提供**（本系统不直接对接外部系统），如何保证审批期间口径一致、提交前做哪些校验、数据时效如何。具体接口、表结构、字段属**详细设计阶段**内容，不在本需求文档范围内。

### 8.1 数据来源总则（需求原则）

> 系统业务数据**统一由内部数据仓库加工后提供**，本系统只消费其成果，不直接对接 CIF/CRM、信贷核心、征信、贡献度平台等系统。数据须支持"**审批当时的数据 = 审批看到的数据**"，避免审批过程中数据变动导致口径漂移。

```
内部数据仓库（统一加工客户/融资/贡献度/征信/机构达成/机构维度等数据）
        │ 按批次提供
        ▼
    业务数据快照（追加保留历史批次，不覆盖）
        │ 申请提交时绑定
        ▼
    申请 ↔ 数据快照固定绑定
        │ 审批/历史审批只读已绑定快照
        ▼
   PC 审批端 / 移动端审批（统一读取申请数据）
```

**需求原则：**
1. 业务数据由内部数据仓库**统一加工提供**，**按本系统要求的落地表结构直接推送到业务库对应表，本系统直接读表访问、不通过接口访问数据仓库**；按批次落地，历史批次追加保留，须可还原某次审批当时的数据（表结构/调度/字段由数据仓库约定，见 §13-C3）。
2. 申请提交时，将客户、融资、关联、贡献度、机构达成等数据**固定绑定**到该申请；审批过程与历史审批只读取已绑定快照。
3. 人工/Excel/OCR 补录与仓库权威数据**分离存储**，并关联证明材料；补录不回写仓库权威数据。
4. 移动端**不直连**数据仓库，只通过审批详情读取申请已绑定的数据。
5. 产品利率参数（LPR、权限利率）作为**系统参数**维护，不由数据仓库提供。

### 8.3 贡献度口径（决议 D13/D15）

**当前贡献度（数仓取数）：**

- **勾稽**：数据仓库传入当前综合贡献总额，本系统对明细加总，两者做差额校验：
  - 差额为 0 → 通过；差额在可配置容差内 → 预警；超过容差或必填指标缺失 → **校验失败（默认不允许提交审批）**。
- **指标口径（已定 D13）**：**数据仓库传入的"存款日均/贷款日均"为业务余额**。因此业务余额类指标**不得**与收入/中收类指标直接汇总为"综合贡献"；系统须分口径展示，综合贡献金额的折算由数据仓库负责。
- **总额来源（已定 D13）**：**数据仓库同时传入当前综合贡献总额与指标明细，由本系统对明细加总并勾稽**。系统不自行折算贡献金额。
- **统计区间（已定 D13）**：对公、本人、关联人当前贡献度使用**统一计算区间**（同一统计区间、同一计算版本）。
- **指标展示维度**：当前贡献度指标须按"对公 / 对私本人 / 关联人"三范围、并区分"业务余额 / 收入中收 / 折算贡献"三类口径分别展示；各范围数值不得混和汇总（见 §9）。

**拟达成贡献度（申请录入，已定 D15/D21）：**

- **来源**：客户经理申请时按申请/担保类型逐笔录入（对公/对私/关联人指标维度），作为本笔申请的承诺基线。
- **规则**：随申请存档、审批期间不变；**不做勾稽校验、不设时效限制**（因它以数仓当前贡献度为实际达成值比对，详见达成跟踪）。
- **承诺类型"其它"（手工录入）**：承诺类型下拉新增"其它"，由客户经理**手工录入**，**目标值可为金额（万元）或自由文本描述**（存 `commitment_desc`）；数仓当前贡献度**无"其它"指标**（数仓不产），故该承诺项**不做数值达成跟踪**——**不计入机构达成率分母（D19）**（分子无数仓"其它"实际达成值，计入将致分母虚高失真）；**跟踪方式为客户经理手工描述**：在承诺跟踪页手工填写跟踪内容（textarea，存 `track_desc`）留痕，不计算数值达成率、不参与月报提醒；展示标注"手工描述跟踪，无数值达成率"。
- **达成跟踪（已定 D21，拟达成最终以数仓贡献度跟踪）**：拟达成贡献度**不自行承担"实际达成"追踪**；达成与否以**数仓加工的当前贡献度**（最近一次跑批，客户级·逐指标）为**实际达成值**判定：
  - 将同一客户跨申请/担保类型的**拟达成承诺按指标 code 加总**，聚合为**客户级承诺基线**（分母）；
  - 与**数仓最近批次当前贡献度**同指标实际值（分子）**逐项对比**，计算达成率与落差；
  - 按月推送落差提醒（F6）。
- **展示**：与数仓当前贡献度**并列展示**给审批人，作为定价参考。

### 8.4 申请提交前必做校验

1. 客户数据存在且证件匹配唯一。
2. 存量客户本行融资合同数据存在，原利率与合同利率一致。
3. **当前贡献度**数据未超时效、明细完整且勾稽通过；**拟达成贡献度**须已录入且完整（不做勾稽）。
4. 主客户、关联人**当前贡献度**统计区间完全一致。
5. 征信报告解析完整（无时效限制，D13）；解析不完整时须补充证明材料。
6. 人工补录他行融资必须记录来源方式、操作人、时间、关联附件，且**按申请逐笔录入**（申请级数据，D13）。
7. 仓库数据存在阻断级质量问题时不允许提交。

### 8.5 数据时效

| 数据类型 | 建议有效期 | 过期处理 |
|---|---|---|
| 对公/对私客户主数据 | 1 天 | PC 提交前重新查询最新数据 |
| 本行融资 | 实时或 ≤1 天 | 阻止提交 |
| 抵押物/担保人 | 实时或 ≤1 天 | 阻止提交；客户经理可申请时补充 |
| 征信报告 | **不作时效限制（已定 D13）** | 不设有效期阻断 |
| 当前贡献度 | T+1，最多 2 自然日 | 超期阻止提交或按参数降级 |
| 拟达成贡献度 | **随申请存档、不设时效限制**（D15） | 不参与时效校验 |
| 机构达成情况 | T+1/月度 | 展示数据日期与预警 |

### 8.6 接口与渠道边界

- **PC 客户经理端**：允许查询最新落地数据（填表视图仅供预览）、提交前执行时效/质量校验、人工/Excel 补录他行融资（须传佐证）、提交时将数据与申请绑定。
- **PC/移动审批端**：仅读取申请已绑定的数据；**不提供"刷新外部数据"能力**；客户/融资/贡献度/机构达成均只读；移动端只做审批操作，不发起申请、不写数据。（移动端审批操作须记录渠道 PC/移动、设备、操作人、时间，满足审计。）
  - **移动端调价终审（已定 D17）**：移动端允许审批人执行"权限内调价确定最终利率"；调价走**与 PC 完全相同的 D2 下限校验**（硬下限/节点下限，越限阻断并提示），最终利率变更需二次确认并落审计轨迹。

### 8.7 提交事务（一致性要求）

申请提交时，以下动作作为一个**原子事务**，任一步失败整体回滚：锁定申请版本 → 以**最新落地数据**重新校验时效/质量/一致性（已定 D20b，填表视图仅预览，提交阈值取最新）→ 写入申请及分项、关联人、人工补录融资及附件 → 建立申请与数据的绑定 → 生成审批任务。

### 9.0 当前贡献度指标一览（依据《XX企业贡献度测算明细》模板核对指标构成）

| `PUBLIC_PROJECT_LOAN_AVG` | 项目贷日均 | 数仓直接提供的贡献度金额 |
| `PUBLIC_DISCOUNT_SPREAD` | 贴现规模 | 数仓直接提供的贡献度金额 |

**当前贡献度（数仓取数）：**
- 直接展示金额数值（万元），系统不做公式计算，仅校验与汇总（§5.1）。**系统须做总额与明细勾稽**，勾稽不平（超容差）不展示为单一总额、且默认阻止提交（见 §8.3）。
- **综合贡献总额（已定 D13）**：当前综合贡献总额由**数据仓库折算后提供**，系统不对业务余额/收入自行折算，也不跨口径拼接"综合贡献"。
- **分口径展示（已定 D13，因"存款日均/贷款日均"为业务余额）**：
  - **企业客户** 对公类明细 = 存款日均、项目贷日均、贴现规模、中间业务收入、结售汇业务总量、代发客户数、代发金额、对公财富中收；（+ 对私本人、关联人的存/贷/财富明细）。
    > ✅ **对公类指标已核对（清单见 §9.0）**：以 PRD docx 用户修订版为准；**指标值为数仓直接提供的贡献度金额，业务系统直接加总勾稽，不做参数折算**（详见 §9.0、D13）。
    > ℹ️ **派生参考指标（非贡献金额，`value_type='RATIO'`，不参与勾稽）**：存贷比 = 对公存款月均/(流贷月均+项目贷月均)。由数仓随指标表直接提供比率值，供审批参考。
  - **个人客户** 明细 = 对私本人（存/贷/财富，企业关系人=法人/董事/实控人/董事长）+ 关联人（存/贷/财富）；
  - 业务余额类（日均）与收入/中收类**分口径展示，不直接相加**生成综合贡献；综合贡献以数据仓库折算值为准。
- 当前贡献度指标按"对公 / 对私本人 / 关联人"范围、"业务余额 / 收入中收 / 折算贡献"口径分别展示，业务余额类不得与收入类直接汇总（见 §8.3）。
- **关联人（已定）**：**关联人是谁由客户经理申请时录入**（姓名/关系/证件号；若在客户信息查中则匹配为关联人）；**数仓只提供关联人的贡献度明细**（作为当前贡献度 `RELATED` 范围指标，按关联人证件号反查），关联人贡献度并入当前贡献度展示（D15）。

**拟达成贡献度（申请录入）：**
- 客户经理发起申请时按申请/担保类型录入**拟达成贡献度**（对公/对私/关联人指标维度），作为本笔申请**承诺基线**，随申请存档、审批期间不变（D15）。
- 拟达成贡献度**不做勾稽校验、不设时效限制**（D15）；其作为**承诺基线（分母）**参与达成对比。
- **承诺类型"其它"（手工录入）**：承诺类型下拉新增"其它"，由客户经理手工录入，**目标可为金额或描述文本**；数仓无"其它"指标，**不做数值达成跟踪**——**不计入机构达成率分母（D19）**，**以客户经理手工描述跟踪**（textarea 留痕，无数值达成率）（见 §8.3）。
- **达成跟踪（已定 D21）**：系统**不用拟达成贡献度自行追踪实际达成**，而以**数仓最近批次当前贡献度为实际达成值（分子）**判定达成——将同一客户跨担保/申请的**拟达成承诺按指标 code 加总**为**客户级承诺基线**，与数仓同指标实际值逐项对比，算达成率并**按月推送落差提醒**（F6）。
- 拟达成贡献度与数仓当前贡献度在审批界面**并列展示**，便于审批人对照"现有贡献 vs 预期贡献"定价。

**其他指标：**
- 客户性质判定（§5.3，D6）：当前有账户且有历史贷款余额 = 存客；有账户无历史余额 = 新客。数据源为客户主数据每日同步（快照批次），申请创建时绑定快照存档，审批期间口径稳定。
- **机构达成率（已定 D13/D19）**：分母**按贡献金额计算**（机构达成率 = 已达成贡献金额 / 应达成贡献金额），非按申请数/承诺数/客户数。**分子"已达成贡献金额"以数仓当前贡献度（最近批次，客户级）为准；分母"应达成贡献金额" = 该机构**已通过审批**的申请所录入的拟达成贡献度（承诺）合计（**不含"其它"手工项**）**（D19/D21，口径同源：分子=数仓实际达成，分母=承诺基线）。
- **人工补录他行融资（已定 D13/D14）**：为**申请级数据**，随申请存档、按申请逐笔录入，不做客户级跨申请复用；**重提时继承引用原申请补录数据**（D14，见 §7.5），可调整后重新随申请存档。

## 11. 验收标准（EARS）

**Ubiquitous（系统始终满足）**
- 系统须以 LPR 系统参数为基准换算各审批权限阈值，LPR 调整后经配置更新自动生效，无需修改规则代码。
- 系统须对利率申请按权限矩阵（§7.2）自动路由终审岗位，不依赖人工选择。
- 系统校验申请利率须满足 申请利率 ≥ max(业务绝对下限, 终审岗位节点下限)，任一不满足则拦截并提示（D2）。
- 系统须在申请提交时将所有数据快照固定绑定到申请，审批过程与历史审批只读取已绑定快照（见 §8.1）。
- 系统须保证客户经理仅在 PC 端发起申请与录入，移动端只承载审批、不暴露申请/录入/数据刷新能力（D10）。

**Event-driven（事件触发）**
- 当申请利率低于对应岗位权限下限时，系统须自动提交存贷款利率审批小组表决。
- 当小组 6 名成员全部完成投票后，系统须判定：赞成票 ≥4 则审批通过并执行申请利率，否则否决并退回。
- 当客户**以数仓当前贡献度（最近批次）为实际达成值**对比承诺基线，发现**拟达成贡献度未达成**时，系统须按月向支行行长及审批小组成员推送落差提醒。

**Unwanted（异常/故障）**
- 若小组表决赞成票不足 4 票，系统须将申请标记为否决并退回申请人。
- 若总行行长行使一票否决，系统须将申请标记为否决，无论小组表决结果。
- 若数据存在阻断级质量问题、或**当前贡献度**勾稽失败、或任一数据超时效，系统须阻止申请提交并提示原因（见 §8.4/8.5）。

**State-driven（特定状态下）**
- 当审批处于"权限内审批"状态时，审批人可在权限内调整利率并确定最终利率。
- 当审批处于"小组表决"状态时，审批人仅可就申请利率投赞成/反对，不可修改利率。
- 当申请为非国企新增授信且落在支行行长权限内时，系统须由支行行长确定最终利率并结束流程，不再上送（D3）。
- 当授信方案含多种担保类型时，系统须对每种类型独立计票，各自≥4票通过方执行该类型利率；任一类型未过则仅该类型退回（D5）。
- 当申请被退回重新提交时，系统须创建新申请并重新绑定最新快照，原申请及快照引用完整保留（见 §7.5）。

**Optional（可选）**
- where 客户为新增客户，系统可不带出本行合同利率与历史履约，并展示空态。
